<a id="section-01"></a>
## DB 정본과 운영 원칙

정본은 서버 `/var/lib/blog/blog.db`, 로컬 `blog.db`는 이관 작업본이다.
평소에는 `deploy/fetch-db.sh`로 **새 백업**을 받아 `backups/`에 저장한다.
로컬 작업본은 자동으로 덮지 않는다. 이관 결과를 올릴 때만 `deploy/upload-db.sh`를 사용한다.
실제 배포·HTTPS·OAuth 활성화·백업 설치 명령은 [deploy/README.md](../deploy/README.md)에 있다.

- CI는 바이너리만 배포한다. DB는 덮지 않는다. 바이너리는 같은 파일시스템 안에서 rename하고
  blog 자체·Caddy 경유·외부 HTTPS 응답을 확인한다. 되돌리기는 revert 후 재배포한다.
- blog는 `127.0.0.1:8080`, Caddy는 80/443을 사용한다. 프록시 헤더 신뢰는 이 연결 구조에 의존한다.
  `deploy/Caddyfile`이 설정의 정본이다. 운영에 `-drafts`를 넣지 않는다.
- Admin 활성화는 `/etc/blog/admin.env`의 `BLOG_ADMIN_FLAG`다. 설정 파일은 저장소 밖에 있고
  0600 root:root로 관리한다. secret을 명령 인자·셸 히스토리·저장소에 남기지 않는다.
- WAL 본체만 복사하면 최신 변경이 빠질 수 있다. 일관된 스냅샷을 만들고 integrity_check한다.
  동기화 비교는 행을 추출해 확인한다. posts의 id·slug·status·updated_at 지문만으로 본문·설정 등
  DB 전체의 동일성이 증명되는 것은 아니다. 변경 대상 값과 렌더링 결과도 확인한다.
- 백업은 `VACUUM INTO`로 만들고 열어서 확인한다. 새 백업 성공 후 오래된 것을 지운다.
  인스턴스 안에 7벌을 유지하는 기존 구성과 외부 자동 백업은 다른 문제다.
- 운영 환경의 포트·방화벽·인증서 만료일·콘텐츠 개수는 직접 확인해야 한다.
  과거 점검 결과를 현재 보증으로 쓰지 않는다.

<a id="section-02"></a>
### 업로드 가드

현재 구현의 정본은 `deploy/upload-guard.sql`이다. 한 줄이라도 나오면 멈추며 우회 스위치를 만들지 않는다.

| 표시 | 현재 조건 |
|---|---|
| LOST | 서버 글이 업로드 DB에 없음. 출처 전체를 보되 curation의 의도된 DropPosts는 예외 |
| STALE | 같은 slug에서 서버 updated_at이 더 최신 |
| LOSTIMG | 서버 이미지가 업로드 DB에 없음. 의도된 DropImages는 예외 |
| BACK | 업로드 DB에만 있는 `source = 'native'` 글이 되살아남 |

GitHub 이관 이후 notion_page_id가 NULL이라는 이유만으로 native로 보면 안 된다.
웹에서 만든 글은 source=native, notion_page_id=NULL을 유지한다.
이관 대상 편집은 재이관이 덮을 수 있으므로 가드 통과만 믿지 말고 변경 내용을 비교한다.
백업·가드·서비스 정지·WAL 정리·교체·응답 확인은 기존 업로드 스크립트 흐름을 따른다.

<a id="section-03"></a>
### 로컬에서 확인하기

서버 시작도 마이그레이션을 적용한다. UI·편집 검증은 실제 작업본이 아닌 사본으로 한다.
받아온 백업이 압축되어 있으면 별도 파일로 해제한 뒤 확인한다. 쓰기 중인 DB 본체만 cp하지 않는다.
예를 들어 로컬 작업본에서 일관된 사본을 만들 때는:

```sh
# 출력 경로는 존재하지 않는 새 이름을 사용한다.
sqlite3 blog.db "VACUUM INTO '/tmp/blog-review.db';"
sqlite3 /tmp/blog-review.db 'PRAGMA integrity_check;'
go run ./cmd/blog -db /tmp/blog-review.db -addr 127.0.0.1:8080
# 인증 없이 편집 확인: loopback에서만 허용된다.
go run ./cmd/blog -db /tmp/blog-review.db -addr 127.0.0.1:8080 -admin -admin-no-auth -drafts
```

두 서버 명령은 같은 포트를 사용하므로 하나를 종료한 뒤 다른 모드로 실행한다.
GitHub 로그인까지 확인하려면 gitignore된 환경 파일로 OAuth 설정을 공급하고
`-admin-no-auth`를 빼며 callback은 `http://127.0.0.1:8080/admin/auth/callback`로 등록한다.
운영 callback은 `https://inquieto.dev/admin/auth/callback`이다.

<a id="section-04"></a>
### 재이관 순서와 보존 경계

```sh
go run ./cmd/import -db <작업-사본>
go run ./cmd/relink -db <작업-사본> -apply
go run ./cmd/categorize -db <작업-사본> -apply
go run ./cmd/regroup -db <작업-사본> -apply
```

새 분류가 생기면 categorize → regroup을 두 바퀴 돌려 수렴을 확인한다.
필요할 때 sortorder를 적용하고 postparent는 해당 카테고리별로 실행한다.
명령 인자의 `<작업-사본>`은 실제 경로로 바꾼다. 이관이 운영 웹 편집을 대체할 수 있다는 점을 먼저 확인한다.

- 노션 글 멱등 키는 notion_page_id, 이미지 키는 sha256이다. 이관은 트랜잭션으로 처리한다.
- 일반 재이관은 created_at을 보존하고 updated_at을 변경한다. 제목·본문 등 이관 소유 필드는 덮을 수 있다.
- import 후에는 relink가 필요하다. 분류·표지·본문 보정은 아래 curation 계약을 따른다.
- 운영 DB에 직접 반영할 값과 재이관용 예외 표를 함께 관리한다. 표만 바꿔도 운영 DB가 자동 갱신되지는 않는다.
- 글·이미지·분류의 현재 건수는 대상 DB나 예외 표에서 확인한다. 오래된 수치를 지침에 복사하지 않는다.

<a id="section-05"></a>
## 카테고리

**최대 3단계다.** 현재 분류 개수는 대상 DB에서 확인한다.

**중간층이 늘 노션 최상위인 것은 아니다** (2026-08-21). `데이터 & 수리`는 노션
최상위 하나(`수학 & 통계`)에 이론·응용·머신러닝이 다 들어 있어서 사람이 세 갈래로
갈랐다. 그 갈래는 노션에 없는 층이라 `source_name`이 NULL이고, `cmd/regroup`의
`subs`가 만든다. 노션 최상위였던 `수학 & 통계`와 `머신러닝 & 딥러닝`은 할 일이
없어져 `DropCategories`로 없앴다.

```
데이터 & 수리                  ← 사람 (groups)
├─ 수리/통계: 이론             ← 사람 (subs)
│   └─ 선형대수 …              ← 노션 2단계
├─ 수리/통계: 응용
└─ 머신러닝
```

**`개발`은 `members`와 `subs`를 함께 쓴다** (2026-08-23). Language·리눅스 & 쉘·
tooling은 노션 최상위가 그대로 한 갈래인데, `웹 프로그래밍` 77편만은 배운 순서
(Django → Spring)와 곁다리로 붙은 것들(HTML/CSS, React, 로그인, 웹소켓)이 한 갈래에
뒤엉켜 있었다. **3단계가 끝이라 `웹 프로그래밍 > 백엔드 > Django`로는 못 내려간다** —
그래서 웹 프로그래밍 자리를 두 갈래가 대신하고, 그 분류는 `DropCategories`로 없앴다.

```
개발                           ← 사람 (groups)
├─ Language …                  ← 노션 최상위 (members)
├─ 리눅스 & 쉘
├─ tooling
├─ 서버 & API                  ← 사람 (subs)
│   └─ Django · Spring · Node.js
└─ 클라이언트 & UI
    └─ Javascript · React · 모바일 프로그래밍
```

- **이름을 "프론트엔드"가 아니라 "클라이언트 & UI"로 뒀다.** 그 밑에 모바일
  프로그래밍(Swift/UIKit)이 들어간다. 웹만 가리키는 말이면 어긋난다.
- **`subs`의 `sort_order`는 `members` 다음부터 센다.** 둘 다 같은 분류의 자식이라
  0부터 다시 세면 사이드바에서 같은 자리를 다툰다. `데이터 & 수리`는 members가
  비어 있어서 이 문제가 안 보였다.
- **입구 글 다섯(Django·Spring·Node.js·Javascript·React)은 같은 이름의 하위 분류로
  내려보내 그 분류의 표지로 삼았다.** école 42에서 쓴 방법과 같다 — 안 그러면
  `서버 & API` 화면에 `Django` 글과 `Django` 분류가 나란히 서서 같은 곳으로 가는
  길이 두 벌이 된다. 나머지 일곱(로그인 5 + 웹소켓 1 + HTML & CSS 1)은 제 분류가
  없어서 두 갈래에 직접 붙였다.
- **`웹 프로그래밍` 표지 글은 뺐다**(`DropPosts`). 본문이 링크 목록과 내용 없는
  `## 실전 프로젝트` 제목뿐이라, 그 목차가 하던 일을 두 갈래가 그대로 대신한다.

**3단계 갈래를 사람이 직접 두는 자리가 생겼다** (2026-09-02, `cmd/regroup`의
`topics`). `subs`는 최상위(group) 밑에만 층을 놓는데, 백준 문제는 그보다 한 칸
아래가 필요했다 — `알고리즘 > 알고리즘: 실전 > 동적 계획법`.

- **categorize로는 못 만든다.** 그 도구는 `original_path`가 알려주는 것만 아는데,
  백준 문제의 경로는 `알고리즘: 실전 > 백준 단계별로 풀기: 1번 ~ 9번 > 1978번:
  소수 찾기`라 **푼 순서**만 적혀 있다. 무엇을 배웠나는 어디에도 없다. 사람이
  정하는 층이라 `groups`·`subs`와 같은 자리에 있는 것이 맞다.
- **부모의 깊이를 regroup이 먼저 본다.** 3단계가 끝이라 부모가 2단계여야 하는데,
  넘으면 002의 트리거가 막아준다 — 다만 그때 나오는 말은 "트리거가 거부했다"라
  무엇이 잘못됐는지 알려주지 않는다.
- **`sort_order`는 표에 적은 순서다.** 갈래 이름은 사람이 지은 것이라 가나다순도
  알파벳순도 뜻이 없다. 지금은 노션에서 온 형제가 남지 않아 0부터 세지만,
  남겨야 할 형제가 생기면 `subs`가 `members` 다음부터 세는 것처럼 고칠 자리다.

- **표지가 가리키는 분류는 `renames`·`topics`·`groups`·`subs`가 이번 실행에서
  만들 slug여도 된다** (2026-09-02, 2026-09-03에 `groups`/`subs`를 더했다).
  `Covers`가 이름이 바뀌거나 새로 생길 분류를 가리키면 그 slug는 아직 DB에
  없는데, 만드는 일도 이름 변경도 계획 검사보다 **뒤에** 일어난다(1a·1b가 3보다
  앞이다). 새 갈래를 놓으면서 그 갈래에 표지를 지정하는 실행이 통째로 멈추던
  자리다 — `프로젝트 > 심심조각`이 실제로 그랬다. 막으면 이름을 바꾸면서
  표지를 지정하는 실행이 통째로 멈춘다 — `Moves`의 `ToSlug`를 받아주는 것과
  같은 이유다. **categorize 쪽은 아예 미룬다**: 그 분류를 만들거나 이름을 바꾸는
  것은 regroup의 일이라, 새 `Covers`를 추가한 직후에는 categorize가 먼저 돌 수
  있다. 실패로 다루면 두 도구가 서로를 기다리는 교착이 된다.
- **표지 글은 `notHidden`을 거친다.** `store.coverSlug`가 숨긴 글을 걸러내므로
  **draft인 표지는 없는 것과 같다.** 그러면 `linkCoveredChildCategories`가 안
  걸려서 표지 본문의 링크가 분류 URL로 안 바뀌고, 같은 이름이 본문과
  `하위 분류`에 두 벌로 나온다. 네트워크의 입구 글 셋이 실제로 그랬다 —
  `Covers`를 적을 때 그 글이 보이는 글인지 함께 봐야 한다(`StatusEdits`).
- **`curation.Moves`의 `ToSlug`는 최상위가 아니어도 된다.** 사람이 둔 중간 층도,
  **노션에서 온 2단계 분류도** 부모가 될 수 있다(2026-09-03에 마지막 것을
  더했다). regroup이 `groups`·`subs`와 `moveTarget` 세 곳에서 찾는다.
  - **2단계여야 한다.** 최상위면 앞의 둘에서 이미 잡히고, 3단계 밑에 매달면
    4단계가 된다. `topics`가 부모의 깊이를 보는 것과 같은 자리다.
  - **그때는 손자가 아니라 자식만 있어도 막는다.** 한 칸이 더 낮아서다 —
    최상위나 중간 층으로 갈 때는 손자만 보면 된다.
  - `클라우드 탐구생활 → 개발 > tooling`이 이 길을 처음 쓴 자리다.
- **새 층을 처음 얹을 때 두 도구가 서로를 기다리지 않게 한다** (2026-08-23).
  categorize가 글을 옮겨야 regroup이 빈 분류를 지울 수 있고, regroup이 층을 만들어야
  categorize가 거기 붙일 수 있다. 새 `subs`를 추가한 직후에는 이게 교착이 된다.
  - **categorize는 아직 없는 `PostMoves` 대상 slug를 기다린다.** 실패가 아니라
    "미룬 글 n건"으로 알리고 그대로 둔다.
  - **regroup은 `Moves`의 `ToSlug`가 DB에 없어도 된다.** `groups`/`subs`에 있으면
    이번 실행이 먼저 만든다(1a·1b가 3보다 앞이다).
  - **regroup은 남은 것이 전부 떠나기로 예정돼 있으면 삭제를 미룬다**
    (`allScheduledToLeave`). 글은 `PostMoves`가, 하위 분류는 `Moves`가 데려간다.
    **하나라도 표에 없으면 예전대로 에러다** — 갈 곳이 정해지지 않은 것을 조용히
    지워서 잃는 것이 그 검사가 막으려는 일이다.
  - 그래서 **categorize → regroup을 두 바퀴** 돌려야 수렴한다. 세 번째 바퀴는 0건이다.
- **`categories.sort_order`는 categorize가 덮지 않는다** (2026-09-02에 고쳤다).
  형제 순서는 사람이 정하는 것이라(regroup의 `members`·`subs`·`topics`) 경로가
  알려줄 수 있는 것이 아니다. 예전에는 두 도구가 같은 칸을 서로 다른 방식으로
  썼다 — categorize는 계획 전체를 훑는 **전역 색인**을, regroup은 **부모별
  색인**을 넣어서 **나중에 돈 쪽이 이겼다.** `categorize → regroup`과
  `regroup → categorize`가 실제로 다른 값을 남겼고, 이 문서가 금지하는 바로
  그 싸움이다. 이제 categorize는 **처음 만들 때만** 순서를 정한다 —
  `name`/`slug`/`parent_id`를 안 덮는 것과 같은 이유다.
- **`DropCategories`는 categorize도 봐야 한다.** 안 그러면 regroup이 지운 분류를
  categorize가 다음 실행에서 되살려서, 두 도구를 번갈아 돌릴 때마다 트리가 달라진다.
  실제로 그렇게 됐다가 고쳤다.
- **regroup은 이름을 바꾸기 전에 먼저 지운다.** 없앨 분류가 쓰던 slug를 다른
  분류가 물려받는 경우가 있어서(`핸즈온 머신러닝 2` → `머신러닝: 기초이론`),
  나중에 지우면 UNIQUE에 걸린다.
- **사람이 만든 최상위 분류를 없앨 때는 `groupDrops`를 쓴다.**
  `curation.DropCategories`는 멱등 키가 `source_name`이라 노션에서 온 분류만
  지운다 — `groups`가 만든 분류는 그 칸이 NULL이다. 배정표에서 줄만 지우면 그
  분류가 "최상위인데 배정표에 없다"로 계획 검사에 걸린 채 남는다.
  안전장치는 `DropCategories`와 같다: 글도 자식도 없을 때만 지운다.
- **`allScheduledToLeave`는 지워질 자식도 떠나는 것으로 센다.** 예전에는
  옮겨지는 것(`Moves`)만 셌는데, 그러면 자식이 전부 `DropCategories`에 있는
  부모가 "예정에 없는 것이 남았다"로 멈춘다. 커리어를 뺄 때 `취업 준비`가
  실제로 그랬다.
- **최상위 분류의 slug를 바꿀 때는 `groupRenames`를 쓴다.** `groups`는 slug가
  멱등 키라 배정표에서 slug만 바꾸면 새 행이 하나 더 생기고 옛 행이 자식을 안은
  채 남는다.

```
dev > Language > 프로그래밍 언어
└ 사람이 정함    └ 노션 최상위    └ 노션 2단계
  (regroup)        (categorize가 original_path에서 뽑음)
```

두 도구가 층을 나눠 맡는다. 순서는 상관없고 몇 번을 섞어 돌려도 결과가 같다.

| 도구 | 하는 일 | 멱등 키 |
|---|---|---|
| `cmd/categorize` | `original_path`에서 분류를 뽑아 글에 붙임 | `source_name` |
| `cmd/regroup` | 사람이 정한 층·이름·순서를 반영 | `slug` |

```sh
go run ./cmd/categorize -db blog.db -apply
go run ./cmd/regroup -db blog.db -apply
```

- **`source_name`이 카테고리의 안정적인 키다** (003에서 추가). `name`/`slug`는 사람이
  바꿀 수 있고 실제로 바꿨다(소프트스킬 → tooling). slug를 키로 쓰면 categorize가
  이름 바뀐 카테고리를 못 찾고 옛 이름으로 다시 만들면서 글까지 가져간다.
  실제로 그렇게 됐다가 003으로 고쳤다.
- `source_name`이 NULL인 카테고리는 사람이 만든 상위 분류다(dev, cs-theory 등).
  categorize는 그런 건 건드리지 않는다.
- **categorize는 이미 있는 카테고리의 `name`/`slug`/`parent_id`를 덮지 않는다.**
  사람이 바꾼 걸 존중한다. 처음 INSERT할 때만 경로가 알려준 부모를 쓰고, 그 뒤의
  이동은 사람 몫이다(regroup). 덤프가 고정이라 경로가 나중에 달라지지 않으므로
  잃는 것도 없다.
- **깊이 제한은 트리거가 지킨다** (002). 삽입과 이동 양방향을 보고, 이동할 때는
  딸려가는 서브트리 높이까지 계산한다. 001의 트리거는 "새 부모가 이미 자식인가"만
  봐서, 자식이 있는 노드를 옮기면 제한을 조용히 넘겼다.
- 경로에서 뽑을 때 **마지막 요소는 글 제목 자신이라 버린다** (1408건 전부 그렇다).
- **노션 최상위 페이지 19개는 자기 카테고리의 "표지 글"이다.** 경로가 자기 제목뿐이라
  조상이 없지만, 그 제목이 하위 글들의 경로에서 카테고리 이름으로 등장한다. 그 이름과
  맞으면 같은 이름의 카테고리에 붙이고 **`categories.cover_post_id`로도 이어둔다** (004).
  방향을 categories → posts로 잡은 이유: 카테고리당 표지는 하나다. posts 쪽에 깃발을
  두면 한 카테고리에 표지가 여럿 생기는 걸 스키마가 못 막는다.
- **`categories.cover_post_id`는 UNIQUE다.** 한 글은 한 카테고리의 표지만 될 수 있다.
  그래서 사람이 표지를 지정하는 건 "새로 만드는" 게 아니라 **"옮기는"** 것이다.
  regroup이 옛 자리를 먼저 비우고, categorize는 그 글이 이미 다른 카테고리의 표지면
  건드리지 않는다(덮으려 들면 UNIQUE에 걸려 categorize 전체가 실패한다).
- 분류 없는 글과 표지 수는 대상 DB에서 확인한다. 특히 데이터베이스 표지의 NULL 기록은 남은 작업에 있다.
- **표지 수를 셀 때 이름이 아니라 DB의 id로 센다.** 사람이 분류 이름을 바꾸면
  계획의 이름과 실제 slug가 갈라진다. 또 **한 글은 한 카테고리의 표지만 될 수
  있어서**(UNIQUE), 사람이 어떤 글을 다른 분류의 표지로 가져가면 경로가 그 글을
  표지로 두려던 카테고리는 표지를 잃는다(`최인렬 (Inryeol Choi)` → `/intro`).
- slug는 소문자 + 공백/`:`/`/`/`.`→하이픈, 나머지 기호는 버린다. **한글은 그대로 둔다.**
- 같은 2단계 이름이 서로 다른 부모 밑에 나오거나, 서로 다른 이름이 같은 slug가 되면
  **에러로 멈춘다.** 조용히 한쪽으로 몰면 트리가 조작된다.

<a id="section-06"></a>
### 사람이 정한 예외 (`internal/curation`)

categorize는 `original_path`가 알려주는 것만 안다. 노션에서 어디에 뒀느냐와
블로그에서 어디에 두고 싶으냐가 다를 때 그 차이를 `internal/curation`에 적는다.
**regroup이 이대로 DB를 고치고, categorize는 이걸 "경로와 다르다"고 트집잡지 않는다.**
두 도구가 같은 표를 봐야 해서 별도 패키지로 뺐다.

| 표 | 뜻 | 멱등 키 | 보는 쪽 |
|---|---|---|---|
| `Moves` | 카테고리를 사람이 정한 다른 분류 밑으로 | `source_name` | categorize·regroup |
| `Covers` | 사람이 정한 분류에 표지 글 붙이기 | `notion_page_id` | 〃 |
| `PostMoves` | 글 하나를 경로와 다른 카테고리에 붙임 | `notion_page_id` | 〃 |
| `PostMetadataEdits` | 글 제목·원작성일·순서를 사람이 지정 | `notion_page_id` | import·sortorder |
| `PostTitleEdits` | 작성일·순서는 유지하고 글 제목만 지정 | `notion_page_id` | import |
| `StatusEdits` | **글의 status를 사람이 지정** | `notion_page_id` | **import** |
| `DropCategories` | 카테고리 없애기 | `source_name` | 〃 |
| `DropPosts` | **글을 이관에서 뺌** | `notion_page_id` | **import** |
| `DropImages` | **이미지를 DB에서 뺌** | `sha256` | **import** |
| `BodyEdits` | **본문에서 줄 삭제·교체** | `notion_page_id` | **import** |
| `BodyAppends` | **본문 끝에 지속적으로 덧붙임** | `notion_page_id` | **import** |

- 키는 전부 사람이 바꾸지 않는 값이다. 이름이나 slug를 바꿔도 안 깨진다.
- 표에서 빼면 다음 categorize 실행이 "경로와 다르다"고 **실패한다.** 되돌리려면
  regroup으로 제자리에 돌려놓은 뒤에 뺀다.
- **`PostMoves`는 경로 처리보다 먼저 걸린다.** 옮긴 글의 경로는 카테고리를 만드는 데
  아예 쓰이지 않아서, 한 카테고리의 글이 전부 옮겨지면 그 카테고리가 계획에서 사라진다.
  `DropCategories`가 남은 빈 행을 지운다. 노션의 `프로젝트` 하위 분류를 이렇게 없앴다.
- **단, 옮긴 글의 1단계 조상 분류는 계획에 남긴다.** 안 그러면 그 분류의 존재 근거가
  옮긴 글들뿐일 때 분류가 통째로 사라지면서 **자기 표지 글까지 카테고리를 잃는다.**
  실제로 `최인렬 (Inryeol Choi)` 밑의 글이 이 6건뿐이라 그렇게 됐다가 고쳤다.
- **`DropCategories`는 글도 자식도 없을 때만 지운다.** 남아 있으면 에러로 멈춘다.
  그래서 순서가 있다: `categorize`로 글을 먼저 옮기고 그다음 `regroup`으로 지운다.
- 네 도구(categorize · regroup · sortorder · postparent)를 어떤 순서로 몇 번
  돌려도 결과가 같아야 한다. 바꾼 뒤에는 그걸 확인할 것.

**`DropPosts`와 `DropImages`는 이 프로젝트의 원칙에 대한 예외다.** 원래 글은
지우지 않고 status로 가린다. 그래서 표에 이유를 함께 적는다. **DB에서 행만 지우면
안 된다** — 덤프에 있는 한 다음 `import -db`가 다시 넣는다. 여기 적어두면 변환·이미지
이관에서 건너뛰고, `runImport`가 기존 DB 행도 같은 트랜잭션에서 지우므로 몇 번을
다시 이관해도 안 돌아온다. 현재 대상은 예외 표에서 확인한다.

- **잎부터 지운다.** `posts.parent_id`가 `ON DELETE RESTRICT`라 부모를 먼저 만나면
  FK가 막는데, 자식까지 전부 표에 있으면 그건 고아가 생기는 것이 아니라 **순서
  문제**다. 커리어 42편을 통째로 뺄 때 실제로 걸렸다. `runImport`가 한 바퀴에
  지울 수 있는 것만 지우고 더 못 지울 때까지 돈다. **그러고도 남으면 에러다** —
  표에 없는 자식이 매달려 있다는 뜻이고, 그건 그 FK가 막으려는 바로 그 일이다.

**`BodyEdits`만 보는 쪽이 다르다** — 분류가 아니라 **본문**을 고치기 때문에
`cmd/import`가 변환 직후에 적용한다.

- **DB의 body를 손으로 고치지 않는다.** 고쳐두면 `import -db`를 다시 돌릴 때
  변환 결과가 덮어써서 되살아난다(relink 재작성이 날아가는 것과 같은 성질).
  여기 적어두면 몇 번을 다시 이관해도 같은 결과가 나온다.
- **`out/`에 쓰기 전에 적용한다.** 검토용 파일과 DB에 들어가는 것이 같아야 한다.
- **줄 단위로만 지우거나 바꾼다.** 문장 중간을 고치면 앞뒤가 어떻게 이어지는지
  표만 보고는 알 수 없다. 지운 자리에 빈 줄이 겹치면 하나로 줄인다.
- **못 찾으면 그 페이지의 변환이 실패한다.** 덤프가 고정이라 변환 결과도 고정이다.
  안 맞으면 표가 낡았거나 변환기가 바뀐 것이지 "그냥 없는" 경우가 아니다.
  조용히 넘어가면 지웠다고 믿는 것이 본문에 그대로 남는다.
- 전체를 돌린 실행에서는 **표에 있는데 한 번도 안 걸린 항목**도 리포트가 짚는다.
- 현재 8줄: 선형대수의 죽은 링크 2개, 소개 글의 증명사진과 `[프로젝트]` 링크,
  핸즈온 머신러닝 2의 `연습문제 2` 제목과 유일한 글 링크, 최적화이론 표지의
  `[수업 : 통수 & 선계]` 묶음 링크, R 표지의 `[R언어 : 시각화]` 묶음 링크다.
- **행을 전부 빼면 그 묶음 링크도 함께 빼야 한다.** 인라인 데이터베이스는 posts에
  행이 없어서, 펼칠 글이 하나도 안 남으면 렌더링이 짝을 못 찾고 링크를 그대로 둔다 —
  눌러도 404다. 선형대수와 R이 그래서 링크째 없앤 자리다.
- 별도로 수리통계2 표지의 참고자료 링크 4줄은 링크 대상은 유지하고 표시 제목 끝의
  불필요한 `(1)`만 교체한다. 대상 글 제목도 `PostTitleEdits`로 함께 맞춘다.
- 핸즈온 머신러닝 2 표지의 `모르면 여기, 저기 클릭!`은 `여기, 저기`가 존재하지 않는
  페이지라 404였다. 깨진 링크와 문구를 없애고 정상 링크 하나인 `모르면 클릭!`으로
  교체한다.
- **원본에 없던 긴 보충 본문은 `BodyAppends`로 덧붙인다.** marker가 이미 있고 내용이
  같으면 그대로 두어 멱등이고, marker만 같은 다른 내용이 있으면 덮어쓰지 않고
  실패한다. 해답은 각각 `<details>` 안에 있어 제목을 클릭해야 보이며 문제 이미지와
  문제 글은 항상 보인다. 현재 세 글에 붙는다:
  - 확률과정론 `중간 & 기말` (중간·기말)
  - 수리통계1 `연습문제와 시험` (연습문제 1·2, 중간·기말) — 문제가 전부 시험지
    **사진**이라 읽어서 옮긴 뒤 풀었다. 연습문제 1의 1번은 인쇄된 분포함수가
    그대로는 **감소해서** 분포함수가 될 수 없어(계수 0.4/0.8이 뒤바뀐 것으로 보인다)
    그 해석을 풀이 안에 적어뒀다.
  - 수리통계2 `수리통계2 - 시험` (중간·기말) — 신뢰구간 문항의 힌트값
    $t_{0.025}(5)=2.571$이 자유도 5의 값이라 $n-1=4$와 어긋난다. 힌트를 그대로
    쓰되 그 사실을 본문에 적었다.
- **`BodyEdits`도 글마다 파일을 나누고 `body_edits.go`가 합친다** (2026-09-02).
  빈 절을 통째로 채우는 손질이 생기면서 한 글의 표가 수백 줄이 됐다. 나눠 두면
  다른 줄 하나를 고칠 때 그 덩어리를 지나가지 않아도 된다.
  - **`Replace`에 여러 줄을 넣을 수 있다.** `replaceLine`이 줄 하나를 갈아끼운
    뒤 다시 이어붙이므로 제목 한 줄을 제목 + 본문으로 바꾸는 것이 그대로 된다.
    `BodyAppends`는 글 끝에만 붙일 수 있어서 **본문 가운데를 채울 때** 이 길을 쓴다.
  - **같은 줄이 두 번 나오면 앞엣것을 먼저 다른 글자로 바꾼다.** `replaceLine`은
    첫 번째 것만 건드리므로, 뒤엣것을 고치려면 앞엣것이 더 이상 안 걸리게 해야
    한다(다항분포의 `Y_{1} \\`가 좌변 벡터와 모수 벡터에 각각 있었다).
    그래서 **표의 차례가 곧 의미다** — 순서를 바꾸면 깨진다.
  - `concatBodyEdits`는 `concatBodyAppends`와 달리 **중복을 막지 않는다.**
    같은 줄을 일부러 두 번 고치는 것이 정상적인 쓰임이기 때문이다.
- **해답 표는 글마다 파일을 나누고 `body_appends.go`가 합친다.** 한 글의 해답이
  수백 줄이라 한 파일에 다 넣으면 다른 표를 고칠 때마다 그 덩어리를 지나가야 한다.
  `concatBodyAppends`는 **같은 (글, marker) 짝이 두 번 나오면 멈춘다** — 그대로 두면
  `appendBody`가 "marker는 있는데 내용이 다르다"로 잡는데, 그 말로는 표가 겹쳤다는
  것을 알 수 없다.

<a id="section-07"></a>
## GitHub 이관 (2026-09-01)

**노션 말고 GitHub 저장소에서도 글을 가져온다.** 대상은 `internal/curation/github.go`가 정하며,
`Java_Modern`과 `Database-System-Concepts`가 포함되어 있다.

```sh
GITHUB_TOKEN=$(gh auth token) go run ./cmd/importgh -db blog.db          # 미리보기
GITHUB_TOKEN=$(gh auth token) go run ./cmd/importgh -db blog.db -apply   # 반영
```

<a id="section-08"></a>
### 노션 이관과 무엇이 다른가

**노션은 덤프가 고정이라 "몇 번을 돌려도 같은 결과"가 목표였다.** GitHub은
저장소가 계속 바뀌므로 목표가 하나 다르다 — **"다시 돌리면 지금의 저장소와
같아진다"**이다. 그래서 멱등 키가 다르다.

| | 노션 | GitHub |
|---|---|---|
| 멱등 키 | `notion_page_id` | `source_ref` (`github:{repo}@{path}`) |
| 원본 | `scripts/dump/` (고정) | 저장소 (계속 바뀜) |
| 작성일 | 노션 `created_time` | **첫 커밋 시각** |

- **`source_ref`는 `migrations/006`이 만든 칸이다.** slug를 키로 쓰면 안 된다 —
  사람이 admin에서 바꿀 수 있는 값이고, 바꾸는 순간 다음 이관이 같은 글을
  못 찾아 하나 더 만든다. `notion_page_id`를 따로 둔 이유가 정확히 이것이다.
- **작성일은 git이 이미 알고 있다.** 목록에 찍히는 날짜는 "실제로 쓴 날"이어야
  하고(노션도 `original_created_at`을 쓰는 이유다), GitHub에서는 그 값이
  **파일을 처음 커밋한 때**다. GitHub이 커밋을 새것부터 주므로 목록의 **마지막**
  원소가 그것이다. `per_page=100`이라 100번 넘게 고친 파일은 늦어질 수 있는데,
  그때는 리포트에 커밋 수가 100으로 찍혀 눈에 띈다 — 조용히 틀리지 않는다.
- **slug는 갱신 때 안 덮는다.** 사람이 바꿨을 수 있고, 이관이 되돌리면 그
  자리가 사람 것이 아니게 된다. 제목·본문·작성일은 저장소가 정본이라 덮는다.

<a id="section-09"></a>
### 어디에 붙나

`internal/curation/github.go`의 표가 정한다. **표에 없는 파일은 안 가져온다** —
저장소에 파일이 늘어도 조용히 딸려 들어오지 않는다.

- **분류를 만들지 않는다.** 트리를 손대는 곳은 categorize·regroup 둘뿐이어야
  해서, 표에 적은 분류가 DB에 없으면 실패한다.
- **`original_path`에 `Language > 프로그래밍 언어 > Java > 모던 자바`를 적는다.**
  노션 경로 자리를 쓰는 이유는 웹이 그 값의 **세 번째 칸으로 언어 갈래를
  나누기** 때문이다(`web.PathBranches`). 그래야 기존 Java 글과 한 갈래에 선다.
- **제목을 표에 사람이 적는다.** 파일 안의 첫 제목은 `3. 람다식 써보기!`처럼
  파일 사정이 그대로 나오고, 파일 이름은 `chapter3`이다. 둘 다 읽는 사람을
  위한 이름이 아니다. 순서(`sort_order`)도 여기서 정하므로
  `sort_order_manual`이 켜진다(migrations/005).

<a id="section-10"></a>
### 본문에 손대는 세 가지 (`prepareBody`)

**한 쌍이라 한 함수로 묶었다.** 하나만 빠져도 화면이 어긋나고, 예전에는
손질을 따로 테스트해서 호출부에서 하나를 빼도 아무 테스트도 안 깨졌다.

1. **`<javascript>`를 글자로 바꾼다.** 글쓴이는 꺾쇠를 절 제목 표시로 썼는데
   (`<특징>`, `<예시>`), 라틴 낱말은 CommonMark의 태그 이름 규칙에 맞아
   **raw HTML로 통과해 화면에서 사라진다.** 브라우저가 모르는 요소라 아무것도
   안 그린다. 한글 표시는 규칙에 안 맞아 우연히 안전하므로 **건드리지 않는다.**
2. **파일 첫머리의 `# 제목`을 뗀다.** 페이지의 `<h1>`은 템플릿이 그리는 글
   제목이라 본문에도 있으면 같은 말이 두 번 나온다.
3. **남은 제목을 한 단계 올린다.** 떼기만 하면 절이 `##`로 남아 화면에서 h3이
   되고, h1 바로 아래 층이 빈다. 목차 들여쓰기(`toc-h2`/`toc-h3`)도 밀린다.

셋 다 **코드 블록 안은 건드리지 않는다.** 셸 주석(`# 주석`)이나 마크다운을
보여주는 예제가 제목으로 둔갑한다.

<a id="section-11"></a>
### 이미지 (2026-09-02)

**저장소의 그림을 받아 DB에 넣는다** (`cmd/importgh/images.go`). 예전에는
"지금 대상에 이미지가 없다. 생기면 그때 노션 쪽 처리를 그대로 가져온다"고
적어뒀는데, `Database-System-Concepts`가 그 "생기면"이었다.

- **멱등 키는 `images.sha256`이다.** 노션 이미지와 같은 표, 같은 서빙 경로
  (`GET /img/{sha256}`)를 쓴다. 같은 그림이 두 저장소에 있어도 행이 하나고,
  파일 이름을 바꿔도 새 그림이 되지 않는다.
- **왜 링크로 안 두나.** `raw.githubusercontent.com`으로 바꿔 두면 글을 열
  때마다 독자 IP가 GitHub에 가고, 저장소를 지우거나 비공개로 돌리면 그림이
  통째로 사라진다 — 외부 파비콘을 안 불러오기로 한 것과 같은 판단이다.
- **경로는 글 파일 기준 상대경로다**(`./images/x.png`). 그 파일의 디렉터리로
  풀어야 저장소 경로가 나온다.
- **마크다운 `![]()`만 보면 놓친다.** 이 저장소는 가운데 정렬을 하려고
  `<p align="center"><img src="./Images/x.png"></p>` 꼴을 섞어 쓴다. 렌더러가
  `html.WithUnsafe()`라 그 태그가 그대로 나가는데, 주소를 안 바꾸면 **우리
  사이트 안의 없는 경로**를 가리켜 깨진 그림이 된다. 실제로 14장이 그랬고
  리포트는 "못 옮긴 참조 1개"라고 했다 — **찾지 못한 것은 리포트에도 안 잡힌다.**
- **`http(s)://`로 시작하는 것은 안 건드린다.** 저장소 파일이 아니라 남의
  그림이다.
- **SVG는 받지 않는다.** `/img/`가 `images.mime`을 그대로 Content-Type에 실어
  보내는데 `image/svg+xml`은 브라우저가 문서로 열고 그 안의 `<script>`가
  **우리 도메인에서** 실행된다. admin 업로드가 SVG를 막는 것과 같은 이유다.
- **못 받은 그림은 원문 그대로 둔다.** 주소만 `/img/`로 바꿔 두면 깨진 그림이
  멀쩡해 보인다 — 죽은 링크를 노션 형태로 남기는 relink의 판단과 같다.
  리포트가 어느 경로를 못 받았는지 이름으로 짚는다.
- Contents API는 1MB가 넘는 파일에 내용을 안 실어 주므로 그때는
  `download_url`을 한 번 더 따라간다.

<a id="section-12"></a>
### 데이터베이스 (2026-09-02)

**노션 글 스무 편을 GitHub 저장소 정리 열아홉 편으로 대체했다**
(`InryeolChoi/Database-System-Concepts`). 같은 책(『Database System Concepts』
10판)을 정리한 것인데 저장소 쪽이 분량이 크고(48만 자) 그림 51장이 함께 온다.
둘 다 남기면 같은 내용이 두 벌로 보여서 노션 쪽을 `DropPosts`에 적었다.

- **순서와 제목은 저장소의 `Syllabus.md`를 따랐다.** 파일 이름은 `chapter4_1`,
  파일 안의 첫 제목은 `4. 중급 SQL (1)`인데 둘 다 읽는 사람을 위한 이름이
  아니다. Syllabus가 사람이 붙인 이름을 이미 들고 있다.
- **표지 목차는 지우고 새로 붙인다.** 옛 목차의 링크 스물은 전부 가리킬 글이
  없어진다. 처음에는 첫 줄 자리에 새 목차를 넣고 나머지를 지웠는데,
  **옛 목차와 새 목차에 글자까지 같은 줄이 있었다**(`# 4. 빅데이터 분석`).
  `removeLine`이 첫 번째 것만 지우므로 방금 넣은 새 목차의 그 줄이 지워져
  화면에서 절이 통째로 사라졌다. 지금은 **지우기만 하고 새 목차는
  `BodyAppends`로 끝에 붙인다** — 그러면 충돌이 없다.
- **레포 자체의 깨진 참조 셋은 그대로 뒀다.** `images10_1.png`(파일은
  `chapter10_1.png`)와 `images/chapter12_*.png`(폴더는 `Images/`)다. GitHub에서도
  깨져 보이는 것이라 우리가 고칠 자리가 아니다 — 리포트가 이름으로 짚어준다.
- 화면에 남은 별표 43개는 **손댈 수 없는 것들이다**: 코드 블록 안 29개(글쓴이가
  코드 줄을 강조하려고 쓴 것이라 글자로 나오는 게 맞다), 짝이 홀수인 것 6개,
  나머지 8개다. 노션 쪽에서 46개를 그대로 둔 것과 같은 판단이다.

<a id="section-13"></a>
### 짝이 안 되는 굵게 (2026-09-02)

**손으로 쓴 마크다운에도 노션과 같은 자리가 있다.** CommonMark는 닫는 기호
바로 앞이 문장부호면 기호 뒤가 공백이거나 문장부호여야 짝으로 인정하는데,
한국어에서 이게 자주 걸린다 — `**경로 표현(Path Expression)**으로`는 닫는
기호 앞이 `)`이고 뒤가 `으`라서 **별표가 그대로 화면에 나온다.**

- 판정 규칙의 정본을 `internal/markdown`으로 옮겼다(`CanPairEmphasis`).
  이건 노션의 사정도 GitHub의 사정도 아니라 **CommonMark의 규칙**이고,
  두 이관 도구가 각자 들고 있으면 언젠가 갈라진다.
- **짝이 안 되는 자리만** `<strong>`으로 낸다. 본문은 사람이 웹에서 고칠
  것이라 되도록 마크다운으로 두는 편이 낫다.
- **코드 펜스와 인라인 코드 안은 건드리지 않는다.** 거기서는 `n**2`가 글자로
  나오는 것이 맞다.

<a id="section-14"></a>
### 겪은 것

- **`cmd/categorize`가 깨졌다.** `SELECT notion_page_id …`를 문자열로 스캔하는데
  GitHub 글은 그 칸이 NULL이다. `WHERE notion_page_id IS NOT NULL`을 붙여 고쳤다 —
  그 도구가 하는 일은 노션 경로에서 분류를 뽑는 것이라 다른 출처에는 할 말이
  없다. **출처가 하나 늘 때 이런 자리가 또 있는지 보라.**
- GitHub 이미지 이관은 구현되어 있다. 새 출처를 추가하면 내부 링크와 이미지 경로도 확인한다.

<a id="section-15"></a>
## 내부 링크

**재작성 결과는 `](/p/{slug})`다.** 서버 라우트가 `GET /p/{slug}` 하나뿐이라
접두사를 반드시 붙여야 한다. 안 붙이면 `GET /{l1}` 카테고리 라우트에 잡혀서
전부 404다. 실제로 옛 relink가 `](/{slug})`로 써서 본문 링크 670개가 전부
404였다(2026-08-18에 고쳤다).

`cmd/relink`가 세 형태를 모두 `](/p/{slug})`로 바꾼다.

| 형태 | 어디서 오나 | 개수 |
|---|---|---|
| `](/p/{페이지ID})` | child_page, child_database, link_to_page 블록 | 729 |
| `](/{32자리 16진수})` | 본문 인라인 링크(rich_text의 href) | 87 |
| `](/{slug})` | 옛 relink가 접두사 없이 써둔 것 | 670 |

두 번째 형태는 `/p/` 접두사가 없고 **하이픈도 없다**. `#조각`이 붙어 있으면
페이지 안의 특정 블록을 가리키며, 재작성할 때 조각은 그대로 둔다.
`importer.SlugIndex`가 두 형태의 키를 모두 만들어준다.

```sh
go run ./cmd/relink -db blog.db          # 미리보기 (기본)
go run ./cmd/relink -db blog.db -apply   # 실제로 고침
```

- 대응하는 글이 없는 링크는 **바꾸지 않고 노션 형태로 남긴다.** 경로만 slug 모양으로
  바꾸면 깨진 링크가 멀쩡해 보인다. 현재 146개(`/p/` 119 + 인라인 27)가 여기 해당한다.
  **이건 눌러도 404가 맞다.** 대부분 인라인 데이터베이스(`object: database`)라
  글이 될 수 없는 것이다. 예: `가상화기술`의 `Docker : 기초 이론`.
- **`/p/`가 노션 형태와 최종 형태를 겸한다.** 그래서 "접두사가 `/p/`면 노션"이 아니라
  **"경로가 실제 `posts.slug`가 아니면 노션"**으로 판별한다. relink는 글 전체의 slug
  집합을 들고 다니며 이걸 가린다. 이게 없으면 이미 바꾼 링크를 또 바꿨다고 세서
  멱등성 검사가 거짓으로 실패한다. slug가 페이지 ID와 같은 지금은 특히 그렇다.
- **`import -db`를 다시 돌리면 본문을 덮어써서 이 재작성이 사라진다.** import가
  경고를 찍는다. 그 뒤에는 relink를 다시 돌려야 한다.
- **slug를 바꾸면 링크도 같이 바꾼다.** Admin 저장은 같은 트랜잭션에서 링크를 갱신한다.
  이관 재작성과 웹 저장의 계약은 architecture.md의 저장 절을 함께 확인한다.
- `-apply`가 끝나면 검증이 세 가지를 확인한다: 설명되지 않는 노션 형태 링크 0개,
  **접두사 없이 글을 가리키는 링크 0개**, 다시 돌려도 안 바뀜.

<a id="section-16"></a>
## 노션 이관

- 변환기는 미지원 블록을 조용히 버리지 않는다. 렌더러가 없는 타입은 **warn**,
  의도적으로 다르게 옮기는 것(단 레이아웃 평탄화, 목차 제거 등)은 **note**로 남긴다.
  새 블록 타입을 지원할 때 이 원칙을 깨지 마라.
- 검증은 결과 문자열을 다시 세어서 한다(렌더링 중에 센 값을 믿지 않는다).
  조립 단계에서 내용이 사라져도 잡히게 하려는 것이다.
- **노션은 목록 번호를 저장하지 않는다.** 렌더링할 때 매긴다. 그래서 중간에 다른
  블록이 끼면 이어지는 목록인지 새 목록인지 데이터만으로는 알 수 없고, **무엇이
  끼었는지**로 판단한다 (`softInterruptTypes`):
  - 코드/그림/수식/표 등과 빈 문단이 끼면 → **번호를 이어간다.** 항목에 딸린
    예시나 그림일 뿐이다. (노션 원본에서 이렇게 보이는 것을 확인했다)
  - 제목이나 내용이 있는 문단이 끼면 → **1부터 다시.** 문단은 대개 "알고리즘은
    다음과 같이 작동한다" 같은 새 목록의 도입문이고, 제목은 아예 새 절이다.
  - 덤프 전체 506건의 끊김 중 94건이 이어가는 쪽, 412건이 재시작하는 쪽이다.
- **목차(`table_of_contents`)는 버린다.** 렌더링할 때 제목에서 다시 만든다.
- **토글(`<details>`)에 관해 두 가지를 변환기가 처리한다** (2026-08-21에 고쳤다):
  - **펼쳐도 아무것도 안 나오는 토글은 내보내지 않는다** (35개 → 0). 화면에 보이는
    모습은 하나지만 원인은 셋이라 리포트에는 종류를 나눠 남긴다:
    목차만 들어서 25개(`dropped-toc-toggle`), 노션에서 원래부터 비어 있어서 8개
    (`dropped-empty-toggle`), 자식은 있었는데 그 내용이 비어서 2개.
  - **마지막 2개는 껍데기만 벗기고 summary를 문단으로 남긴다**
    (`toggle-to-paragraph`). 자식조차 없던 토글과 자식을 넣어둔 토글은 구조가
    다르고, 그 차이가 곧 "라벨이냐 문장이냐"와 겹친다. 자식이 없던 8개의 summary는
    `p.123`·`코드`·`3차 적률` 같은 라벨이지만, 자식을 넣어둔 2개는 문장이었다
    (`없으면 스프링부트 플러그인에 들어가 깔아야 한다.`,
    `이를 시행한 뒤 train_dataset[0]을 시행하면 다음과 같음`). 사람이 거기 뭔가를
    쓰려고 자리를 잡아둔 것이라 글자를 버리지 않는다. 문단이 되므로 summary와 달리
    **마크다운으로** 낸다 — 거긴 goldmark의 인라인 파싱이 닿는 자리다.
  - 토글을 뺄 때는 summary 글자를 리포트 메시지에 같이 찍는다. 무엇이 사라졌는지
    눈으로 볼 수 있어야 한다.
  - **`<summary>` 안은 마크다운이 아니라 HTML로 낸다** (`renderRichTextHTML`).
    CommonMark는 raw HTML 블록 안을 인라인 파싱하지 않아서 `**목차**`의 별표가
    글자로 보였다(75개). 굵게는 `<strong>`, 코드는 `<code>`로 내고 글자는
    HTML 이스케이프한다 — 결과가 raw HTML 자리에 그대로 들어가기 때문이다.
  - **내용이 빈 코드 블록이 든 토글은 남는다.** 그건 노션 원본의 코드 블록이 비어
    있는 것이라 `<pre>`가 비어 보이는 게 맞다. 현재 1건(`10. 무중단 배포`).
  - 이 변경에는 **1408건 재변환 + `relink -apply` 재실행**이 따라왔다.
- **문단의 자식은 들여쓰지 않는다.** 마크다운에는 "문단의 자식"이라는 구조가 없어서
  들여써도 뜻이 없고, 대신 위험하다: **CommonMark에서 4칸 들여쓰기는 코드 블록이다.**
  문단 안에 문단이 겹치면 2칸씩 쌓여 4칸을 넘고, 그 아래 목록이 통째로 회색 상자가
  되면서 안의 `$수식$`이 코드 안이라 글자로 굳는다. `1. 확률`이 그랬다.
  - 제목(`heading_*`)은 원래부터 안 들여썼다. 목록 항목만 표시 너비만큼 들여쓴다 —
    거기서는 들여쓰기가 실제로 중첩을 뜻한다.
  - **goldmark에서 들여쓰기 코드 블록 파서를 빼는 길은 안 된다.** goldmark는 4칸
    이상 들여쓴 줄을 그 파서에만 넘기므로, 빼면 그 줄이 어느 파서에도 안 걸려
    **내용이 통째로 사라진다.** 실제로 해보고 되돌렸다.
  - 고치기 전 덤프 전체에 이렇게 생긴 블록이 5개였고 **다섯 다 코드가 아니었다**
    (LaTeX 2, 산문 1, 목록 2). 고친 뒤 0개다. 본문이 바뀐 글은 27편.
- **렌더링된 글 전체에서 "눈에 보이는 고장"을 종류별로 센다** (2026-08-21).
  표본 하나를 손보는 대신, 징후별로 전수를 세고 그 원인을 고치는 방식이다.
  1390편을 훑어 나온 것과 처리:

  | 징후 | 전 | 후 | 판정 |
  |---|---:|---:|---|
  | 빈 표 칸 | 303 | 76 | 227개는 **머리 없는 표에 넣은 빈 머리**였다. 나머지 76은 원본에 실제로 빈 칸 |
  | 빈 목록 항목 | 53 | 0 | 노션에서 만들다 만 빈 줄. 자식이 있는 것은 없어서 그냥 뺐다 |
  | 노션으로 나가는 링크 | 3 | 0 | relink가 `https://app.notion.com/p/...` 형태를 아예 안 잡고 있었다 |
  | 굵게 기호 노출 | 46 | 46 | **원문에 사람이 직접 친 것.** `int(n**(0.5))`가 섞여 있어 손대지 않는다 |
  | alt 없는 이미지 | 469 | 469 | 변환기는 이미 캡션을 alt로 쓴다. **원본에 캡션이 500개 중 7개뿐**이라 쓸 글자가 없다 |
  | 취소선 기호 노출 | 4 | 4 | 대부분 LaTeX의 `~~`(공백)이고, 나머지는 원문 그대로다 |
  | 만료된 노션 첨부 링크 | 8 | 8 | 이 문서의 "남은 작업" 참고. 덤프에 파일이 없다 |

  - **`~~`를 세려면 수식과 코드를 먼저 빼야 한다.** LaTeX에서 `~`는 공백이라
    수식 안에 `~~`가 흔하다. 안 빼면 취소선 오탐이 백 건 넘게 나온다.
- **변환에서 글자가 새는지 전수로 본다** (2026-08-21에 했다). 블록 타입별 렌더러를
  믿지 않고 **결과 문자열을 다시 세는** 방식이다 — 변환기 자신의 검증과 같은 원칙이라
  조립 단계에서 사라져도 잡힌다. 덤프 1408개의 모든 `rich_text`/`caption`/표 칸/제목을
  모아 변환 결과에 남았는지 확인했다.
  - **글자 조각 40,459개 중 못 찾은 것 32개, 전부 의도한 것이다.** 일부러 뺀 토글
    summary 31개와 `curation.BodyEdits`로 지운 `프로젝트` 링크 1개. **조용히 새는
    곳은 없다.**
  - 비교할 때 **결과 쪽의 줄머리 `>`(인용)와 들여쓰기는 떼고 본다.** 원문 한 덩어리가
    여러 줄로 나가면 그 표시가 사이에 끼어서, 안 떼면 멀쩡한 글자를 "사라졌다"고 센다.
    처음에 99개가 나왔는데 그중 67개가 이 오탐이었다.
  - **목록 표시(`-`, `1.`)까지 떼면 안 된다.** 원문에 있던 "1. "까지 지워져서 이번엔
    반대 방향으로 못 맞춘다. 실제로 그렇게 17개를 잘못 셌다.
- `embed`/`bookmark`/`link_preview`는 링크로 바꾼다(각 1/24/12건). 링크가 죽어
  보이는 건 대개 원본이 이미 죽은 것이다. apption.co 임베드 1건이 그렇다.
- 이미지 블록 500개 중 **24개는 원본 URL이 비어 있다**(노션 쪽에서 이미 깨진 것).
  주석만 남긴다. 별도로 10개는 다운로드가 실패해 외부 URL을 그대로 쓴다.
- **수식은 마크다운의 빈 줄과 충돌한다.** 노션 수식에는 개행과 빈 줄이 들어 있는데,
  마크다운에서 빈 줄은 문단을 끊는다. 그대로 두면 여는 `$`와 닫는 `$`가 다른 문단으로
  갈라져서 수식이 렌더링되지 않고 `$`가 글자로 보인다. 그래서:
  - 인라인 수식은 공백을 정리해 **한 줄로 편다** (`normalizeInlineMath`)
  - 블록 수식은 여러 줄 배치를 살리되 **빈 줄만 지운다** (`normalizeBlockMath`)
  - LaTeX는 수식 모드에서 공백 길이를 구분하지 않고 진짜 줄바꿈은 `\\`로 쓰므로
    의미는 그대로다. 이스케이프는 절대 넣지 않는다 — `\`, `{`, `}`, `_`, `|`에
    백슬래시를 덧붙이면 LaTeX가 깨진다.
- **서식 기호는 CommonMark가 짝을 지을 수 있게 낸다.** 노션의 굵게/기울임을
  `**...**`로 옮길 때 두 가지가 걸린다. 덤프 전체에서 이 때문에 별표가 글자로
  보이던 자리가 **186개(글 38편)**였고 지금은 0개다.
  - **기호가 공백을 감싸면 안 된다.** 노션은 굵게 범위에 뒤따르는 공백까지 넣는
    일이 잦은데(`"시그마 대수, "`), 그대로 쓰면 닫는 기호 앞이 공백이라 짝이 안
    된다. 공백을 기호 밖으로 뺀다(237조각). **줄바꿈 없는 공백(U+00A0)까지 봐야
    한다** — 노션 본문에 흔하고 CommonMark도 공백으로 친다.
  - **알맹이가 문장부호로 끝나고 뒤에 조사가 붙으면 짝이 안 된다.**
    `**릴레이션(relation)**이라고`가 그렇다. 닫는 기호 앞이 `)`이고 뒤가 한글이면
    CommonMark는 닫는 기호로 보지 않는다. 한국어에서 특히 자주 걸린다.
    **그런 자리만 `<strong>`/`<em>`/`<del>` HTML로 낸다** — 본문은 사람이 웹에서
    고칠 것이라 되도록 마크다운으로 두는 편이 낫다.
  - **원문에 사람이 직접 친 `**`는 건드리지 않는다.** 33조각(글 20편)이 그렇다.
    붙여넣기로 들어온 마크다운이라 굵게로 바꾸고 싶어 보이지만, 그중에는
    `int(n**(0.5))`(파이썬 거듭제곱)처럼 바꾸면 망가지는 것이 섞여 있다.
    현재 화면에 남은 별표 46개(글 14편)가 전부 이것이다.
- **수식 안의 한글은 `\text{}`로 감싼다** (`internal/notion/mathtext.go`). KaTeX는
  수식 모드의 글자를 수학 글꼴로 그리는데, 라틴 문자는 이탤릭 변수로 보이면 그만이지만
  **한글은 자모가 겹쳐 뭉개진다.** `"조건부확률" = \dfrac{"결합확률"}{"주변확률"}`이
  읽을 수 없게 나왔다. 대상은 24개(글 11편)뿐이고 전부 설명하려고 한글을 그냥 쓴
  자리다 — 첨자(`X_{선수}`), 행렬 칸, 분수 같은 것들이다.
  - **한글 덩어리 사이의 공백은 함께 감싼다.** 수식 모드에서 공백은 무시되므로
    `행의 갯수`를 따로 감싸면 `행의갯수`가 된다.
  - **이미 `\text{...}` 안에 있는 한글은 건드리지 않는다.** 두 번 감싸면 중괄호만
    늘고, 원문이 옳게 쓴 자리를 다시 쓰는 셈이다.
- 본문에 **진짜 `$` 문자**를 쓴 페이지가 90개 있다(R의 `data1$col`, Makefile 변수,
  정규식 등). 그중 20개는 수식도 같이 있어서, 렌더러가 본문 `$`와 수식 `$`의 짝을
  잘못 지을 수 있다. 렌더러를 고를 때 확인할 것.
- `file`/`video` 블록의 노션 호스팅 URL은 서명이 붙은 임시 주소라 만료된다.
  덤프 스크립트는 이미지만 받아뒀다. 첨부파일이 필요하면 따로 받아와야 한다.

## 나중에 접근 권한이 열린 페이지 받기

integration에 페이지를 새로 연결하면 그 트리가 통째로 새로 보인다. 2026-08-16에
`웹 프로그래밍`(77) + `리눅스 & 쉘`(20) = **97개**가 이렇게 들어왔다.

```sh
# 1) 받을 page id 목록을 만든다 (search 결과에서 기존 덤프에 없는 것만)
# 2) 목록만 덤프한다. 기존 파일은 existsSync 검사가 건너뛴다.
node --env-file=.env scripts/notion-block-dump.mjs --pages-file <목록파일>
# 3) audit 인벤토리에 새 객체를 덧붙이고 status CSV를 다시 만든다
node --env-file=.env scripts/notion-page-status.mjs
# 4) 신규만 변환·이관한 뒤 나머지는 전부 다시 돌린다 (전부 멱등)
go run ./cmd/import -pages "<쉼표구분 id>" -db blog.db
go run ./cmd/relink -db blog.db -apply
go run ./cmd/categorize -db blog.db -apply
go run ./cmd/sortorder -db blog.db -apply
```

- `--pages-file`은 `notion-block-dump.mjs`에 나중에 붙인 옵션이다. 없으면
  `notion-audit-raw.json`(옛 목록)을 쓰므로 새 페이지를 못 받는다.
- **`notion-page-status.mjs`는 `notion-audit-raw.json`에 의존한다.** 새 페이지가
  거기 없으면 제목이 `(제목 없음)`, 경로가 자기 제목만으로 나온다. 새 객체를
  먼저 덧붙여야 한다.
- 전체 audit 재실행은 모든 페이지의 블록을 다시 읽어서 비싸다. `search`로 새
  객체만 추가하면 몇 초면 된다.

- 콘텐츠를 추가 수집해 공개하기 전 자격증명이 섞이지 않았는지 다시 확인한다.

3. 홈 본문의 블록 편집 적용 여부. 현재 홈은 원문/미리보기 방식이고 글 편집기는 slug에 결합되어 있다.
4. `데이터베이스` 표지 글(id 1236)의 category_id가 NULL이라는 2026-09-09 기록 재확인.
   과거 "NULL 0건" 통계로 덮지 않는다.
5. parent_id의 추가 확장 여부. 분류별 출처와 화면 개선을 확인한다. 표지의 인라인 DB 목록이
   이미 묶어 보여주는 경우는 parent_id를 늘릴 필요가 없을 수 있다.
6. published 선별과 draft 정리. draft 일괄 삭제는 보류했던 결정이다. 본문·들어오는 링크를 보고 분류별로 판단한다.
7. 이름 없는 인라인 DB(Untitled/New database)의 연결 복원. 원본 재조회가 필요할 수 있다.
8. 만료 가능한 노션 file/video 첨부 복구. 기존 덤프는 이미지만 내려받았으므로 파일 존재부터 확인한다.
9. 근거가 없는 수동 순서 지정, 갈래 카드 확장 여부. 현재 수동 순서 패널·최근순 규칙을 먼저 확인한다.
10. 외부 링크 카드의 파비콘 이관. 이관 때 받아 DB BLOB으로 저장하며 호스트별로 연결하고 sha256으로 중복 제거한다.
    독자가 글을 열 때 외부 파비콘 서비스에 요청하는 방식은 쓰지 않는다. 그때까지 기본 아이콘을 유지한다.

### 운영과 접근 제어

- 기계 밖 자동 백업, www DNS·리다이렉트, IAP 외 SSH 허용 범위, 배포 인증의 WIF 전환 여부.
  배포 README의 미완료 목록과 함께 갱신한다.
- 속도 제한은 구현되어 있다. 추가 프록시·인프라 방어가 필요한지 별도 판단한다.
- `/img/{sha256}`는 사용하는 글의 권한을 확인하지 않는다. draft/private 이미지도 해시를 알면 받을 수 있다.
  강화하려면 이미지 참조와 접근 권한을 설계해야 한다.
- 글 삭제 후 아무도 쓰지 않는 이미지의 정리 기능. 현재 글 삭제가 이미지를 함께 지우지 않는다.
- CDN 자산의 로컬 포함 여부. 현재는 필요한 페이지에서만 CDN을 사용하고 실패 시 원문을 보여준다.

<a id="section-22"></a>
### AI 삽입과 MCP

화면·인증·저장·삭제·팔레트·이름 붙인 애니메이션은 구현되어 있다.

**글감함(2026-09-19)은 구현되어 있다.** 프로젝트를 하며 남긴 메모를 `notes`
테이블에 쌓아두고(`migrations/009_notes.sql`), admin의 `/admin/notes`
화면에서 "초안 생성"을 누르면 OpenRouter(`internal/admin/openrouter.go`,
기본 모델 `anthropic/claude-sonnet-5`)가 정리해 **항상 draft** 글 하나를
만든다(`internal/admin/notes.go`의 `generateNoteDraft` → 기존 `savePost` 재사용).
공개는 사람이 admin에서 status를 바꿔야 일어난다.
생성 요청은 최대 5분 기다리고, 이 요청의 서버 응답 기한은 5분 15초다.
시간이 지나면 504와 재시도 안내를 돌려준다. 브라우저 연결이 끊기면
OpenRouter 호출도 취소한다.
기존 글의 AI 수정도 같은 모델과 5분 제한을 사용한다. 수정 요청·본문을
OpenRouter에 보내지만 제안만 돌려주며, 실제 저장은 admin 편집기에서 한다.

**키는 `OPENROUTER_API_KEY`다.** 값은 GitHub Actions의 같은 이름 secret에 있고,
배포가 `/etc/blog/openrouter.env`와 `blog.service.d/openrouter.conf` 드롭인을
만들어 넣는다(`.github/workflows/deploy.yml`). 사람이 손으로 적는
`/etc/blog/admin.env`와 **일부러 갈라 둔 파일**이다 — 배포가 매번 건드리는
파일에 GitHub client secret이 같이 있으면 CI 사고 하나가 로그인까지 망가뜨린다.
키가 비어 있어도 서버는 뜨고 그 버튼만 503으로 실패한다.
**키 값은 어떤 API 응답에도 실리지 않는다**(`internal/admin/ai.go`는 있는지
여부만 boolean으로 내려준다).

쓸 모델과 지시문은 secret이 아니라서 **admin 환경설정 화면에서 고친다**
(`settings` 표의 `ai.model`·`ai.prompt`, `internal/admin/ai.go`). 저장된 값이
없으면 서버 환경변수 `OPENROUTER_MODEL`, 그것도 없으면 코드 기본값 순으로
고른다. 같은 화면에서 OpenRouter의 `/api/v1/credits`로 잔액을,
`/api/v1/models`로 고를 수 있는 모델 목록을 본다 — **둘 다 설정 조회와 갈라 둔
요청이라**, OpenRouter가 죽어도 설정 화면과 초안 생성은 그대로 동작한다.

남은 것:

- 본문 렌더러는 html.WithUnsafe()를 사용한다. AI 본문을 임의 스크립트로 실행시키지 않는다.
  애니메이션은 등록된 이름과 사람이 작성한 static 컴포넌트로 제공한다.
- MCP 클라이언트는 브라우저 세션 쿠키와 다른 토큰 인증을 설계한다.
  Origin 없는 요청을 허용하려고 기존 브라우저 CSRF 검사를 느슨하게 풀지 않는다.
- HTTPS·백업·DB 정본 방향·업로드 타임아웃·CSRF는 기존 선행 작업이다. 다시 미구현으로 취급하지 않는다.

<a id="section-23"></a>
### 번역 결정

현재 공통 UI는 고정 사전, 본문은 브라우저 Translator 기능에 의존한다.
지원 여부는 실행 환경에서 확인한다. 여러 브라우저에서 일관된 본문 번역을 제공하려면
서버에 번역본을 보관하는 설계가 필요하며 다음 선호를 보존한다.

- **DB 번역본(권장):** `post_translations`에 언어별 제목·본문을 저장하고 원문
  `updated_at`이 바뀌면 번역을 낡은 것으로 표시한다. 읽을 때 외부 요청이 없고
  “DB가 정본” 원칙과 맞지만, 번역본을 만드는 작업/관리 화면이 필요하다.
- **클라우드 번역 + DB 캐시:** Google Cloud Translation·DeepL 같은 서비스를
  서버가 호출하고 결과를 DB에 보관한다. 바로 자동화할 수 있지만 API 키·비용과
  본문을 외부에 보내는 결정을 먼저 해야 한다. **키나 동의 없이 임의의 무료 번역
  엔드포인트로 본문을 보내지 않는다.**
- **번역 품질은 일반 직역이 아니다.** 작성자는 데이터 분석을 거쳐 데이터 관리·처리,
  백엔드 프로그래밍·데이터베이스·클라우드에 관심을 넓힌 성인 개발자다. 영어는
  자연스럽고 절제된 비즈니스 영어, 스페인어는 특정 국가의 과한 구어체를 피한
  자연스러운 국제 비즈니스 스페인어로 쓴다. 학생·취업 준비생처럼 낮춰 말하거나
  원문의 한국어 어순을 옮기지 않는다. 코드·수식·URL·마크다운 구조는 그대로 둔다.
  이 목소리는 번역 프롬프트 버전과 함께 저장해야 재생성해도 일관된다. 일반 기계번역
  API보다 문체 지시를 받는 LLM + DB 캐시가 이 요구에는 더 맞다.
- **Mac의 Ollama가 번역 작업을 가져가는 구조는 채택하지 않는다.** 개인 컴퓨터가
  켜져 있어야 클라우드의 새 글 번역이 끝나는 운영 방식은 원하지 않는다. GCP 배포
  뒤에는 글 저장이 `translation_jobs`를 pending으로 만들고, 별도 일회성 작업이
  Vertex AI 같은 사용량 기반 LLM을 호출해 `post_translations`에 넣는 쪽이 현재
  선호다. 웹 서버에 모델을 상주시켜 요청마다 번역하지 않는다. 원문 hash가 바뀐
  글만 다시 번역하고 읽을 때는 DB 번역본만 SSR한다. 초기 아카이브 일괄 번역과 이후
  새 글 번역은 같은 작업을 쓰되 비용을 따로 판단한다.
