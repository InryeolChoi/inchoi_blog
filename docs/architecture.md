이 문서는 구조·화면·렌더링·편집의 동작과 설계 이유를 다룬다.

## 구조

```
cmd/blog/       서버. 시작할 때 마이그레이션을 적용하고 HTTP를 연다.
internal/web/   읽기 전용 공개 페이지 (라우팅, 템플릿)
internal/admin/ 글쓰기 화면 (CSR) + GitHub 로그인. **-admin을 줘야 뜬다**
internal/markdown/ 본문 마크다운 → HTML (goldmark + 수식 확장)
cmd/import/     노션 이관 CLI. 기본은 검토 파일 출력, -db를 주면 DB에도 이관한다.
internal/db/    연결(Open)과 마이그레이션 러너(Migrate)
internal/notion/ 덤프 파싱과 마크다운 변환기
internal/importer/ 변환 결과를 DB에 넣기 (posts/images upsert)
cmd/postparent/  글끼리의 부모-자식(parent_id) 복원. 카테고리 하나씩
cmd/importgh/    GitHub 저장소의 마크다운 노트를 DB로 (operations.md의 "GitHub 이관")
internal/curation/ 사람이 정한 예외. 분류는 categorize·regroup이, 본문에서
                   덜어낼 줄(BodyEdits)은 import가 본다
migrations/     번호순 SQL. 001_init.sql 형식.
out/            (gitignore) 변환 결과 검토용
embed.go        루트 패키지. migrations/를 embed해서 MigrationsFS()로 노출.
deploy/         GCP 배포물. systemd 유닛과 인스턴스 준비 스크립트, 절차 문서
.github/workflows/deploy.yml  main push → 빌드 → 인스턴스에 바이너리 전송
scripts/        노션 이관용 일회용 Node 스크립트 (런타임과 무관)
  notion-workspace-audit.mjs   워크스페이스 구조 조사 → notion-audit-raw.json
  notion-block-dump.mjs        페이지 블록 원본 덤프 → dump/
  notion-page-status.mjs       덤프 분석해서 초기 status 결정 → notion-page-status.csv
  dump/                        (gitignore) 페이지 JSON 1408개 + images/ 446개
.env                           (gitignore) NOTION_TOKEN
```

`embed.go`가 루트에 있는 이유: `//go:embed`는 상위 디렉토리를 못 가리킨다
(`../migrations` 불가). `migrations/`를 루트에 두려면 embed 선언도 루트여야 한다.

```sh
go test ./...                                  # 전체 테스트
go run ./cmd/blog -db <일관된-DB-사본> -addr 127.0.0.1:8080  # 로컬 서버
CGO_ENABLED=0 go build -o blog ./cmd/blog      # 단일 바이너리

go run ./cmd/import -pages <id>,<id> -v        # 특정 페이지만 변환 (리포트 전체 출력)
go run ./cmd/import -limit 20                  # 앞 20개만 변환
go run ./cmd/import                            # 전체 1408개, out/에만 (DB는 안 건드림)
go run ./cmd/import -db blog.db                # 변환 + DB 이관 (몇 번 돌려도 안전)
```

## 형제 순서 (sort_order)

`cmd/sortorder`가 채운다. **출처에 따라 신뢰도가 다르다.**

| 출처 | 건수 | 신뢰도 |
|---|---:|---|
| `child_page` 배열 위치 | 596 | 정확. 노션 API가 블록을 화면 순서대로 준다 |
| `created_time` 순위 | 708 | 차선. 쌍 기준 85.8%만 정해짐 |
| 근거 없음 → 0 | 104 | 전부 같은 분에 생성된 85건 + 최상위 19건 |

- **노션 API는 데이터베이스 행의 화면 순서를 노출하지 않는다.** 뷰의 수동 정렬은
  API에 없고, `sorts`로는 속성·타임스탬프 정렬만 지정할 수 있다. 실제로 3개 DB를
  쿼리해 확인했다 — 반환 순서가 화면 순서가 아니었다. **재수집해도 안 나온다.**
- **`created_time`은 분 단위다** (초가 항상 `00`). 한 번에 만든 페이지들이 같은 값을
  가진다. 그런 건 `DenseRank`가 **같은 순위**를 줘서 "순서 미정"으로 남긴다.
  억지로 다른 값을 주면 없는 순서를 지어내는 것이다.
- 검증해보니 **시각이 다르면 98.3%가 논리적 순서와 일치**한다(제목에 번호가 있는
  DB 18개, 347쌍 중 341쌍). 틀리는 게 아니라 자주 침묵하는 신호다.

**사람이 정한 순서는 예외다** (2026-09-01, `migrations/005`). 아래 규칙은
"이 sort_order가 `created_time`에서 나왔다"는 불신에서 온 것이지 "sort_order라서"가
아니다. `curation.PostMetadataEdits`로 사람이 적어둔 순서는 `posts.sort_order_manual`에
표시가 남고, 화면은 **그 글들을 맨 앞에 제 순서대로** 놓는다.

- **왜 컬럼인가.** 웹이 `internal/curation`을 직접 읽게 하면 같은 DB를 다른
  바이너리로 서빙할 때 순서가 달라진다 — DB가 정본이라는 전제가 거기서 깨진다.
  순서를 누가 정했나는 데이터의 성질이라 데이터가 들고 있어야 한다.
- **섞인 목록에서는 앞뒤로 가른다.** "전부 sort_order"로 돌아서면 나머지가 못
  믿을 `created_time` 순서로 되돌아가고, 무시하면 사람이 정한 것이 사라진다.
- 실제로 `다변량분석 : 코드` 12편이 이 때문에 어긋났다. 표에 0~11을 적고
  `sortorder -apply`까지 했는데 화면은 가나다순이었다 — 제목에 앞 번호가 없어서
  아래 자연 정렬이 다시 세웠기 때문이다.
- **`cmd/sortorder`의 수동 묶음 이름은 표에서 가져온다**(`PostMetadataEdit.Group`).
  예전에는 `"manual:linear-algebra"`가 박혀 있었는데, 수동 묶음이 둘이 되면서
  두 묶음의 `sort_order` 0이 한 묶음 안에서 겹치는 것으로 보였다.
- **편집기에서 목록을 보고 옮긴다** (2026-09-08). 예전에는 `cmd/sortorder`와
  `cmd/importgh`만 이 칸을 썼고, 편집기의 `형제 순서`는 `sort_order`만 적었다 —
  **저장은 되는데 화면은 그대로인, 안 듣는 칸이었다.** 이제 그 자리에 이 글이
  화면에서 서 있는 목록이 그대로 뜨고, ↑↓로 옮긴 뒤 저장하면 그대로 선다.
  아래 "형제 순서 패널" 절 참고.
  - **저장할 때마다 켜면 안 된다.** 편집기는 이 칸을 언제나 함께 보내므로,
    오타 하나 고쳐 저장한 글이 전부 목록 맨 앞으로 튀어나온다. 사람이 그
    자리에서 실제로 켠 요청만 켠다 — 그래서 요청에 **불리언 칸을 따로 뒀다.**
    `sortOrder > 0`으로 짐작하는 길도 있었는데, 0은 "첫째"라는 멀쩡한 값이다.
  - **끄는 것도 사람이 한다.** 켜는 쪽만 있으면 한 번 켠 글을 되돌릴 길이
    DB를 직접 여는 것뿐이 된다.
  - **숫자와 체크를 한 줄에 붙여 둔다.** 떼어 놓으면 숫자만 고치고 왜 화면이
    안 바뀌는지 모르게 된다 — 그게 이 기능이 없던 동안의 상태였다.
  - **`curation.PostMetadataEdits`와 부딪힐 수 있다.** 노션에서 온 글이면
    다음 `import -db`가 표의 값으로 되돌린다. 편집 화면의 경고 띠가 이미
    그것을 말한다(`Managed`).

### 형제 순서 패널 (2026-09-08)

편집기의 `형제 순서` 자리에 **이 글이 화면에서 서 있는 목록이 그대로** 뜬다.
↑↓로 옮기고 저장하면 그 차례로 선다(`internal/web/siblings.go` +
`internal/admin/siblings.go`). 숫자를 손으로 적는 칸은 목록을 못 만들 때만 나온다.

- **목록을 admin이 제 눈으로 세지 않는다.** 화면에 서는 순서를 아는 것은 공개
  쪽이라 `web.SiblingOrder`를 부른다 — 미리보기가 렌더러·CSS·CDN 태그를 공개
  쪽에서 그대로 가져다 쓰는 것과 같은 규칙이다. **화면과 다른 트리를 끌어
  놓게 하면 옮긴 대로 안 서고, 그러면 안 하느니만 못하다.**
- **"형제"는 `parent_id`가 같은 글이 아니다.** 화면의 층은 세 군데서 온다:
  `parent_id`(5개 분류 172건), `original_path`로 다시 묶은 것(pathtree.go),
  표지 본문이 펼친 상자. 부모로만 모으면 `프로그래밍 언어`가 **화면엔 상자
  열 개인데 패널엔 191편이 한 줄**로 쏟아진다.
- **목록 전원에게 쓴다**(`sort_order = i`, `sort_order_manual = 1`). 한 편만
  켜면 그 한 편이 맨 위로 갈 뿐 나머지는 제목으로 다시 세워진다 — 목록이
  통째로 사람 것이어야 적어둔 차례가 곧 화면의 차례가 된다.
- **저장과 같은 트랜잭션이고 글 저장보다 뒤에 돈다.** 절반만 바뀐 결과를
  남기지 않고, 패널을 썼으면 거기서 정한 순서가 숫자 칸을 이긴다.
- **표지가 안내하는 글도 정할 수 있다.** 그 글은 카테고리 목록에서 빠지지만
  (`dropShownPostTrees`), 표지 본문이 펼친 상자 안의 차례도 결국 같은
  `sortPosts`가 정한다 — `InlineDBGroups`가 마지막에 그것을 부른다. 그래서
  `bodyFix.Lists`에 펼친 상자의 행을 담아 두고 패널이 그것을 본다.
  **여기서 물러나면 공개 946편 중 573편에 이 기능이 안 닿는다.**
- **못 정하는 자리는 error가 아니라 `Reason`이다.** 화면이 못 그리는 것이지
  고장이 아니라, 그 말을 그대로 적고 숫자 칸으로 돌아간다. 공개 946편 기준:
  정할 수 있는 글 482, 표지 본문이 낱개 링크로 안내 269, 갈래 카드만 있는
  분류 138, 표지 글 자신 52, 사람이 정한 묶음 4, 분류 없음 1.
- **draft는 목록에 안 선다 → 정할 순서도 없다.** 로그인해서 고치는 중이어도
  마찬가지다 — draft를 숨기는 것은 로그인 여부가 아니라 status가 정하는 일이라
  (`-drafts`도 이 규칙을 안 바꾼다), 여기서 예외를 두면 화면과 다른 목록이 나온다.
- **이름표가 섞인 층은 거절한다.** `pathtree`의 이름표는 posts에 행이 없어서
  순서를 적을 자리가 없는데, `sortNodes`가 사람이 정한 순서를 맨 앞에 놓으므로
  글만 옮기면 **이름표가 통째로 아래로 밀린다** — 사람이 옮긴 적 없는 것이 움직인다.
- **지금 고치는 글이 목록에 없으면 400이다.** 그건 남의 목록을 재배열하는
  요청이고, 이 패널이 하는 일이 아니다.
- **slug를 바꾸면서 순서도 옮기면 옛 이름을 새 이름으로 갈아끼운다.** 패널이
  들고 있는 것은 열었을 때의 slug라, 안 바꾸면 방금 이름을 바꿨다는 이유로
  저장 전체가 "그런 글이 없다"로 실패한다.
- **노션에서 온 글이면 다음 `import -db`가 `PostMetadataEdits`의 값으로
  되돌린다.** 편집 화면의 경고 띠(`Managed`)가 이미 말하는 그것이다.
- **`hidden`은 `display`를 준 요소에 안 먹는다.** 기본 시트의
  `[hidden] { display: none }`과 특정성이 같아 나중에 선언된 `display: flex`가
  이긴다 — 목록이 있을 때 감춘 줄 알았던 숫자 칸이 그대로 보였다.
  `label[hidden] { display: none }`을 따로 적는다.
- 돌연변이 일곱(화면 순서 대신 DB 순서 / draft도 허용 / 표지가 펼친 글을 목록에
  그대로 둠 / 지금 글이 없어도 통과 / 첫 글에만 순서를 씀 / 옛 slug를 안 갈아끼움 /
  manual 표시를 안 켬)을 넣어 테스트가 실제로 실패하는 것을 확인했다.
  브라우저로도 몰아봤다 — ↑↓로 옮겨 저장하니 공개 화면의 상자 차례가 그대로 바뀌었고,
  390px에서 문서폭이 넘지 않는다(900px 조각으로 검사기가 진짜 잡는지 먼저 확인했다).

### 최근 글이 앞에 서는 분류 (2026-09-08)

**`라이프`는 최근에 쓴 글이 맨 앞이다** (`internal/web/recentfirst.go`).

- **기본 순서는 읽는 차례다.** 제목 앞 번호를 따르고 그 뒤는 자연 정렬이라
  1강부터 11강까지가 순서대로 선다 — 배운 것을 정리한 글에는 그게 맞다.
  그런데 일지처럼 쌓이는 글은 **읽는 차례가 곧 쓴 차례의 역순**이라, 새 글이
  아래로 밀리면 매번 끝까지 내려가야 그것을 본다.
- **`sort_order`로는 안 된다.** 사람이 정한 순서로도 같은 배열을 만들 수
  있지만 그건 **한 번 정한 차례**라 글을 쓸 때마다 다시 정해야 한다.
  "항상 최근 글이 앞"은 그런 뜻이 아니다 — 규칙이라 코드가 든다.
- **화면 장치라 웹 코드에 둔다.** 갈래 카드·바깥 링크·`deferredSections`와
  같은 이유다. 본문(DB)에 적으면 `import -db`가 덮고, `curation`에 적으면
  웹이 그 패키지를 읽게 되어 "DB가 정본"이 깨진다.
- **`PostsInCategory`가 분류를 통째로 받는다.** id만 받으면 이 판정을 부르는
  쪽마다 따로 해야 하고, 그러면 **화면과 `형제 순서` 패널이 서로 다른 차례를
  본다.**
- **날짜 없는 글은 뒤로 보낸다.** 어느 날짜 옆에 놓을지 알 방법이 없다 —
  번호 없는 글을 번호 있는 글 사이에 안 끼우는 것과 같은 판단이다.
- **중첩된 하위 글도 같은 규칙으로 세운다.** 한 목록 안에서 층마다 순서가
  다르면 읽는 사람이 그 차이를 뜻으로 읽는다.
- **`형제 순서` 패널은 이 분류를 거절한다.** 여기서 옮겨봐야 다음에 쓴 글이 그
  앞에 서므로, 되지도 않는 일을 되는 것처럼 보여주지 않는다.
- 돌연변이 셋(규칙을 안 검 / 모든 분류에 검 / 날짜 없는 글을 앞으로)을 넣어
  테스트가 실제로 실패하는 것을 확인했다.

**그 밖의 화면 순서는 `sort_order`가 아니라 제목 앞 번호를 먼저 따른다** (`web.sortPosts`).
`created_time` 출처 708건이 분 단위라 자주 어긋나기 때문이다 — 실제로
`10. 무중단 배포`가 `2. 테스트 코드`보다 앞에 오는 목록이 있었다. 제목 앞 번호는
사람이 직접 붙인 것이라 훨씬 믿을 만하다. **DB의 `sort_order`는 안 고친다**;
읽을 때만 다시 세운다.

- 구분자(`.` 또는 `)`)와 공백을 반드시 요구한다. 안 그러면 `2022년 탐자 1차 시험`,
  `1주차 정리`, `42 : Cpp 모듈`의 앞자리를 번호로 착각한다.
- 번호 없는 글은 **번호 있는 것들 사이에 끼우지 않고 뒤로 보낸다.** 어느 번호 옆에
  놓을지 알 방법이 없다.
- **그 뒤쪽은 제목 자연 정렬로 세운다** (`naturalCompare`, 2026-08-23). 제목을 숫자
  덩어리와 글자 덩어리로 갈라 앞에서부터 견주고, 숫자끼리는 값으로, 숫자와 글자가
  만나면 숫자가 앞이다. 예전에는 들어온 순서(`sort_order`)를 그대로 뒀는데 그 값이
  노션 작성 시각이라, **번호가 제목 끝이나 중간에 붙은 시리즈가 통째로 엇갈렸다** —
  `practice problem 1 / 2022년 탐자 1차 / practice problem 2 / 연습문제 …`처럼.
  제목에 이미 번호가 적혀 있는데 그걸 안 읽고 작성 시각을 따르는 것이라, 없는 순서를
  지어내지 않는다는 원칙과는 반대쪽 문제였다.
  - 글자로 견주면 `(10)`이 `(2)`보다 앞에 온다. 그래서 숫자는 값으로 읽는다 —
    `인자분석 : 코드 (1)~(4)`가 실제로 그랬다.
  - **앞 번호 규칙은 그대로다.** 자연 정렬은 앞 번호가 없는 뒤쪽에만 걸린다.
    `42 : Cpp 모듈`이 `1. 확률`과 `2. 확률분포` 사이로 끼어들지 않는다.
- 카테고리 87개와 글 1357편을 전부 훑어 **51페이지(카테고리 17)의 목록 순서가
  바뀌는 것**을 확인했다. 전부 시리즈 번호가 흩어져 있던 자리다.
- 목록에 **원본 작성일을 같이 찍는다**(`original_created_at`). 순서가 이상해 보일 때
  근거를 눈으로 확인하라고 둔 것이다.
- **사람이 직접 정한 제목·작성일·순서는 `curation.PostMetadataEdits`가 이긴다.**
  import가 이 표의 제목·`original_created_at`·`sort_order`를 함께 적용하고,
  sortorder도 `-only all`일 때 같은 표로 덮는다. 일반 글의 재이관은 이미 복원한
  `sort_order`를 보존한다. 대상 묶음은 `curation.PostMetadataEdits`를 확인한다.

```sh
go run ./cmd/sortorder -db blog.db -only childpage          # child_page 출처만
go run ./cmd/sortorder -db blog.db -only created            # created_time 출처만
go run ./cmd/sortorder -db blog.db                          # 전체 미리보기
go run ./cmd/sortorder -db blog.db -only created -apply     # 반영
```

<a id="section-05"></a>
## 글 계층 (parent_id)

`cmd/postparent`가 채운다. 카테고리는 3단계가 끝이라 그보다 깊었던 노션 계층은
categorize를 거치며 평평해진다. `수학 & 통계 > 수리통계1 > 3. 일변량 분포 : 예시 >
베르누이 분포`의 글은 수리통계1 카테고리에 붙고, 사이의 `3. 일변량 분포 : 예시`는
카테고리가 아니라 **같은 카테고리의 다른 글**이 된다. `parent_id`가 그 잃어버린
층을 되살린다.

```sh
go run ./cmd/postparent -db blog.db -category 수리통계1          # 미리보기 (기본)
go run ./cmd/postparent -db blog.db -category 수리통계1 -apply   # 반영
```

- **한 번에 한 카테고리씩만 한다.** `-category`가 필수고 전체를 한 번에 도는 모드는
  없다. 먼저 수리통계1로만 시험했다(2026-08-16, 46건 전부 붙음). 추가 카테고리는 출처와 화면 개선을 확인한 뒤 적용한다.
- **출처는 sort_order와 같은 child_page 블록이다.** 덤프 스크립트가
  `child_page`/`child_database` 안으로는 재귀하지 않으므로(`notion-block-dump.mjs`),
  `{page}.json`에 나오는 child_page 블록은 **전부 그 페이지의 직속 자식**이다.
  단이나 토글 안에 깊이 박혀 있어도 부모는 덤프의 주인 페이지 하나로 정해진다.
  데이터베이스 행은 그 데이터베이스를 담은 페이지를 부모로 삼는다
  (`child_database` 블록의 id가 곧 데이터베이스 id다).
- **부모가 다른 카테고리에 있어도 그대로 가리킨다.** 수리통계1의 최상단 10건은
  부모가 `수리통계1` 글(id 597)인데 그 글은 상위 카테고리에 붙어 있다. 그래도
  **고치는 행은 언제나 `-category`로 준 카테고리의 글뿐이다.**
- 검증은 `original_path`로 한다. 자식 경로에서 마지막 한 칸(자기 제목)을 떼면
  부모 경로와 같아야 한다. 46/46이 맞았다. 어긋나면 미리보기가 짚어준다.
- **빅데이터 분석기사는 42건 전부 연결했다**(2026-08-22). 정확한 child_page는
  3건이고 나머지 39건은 경로 중간의 인라인 데이터베이스 한 칸을 건너뛰어 그
  데이터베이스를 담은 실제 글에 붙는다. 그래서 미리보기의 단순 경로 검사는
  3/42만 일치한다고 찍지만, 출처는 `데이터베이스 소유자`로 따로 명시되고 적용 뒤
  계획과 다른 값 0건·재실행 변경 0건을 확인했다. 명령의 `-category`는 이름이 아니라
  현재 slug이므로 `-category 빅데이터-분석기사`로 실행한다.
- 자식만 있고 본문이 없는 중간 노드도 **글로 남겨서 사슬에 유지한다.** 버리면
  원래 몇 단계였는지가 사라진다.
- `posts.parent_id`에는 `categories`와 달리 **깊이/순환을 막는 트리거가 없다.**
  postparent가 반영 전에 사슬이 도는지 보고, 웹 쪽 `nestPosts`와 `PostAncestors`도
  각자 방어한다.

<a id="section-06"></a>
## 카테고리 모델

카테고리는 최대 3단계다. `source_name`은 노션 유래 분류의 안정 키이고,
사람이 만든 분류에서는 NULL이다. name·slug·parent_id는 사람이 바꿀 수 있다.
`categories.cover_post_id`는 UNIQUE라 글 하나가 여러 분류의 표지가 될 수 없다.
분류 깊이는 트리거가 지키지만 `posts.parent_id`의 순환은 저장·이관 코드가 확인한다.
표지·인라인 DB·original_path가 만드는 화면 계층은 parent_id만으로 설명되지 않는다.

분류를 재구성할 때는 [운영 문서의 카테고리·curation](operations.md)을 읽는다.

<a id="section-07"></a>
## 마이그레이션

- 파일명은 `001_init.sql` 형식. 번호는 사전순이 아니라 **숫자순**으로 적용된다.
- **down 마이그레이션은 만들지 않는다.** 러너가 `*.down.sql`을 발견하면 거부한다.
  되돌려야 하면 되돌리는 내용의 새 마이그레이션을 추가한다.
- **이미 적용된 마이그레이션 파일은 고치지 않는다.** 러너가 sha256을 기록해두고
  내용이 바뀌면 실행을 거부한다 (DB의 실제 스키마와 파일이 갈라지는 걸 막기 위해).
- 각 마이그레이션은 트랜잭션 안에서 돌고, 실패하면 DDL과 적용 기록이 함께 롤백된다.

<a id="section-08"></a>
## SQLite에서 조심할 것

- **`_time_format=sqlite`를 DSN에서 빼지 마라.** 이게 없으면 드라이버가 `time.Time`을
  Go의 `String()` 형식으로 저장하고, SQLite의 `date()`/`datetime()`/`strftime()`이
  그걸 파싱하지 못해 **에러 없이 NULL**을 돌려준다. 발행일 기준 쿼리가 조용히 빈 결과를
  낸다. `internal/db/time_test.go`가 이걸 지키고 있다.
- **`foreign_keys`는 SQLite 기본값이 OFF다.** 커넥션 단위 설정이라 DSN으로 건다.
  `Open`이 실제로 켜졌는지 확인하고 아니면 에러를 낸다.
- 테스트에서 `:memory:`를 쓰지 마라. 커넥션 풀이 커넥션마다 별개의 인메모리 DB를
  만들어서 마이그레이션을 건 DB와 조회하는 DB가 달라진다. `t.TempDir()`에 파일로 만든다.
- **CHECK 제약은 나중에 못 고친다.** SQLite는 CHECK을 ALTER로 수정할 수 없어서
  테이블을 새로 만들어 옮겨야 하는데, 그건 아래 "삭제 금지" 원칙과 부딪힌다.
  값이 늘어날 수 있는 컬럼(`posts.source` 등)에는 CHECK을 걸지 않고 애플리케이션에서
  검증한다. `posts.status`는 세 값으로 확정이라 CHECK을 걸었다.

## 공개 서버 (읽기 전용)

`cmd/blog`의 공개 읽기 화면이다. status·visibility에 따른 접근 제어를 적용한다.
글쓰기/수정은 `internal/admin`에 따로 있고 **`-admin`을 줘야 뜬다**.
아래 실행 예의 DB는 실제 작업본 대신 일관된 사본을 사용한다.

```sh
go run ./cmd/blog -db blog.db -addr 127.0.0.1:8080            # draft 가림 (배포와 같은 모습)
go run ./cmd/blog -db blog.db -addr 127.0.0.1:8080 -drafts    # draft까지 보임 (로컬 확인용)
go run ./cmd/blog -db /tmp/admin.db -admin -admin-no-auth -drafts  # admin까지 (로컬 전용)
```

<a id="section-10"></a>
### 검색엔진에 주는 두 파일 (2026-09-03)

`robots.txt`와 `sitemap.xml`이다. **둘 다 파일로 두지 않고 요청이 올 때 DB에서
그린다** — DB가 정본이라 글이 늘거나 status가 바뀔 때마다 파일을 다시 만들어야
하는데, 그리면 그 일이 아예 없고 배포물도 안 는다.

- **사이트맵이 draft를 흘리면 안 된다.** 크롤러에게 주소를 알려주는 것이 곧
  공개라, 숨긴 글의 slug가 나가면 목록·카운트·본문 링크에서 draft를 가려온
  것이 통째로 무의미해진다. 그래서 새 조건을 쓰지 않고 `store`가 이미 쓰는
  `notHidden`·`visibleCategory`를 그대로 부른다. 현재 1,042개(홈 1 + 글 953 +
  분류 88)이고 draft 누출 0건이다. `TestSitemapNeverLeaksDrafts`가 지킨다.
- **호스트를 코드에 박지 않는다.** 요청의 `Host`를 쓴다 — 박아두면 로컬에서
  띄운 사이트맵이 배포 주소를 가리킨다. 스킴은 `X-Forwarded-Proto`로 안다.
  **blog 자신은 평문 8080을 듣고 있어서 `r.TLS`가 언제나 nil이다** — admin
  세션 쿠키가 `Secure`를 정하는 근거와 같은 자리다.
- **slug에 한글이 그대로 있어서** 경로 조각마다 URL 인코딩을 한다. 안 하면
  규격에 안 맞는다.
- `<lastmod>`는 `updated_at`이고 **날짜까지만** 적는다. 시각까지 주면 초 단위로
  바뀔 때마다 크롤러가 다시 받는다. 분류에는 고칠 때가 없어 아예 안 적는다 —
  모르는 날짜를 지어내지 않는다.
- **`robots.txt`는 차단 장치가 아니라 요청이다.** 나쁜 봇은 무시하므로 이걸로
  무엇을 지키지는 못한다 — `/admin`의 진짜 관문은 허용 목록과 세션이고
  `/api/admin`은 로그인 없이 401 JSON을 준다. 여기서 얻는 것은 **크롤 예산을
  글 쪽에 쓰게 하는 것**뿐이다. `/img/`와 `/static/`도 같은 이유로 막는다.
- 돌연변이 셋(draft를 안 가림 / 한글을 인코딩 안 함 / `X-Forwarded-Proto`
  무시)을 넣어 테스트가 실제로 실패하는 것을 확인했다.

<a id="section-11"></a>
### 허용된 계정만 보는 글 (2026-09-03)

**`posts.visibility = 'private'`인 글은 로그인해야 보인다**(`migrations/007`).
누구를 허용하느냐는 admin이 이미 들고 있는 `BLOG_ADMIN_LOGINS` 하나가 정한다 —
web은 세션도 목록도 모르고 "지금 누가 들어와 있나"만 함수로 받는다(`WithEditor`).

- **status와 축이 다르다.** status는 **글이 어디까지 왔나**(안 쓴 자리 /
  아카이브 본문 / 골라 세운 글)이고 visibility는 **누가 볼 수 있나**다. 한 칸에
  밀어 넣으면 "draft이면서 비공개"를 적을 수 없다. 그래서 `-drafts`를 켜도
  비공개 글은 안 열린다 — 로컬 확인용 스위치 하나가 공개 규칙을 바꾸면 안 된다.
- **`status`에 값을 더하는 길은 애초에 막혀 있다.** 거기에는 CHECK이 걸려 있고
  SQLite는 CHECK을 ALTER로 못 고친다. 테이블을 새로 만들어 옮기는 것은
  "삭제하는 마이그레이션은 만들지 않는다"와 정면으로 부딪힌다.
- **판정은 여전히 `store` 한 곳이다**(`notHidden`·`hides`). 다만 draft와 달리
  **요청마다 다르다.** 그래서 `Server`가 store를 두 벌 들고(`store`·`member`)
  요청마다 하나를 고른다(`viewFor`). 핸들러는 맨 앞에서 `st := s.viewFor(r)`를
  받고 그 뒤로는 예전과 같다.
- **`WithEditor`가 없으면 아무에게도 안 보인다.** `-admin`이 없는 배포에서
  실수로 열리는 방향이 아니라 막히는 방향으로 틀린다 — 고치기 버튼의 기본값이
  "닫힘"인 것과 같은 규칙이다.
- **사이트맵에는 로그인해도 안 나온다**(`s.store`를 그대로 쓴다). 크롤러에게
  주소를 알려주는 것이 곧 공개라, 여기서 새면 목록에서 가린 것이 통째로
  무의미해진다.
- **본문 링크는 draft와 똑같이 글자로 푼다**(`unlinkHidden`). 줄째 지우면
  문장이 끊기고, 링크로 두면 눌러야 없는 줄 안다.
- **보고 있을 때 "비공개"라고 적는다**(`span.status.private`). 로그인해서 보면
  평소와 똑같아서 다른 단서가 없다. **이 표시가 새는 자리는 아니다** — 로그인이
  풀린 사람에게는 그 글이 통째로 404다.
- **이관은 이 칸을 안 건드린다.** `import`도 `importgh`도 컬럼 목록에 없어서
  재이관해도 그대로 남는다. 사람이 정하는 값이라 맞다 — GitHub 이관이 slug를
  안 덮는 것과 같은 판단이다.
- **`/img/{sha256}`는 여전히 어느 글이 그 그림을 쓰는지 보지 않는다.** draft
  이미지가 해시를 알면 받아지는 것과 똑같은 구멍이고, 비공개 글의 그림도
  마찬가지다. 여기를 막으려면 이미지마다 쓰는 글을 세야 한다.
- 돌연변이 셋(`notHidden`이 visibility를 무시 / `viewFor`가 늘 member /
  `hides`가 visibility를 무시)을 넣어 테스트가 실제로 실패하는 것을 확인했다.

<a id="section-12"></a>
### 없는 길과 터진 요청 (2026-08-24)

**404와 500도 이 사이트의 화면으로 나간다** (`internal/web/errorpage.go`,
`templates/error.html`). 홈 표제지와 같은 활자만 쓰고 사이드바가 함께 나온다 —
막다른 화면이면 뒤로 가기 말고는 길이 없다.

- **상태 코드는 그대로다.** 404 화면은 404를 준다. 화면이 생겼다고 200을 주면
  검색엔진과 링크 검사기에게 거짓말이 된다.
- **숨긴 글과 없는 글의 화면이 글자 하나까지 같아야 한다.** 다르게 말하면
  그 차이 자체가 "여기 draft가 있다"는 신호가 된다. 테스트가 지킨다.
- **`Cache-Control: no-store`.** 글 하나를 공개로 바꿨는데 중간 캐시가 404를
  들고 있으면 그 글은 계속 없는 것이 된다.
- **`/img/`와 `/static/`은 예전대로 글자 한 줄이다.** `<img>`가 오류 화면을
  받아봐야 깨진 그림 아이콘 하나로 끝나고, 67KB짜리 페이지만 헛되이 나간다.
  자산 라우트에서만 `http.NotFound`를 그대로 쓴다.
- **`GET /`를 catch-all로 등록했다.** 네 단계 이상처럼 어느 패턴에도 안 걸리는
  경로가 ServeMux 기본 404(글자 한 줄)로 빠지던 것을 막는다. `GET /{$}`가 홈이라
  더 구체적인 쪽이 이긴다.
- **`renderError`는 `render`를 거치지 않는다.** `render`는 실패하면 `fail`을
  부르고 `fail`은 다시 `renderError`로 오므로, 그 길로 가면 사이드바 조회가 한 번
  삐끗할 때 무한히 돈다. 여기서는 사이드바를 "되면 좋은 것"으로 다룬다 — 못
  가져오면 없는 채로 그린다. **오류 화면만은 DB가 어떻든 나가야 한다.**
- **본문을 다 그린 뒤에 한 번에 내보낸다.** 템플릿이 도중에 실패해도 반쯤 그린
  화면이 나가지 않는다. 그것마저 실패하면 마지막으로 글자만 내보낸다.
- 글자는 공통 UI라 `data-i18n` 키로 `preferences.js`의 고정 사전이 세 언어로
  바꾼다. **키가 코드(`errorInfos`)에 있고 화면에는 속성값으로만 나가서** 이름을
  바꿔도 조용히 한국어로 남는다 — `TestErrorPageTextIsInEveryDictionary`가 지킨다.

**panic이 연결만 끊고 끝나지 않는다** (`internal/web/recover.go`).

- **net/http도 panic을 잡는다.** 다만 잡은 뒤에 하는 일이 연결을 그냥 끊는
  것이라 브라우저는 빈 화면이나 "연결이 재설정됨"을 본다. 가로채면 스택이
  로그에 남고 읽는 사람에게는 500 화면이 간다.
- **panic은 응답을 쓰는 도중에도 난다.** 템플릿이 본문 절반을 내보낸 뒤 터지면
  상태 코드는 이미 200으로 나가 있어 바꿀 수 없다. `trackedWriter`가 무엇이든
  쓰기 시작했는지 기억해두고, **안 썼을 때만** 500 화면을 그린다. 이미 썼으면
  로그만 남기고 끊는다 — 잘린 HTML 뒤에 오류 화면을 덧붙이면 더 읽기 힘들다.
- **`http.ErrAbortHandler`은 되던진다.** 그건 "조용히 끊어라"라는 약속된
  신호라, 우리가 삼키면 그 뜻이 사라지고 로그만 지저분해진다.

**HTTP 타임아웃을 걸었다** (`cmd/blog`의 `httpServer`).

**`http.ListenAndServe`의 기본값은 전부 "무제한"이다.** 연결을 열고 요청을 끝내지
않는 클라이언트가 고루틴과 파일 디스크립터를 계속 물고 있어서, 공개 주소에 그대로
두면 느린 연결 몇 개로 서버가 멎는다. 인증이 없는 읽기 전용 서버라 더 그렇다.

| 값 | 왜 |
|---|---|
| `ReadHeaderTimeout` 5초 | GET뿐이라 받을 것이 사실상 헤더밖에 없다 |
| `ReadTimeout` 15초 | 〃 |
| `WriteTimeout` 60초 | 가장 큰 응답이 3.4MB짜리 이미지 BLOB이다. 60초면 57KB/s에서도 끝난다 — **짧게 잡으면 느린 회선에서 그림이 잘린다** |
| `IdleTimeout` 60초 | keep-alive를 그보다 오래 붙들지 않는다 |
| `MaxHeaderBytes` 64KB | 정상 요청에 쿠키도 인증 헤더도 없다 |

- 헤더를 끝내지 않는 소켓이 **5.0초 뒤 끊기는 것**을 실측했다. 그 전에는 영원히
  기다렸다.
- `cmd/blog/main_test.go`가 네 타임아웃이 0(무제한)이 아닌지, 쓰기가 읽기보다
  긴지 지킨다.

<a id="section-13"></a>
### draft는 남에게 안 보인다 (2026-08-23)

**`draft`는 목록·카운트·본문 링크 어디에도 안 나오고 `/p/{slug}`도 404다.**
status의 뜻은 다음과 같다. 현재 건수는 대상 DB에서 확인한다:

| status | 뜻 | 공개 서버 |
|---|---|---|
| `draft` | 아직 안 쓴 자리 | 숨긴다 |
| `unlisted` | 아카이브 본문 | 보인다 |
| `published` | 골라 앞에 세운 글 | 보인다 + 나중에 홈에 |

**status와 나란히 `visibility`가 있다**(2026-09-03, `migrations/007`). 그건
"어디까지 썼나"가 아니라 **"누가 볼 수 있나"**라 축이 다르다 — 위
"허용된 계정만 보는 글" 참고.

- **"published만 보여준다"가 아니다.** `unlisted` 아카이브도 공개 대상이다.
  published는 선별한 글을 구분하는 상태다.
- **판정은 `store` 한 곳에만 있다** (`notHidden`). 핸들러마다 챙기게 하면 새 조회를
  더할 때마다 구멍이 하나씩 생긴다 — render가 사이드바를 한 번에 채우는 것과 같은
  이유다. `-drafts`(`web.WithDrafts()`)면 예전처럼 전부 보인다.
- **기본값은 "가린다"다.** 켜고 끄는 것을 실수해도 새는 방향이 아니라 막는 방향으로
  틀리게 둔다.

**가리면 연쇄로 깨지는 자리가 있어서 함께 처리했다.**

| 무엇 | 규모 | 처리 |
|---|---:|---|
| 글 상세 | 366편 | `PostBySlug`가 걸러 404 |
| 목록·트리 | — | `PostsInCategory`·`ChildPosts`·`PostAncestors`·`InlineDBGroups`·`CategorySubtreePostSlugs`·`PathBranches` |
| 사이드바 글 수 | 1,356 → **990** | `subtreePostCount` |
| 표지가 draft인 분류 | 3개 | `coverSlug`가 빈 값을 줘서 표지 없는 분류로 다룬다 |
| draft를 가리키는 본문 링크 | 129개 / 32편 | **링크만 벗기고 글자는 남긴다** (`unlinkHidden`) |
| 통째로 비는 인라인 DB 목록 | 16개 | 〃 |
| 낱개 링크 상자 | 전부 draft 12 / 일부 47 | 위의 결과로 저절로 정리된다 |
| 글이 0이 된 분류 | 3개 | 아래 참고 |
| where42 카드 글 수 | 3 → 2 | 보이는 링크만 센다 |

- **표지가 draft면 반드시 걸러야 한다.** 표지는 본문을 목록 위에 **통째로 펼치므로**,
  안 거르면 draft 본문이 그대로 공개된다. 현재 pipex·Shell·Javascript 세 곳이고,
  지금은 평소 목록으로 그려진다.
- **링크는 지우지 않고 푼다.** 줄째 지우면 문장이 끊기고, 링크로 두면 눌러야 없는
  줄 아는 길이 된다. `[페이지 링크]` 자리표시자는 그냥 풀면 그 말이 글자로 드러나서
  **진짜 제목으로 바꿔** 남긴다.
- **`PostSummariesBySlug`만은 숨긴 글도 돌려준다** (`PostSummary.Hidden`).
  `resolveBody`가 **"posts에 없는 slug = 노션 데이터베이스"** 로 판정하기 때문이다.
  draft를 조회에서 그냥 빼면 draft 링크가 이 판정에 걸려 **엉뚱한 목록이 펼쳐진다.**
  세 상태를 구별해야 한다: 보인다 / 숨겼다 / 아예 없다.
- **`InlineDBGroups`는 행이 다 숨겨져도 이름을 남긴다**(빈 슬라이스). "행이 하나도
  안 남은 목록"과 "애초에 없는 목록"은 다르게 다뤄야 한다 — 앞은 링크를 풀고,
  뒤는 손대지 않는다(짝을 못 찾은 죽은 링크다).
- **글이 0이 된 분류는 노션 유래만 감춘다** (`visibleCategory`). `알고리즘 : 기초
  (1)`·`(2)`는 덤프가 만든 마디라 `0`으로 남으면 막다른 길이지만, `라이프`는
  사람이 앞으로 채우려고 세운 빈 선반이라 남긴다. 이 구분은 `source_name`이
  이미 하고 있다(NULL이면 사람이 만든 것).
- **본문은 짧아도 남을 묶는 마디는 `curation.StatusEdits`로 `unlisted`로 올린다.**
  덤프 분석이 블록 5개 미만을 draft로 보는데, 빅데이터 분석기사의 `개념정리`(자식 23)와
  `실전문제`(자식 8)가 그 어림짐작에 걸렸다. 가리면 표지의 두 링크가 글자로 풀리고
  자식 27편이 묶음을 잃는다. DB를 손으로 고치면 다음 `import -db`가 CSV 값으로
  되돌리므로 표에 적는다.
- 전수 검증: 숨긴 글 366편 URL이 **전부 404**, 보이는 글 990편 + 카테고리 88개
  **전 페이지 200**, 그 1,078페이지에 그려진 `/p/` 링크 986개 중 **숨긴 글을
  가리키는 것 0개**, 사이드바 합계 990 = DB 990.

| 라우트 | 하는 일 |
|---|---|
| `GET /{$}` | 표제지 하나뿐인 홈 (분야 탐색은 사이드바가 전담) |
| `GET /robots.txt` | 크롤러에게 주는 규칙 (sitemap.go) |
| `GET /sitemap.xml` | 주소 목록. DB에서 그때그때 그린다 |
| `GET /{l1}` `GET /{l1}/{l2}` `GET /{l1}/{l2}/{l3}` | 하위 분류 + 직속 글 |
| `GET /p/{slug}` | 글 상세 (마크다운 렌더링) |
| `GET /img/{sha256}` | 이미지 BLOB, Content-Type은 `images.mime` |
| `GET /static/{file}` | 바이너리에 박힌 JS |
| `GET /` | 어디에도 안 걸린 경로 → 404 화면 |

- **홈은 표제지·자유 본문·최근 글로 구성한다.** 분야 탐색은 사이드바가 맡고,
  자기소개 본문은 `/intro`에서 편다. 옛 홈의 지도·추천 경로는 활성 기능이 아니다.
- **홈 화면을 admin에서 짠다** (2026-09-08, `migrations/008`의 `settings`,
  `internal/web/settings.go`). 표제지 네 줄과 **자유 본문**, 최근 글 수를
  admin의 `홈 화면` 메뉴에서 고친다(2026-09-09에 제 화면으로 나왔다 — 그전에는
  환경설정 구석에 문구 네 줄만 있어서 **있는 줄을 몰랐다**).
  - **홈도 글처럼 쓴다.** 표제지 아래 본문은 마크다운이고 **글과 같은
    렌더러로 그린다** — 수식도 코드도 목록도 글에서 되는 것은 여기서도 된다.
    홈에 무엇을 둘지는 사람이 정할 일이지 코드가 정할 일이 아니다.
  - **그 본문도 자산 판정에 넣는다**(`assetBody`). 빠뜨리면 홈에서만 수식이
    원문 LaTeX로 남는다 — 표지의 참고 절을 빠뜨리면 안 되는 것과 같은 자리다.
  - **최근 글 수는 0도 뜻이 있다.** "그 절을 안 그린다"라서 빈 값(안 정함)과
    구별해야 한다 — 아래 문구들과 반대다. 문장 하나를 고치려고 코드를 고쳐 배포하는 것은 "글은 웹
  UI에서 직접 쓰고 고친다"와 어긋난다 — 홈에 서는 문장도 결국 글이다.
  - **posts가 아니라 key-value다.** 홈 문구는 주소도 목록도 분류도 없다.
    posts에 넣으면 사이트맵·목록·표지 판정이 전부 "이건 예외"를 하나씩 더 든다.
  - **값마다 행이다.** JSON 한 덩어리면 두 화면이 동시에 저장할 때 나중 것이
    앞의 것을 통째로 지운다.
  - **기본값은 DB에 미리 안 넣는다.** 행이 없다는 것이 곧 "아무도 안 고쳤다"라서,
    그동안은 코드에서 문장을 다듬을 수 있다. 넣어두면 아무도 고친 적 없는
    문장이 그 순간 DB에 굳는다. 그래서 **빈 값은 저장이 아니라 삭제다** —
    비우면 기본 문구로 돌아가고, 화면은 그 기본값을 자리표시자로 깔아 둔다.
  - **사람이 고치면 눈썹줄의 `data-i18n`을 뗀다.** 그 속성이 있으면
    `preferences.js`의 고정 사전이 언어를 바꿀 때 `textContent`를 통째로
    갈아치워서 **방금 적은 문장이 조용히 사라진다.** 기본 문구일 때만 사전을 쓴다.
  - **제목을 두 줄로 나눠 든다.** 아랫줄에만 형광 노랑 블록이 깔리는데, 한 칸에
    담아 `<br>`을 글자로 받으면 태그가 화면에 드러나거나 사람이 HTML을 쓰게 된다.
    둘째 줄을 비우면 제목이 한 줄이다.
  - **저장은 통째로 바꾸기가 아니다**(보낸 키만 고친다). 나중에 다른 화면이 다른
    키를 저장할 때 이 화면의 값을 조용히 날리지 않게. **모르는 키는 400이다.**
  - 돌연변이 둘(고쳐도 사전 키를 계속 붙임 / 저장된 값을 무시)을 넣어 테스트가
    실제로 실패하는 것을 확인했다. 브라우저로 폼에 적어 저장하니 홈이 그대로
    바뀌고, 390px에서 문서폭이 넘지 않는다.

- **홈에 최근 글이 붙었다** (2026-09-01, `store.RecentPosts`). 예전에는 정직하게
  만들 수 없다고 적어뒀는데 **그 전제가 바뀌었다** — 아카이브의 최신 글이 실제로
  2025년이고, admin이 붙어 새 글은 쓰는 날짜가 그대로 들어간다. 그래서
  `original_created_at`이 곧 진짜로 쓴 날이다.
  - **날짜를 같이 찍는다.** "최근"이라는 말이 날짜보다 앞서 나가지 않게 —
    목록에 원본 작성일을 찍어 순서의 근거를 보이게 한 것과 같은 이유다.
  - 날짜 없는 글은 뺀다. 없는 순서를 지어내지 않는다. 6편, 중첩 없이.
  - 방명록은 여전히 없다.

- **카테고리 경로는 3단계까지 받는다.** 글 1408건 중 1279건이 3단계에 있어서,
  두 단계만 열면 대부분의 글에 탐색으로 닿지 못한다.
- 경로는 위에서부터 부모가 맞는지 확인한다. 존재하는 카테고리라도 엉뚱한 부모
  밑에 붙여 부르면 404다.
- `/{l1}`이 `/p/...`나 `/img/...`를 삼킬 것 같지만, Go의 ServeMux가 더 구체적인
  패턴을 먼저 고르므로 리터럴이 있는 쪽이 이긴다.
- **글 하나를 가리키는 경로는 `/p/{slug}`뿐이다.** `/{slug}`는 글이 아니라 최상위
  카테고리로 해석된다. 본문 안의 링크를 만드는 쪽(`internal/importer`의
  `PostURLPrefix`)과 이 라우트가 같은 접두사를 써야 한다. 한동안 어긋나 있었다.
- **본문의 죽은 링크 두 종류는 렌더링 직전에 손본다** (`internal/web/inline.go`).
  DB의 `body`는 건드리지 않는다. 변환기를 고쳐 재이관하는 길도 있었지만, 그러면
  1408건 재변환 + relink 재실행이 딸려오고 다음 재이관 때 또 날아간다.
  렌더링에서 처리하면 재이관과 무관하게 항상 맞는다.

  | | 무엇 | 어떻게 | 현재 |
  |---|---|---|---|
  | ① | `[페이지 링크](/p/{slug})` | 대상 글의 `title`로 글자만 바꾼다 | 14개 / 9글 |
  | ② | `[제목](/p/{데이터베이스 id})` | 그 밑 글들을 목록으로 펼친다 | 100개 / 57글, 763건 |

  - ①의 원인은 **`link_to_page` 블록에 제목이 없다는 것**이다(페이로드에 `page_id`만
    있다). 변환기는 페이지를 하나씩 따로 처리해서 그 시점에 제목을 알 수 없다.
    링크 글자가 `페이지 링크`와 **정확히 같을 때만** 바꾼다. 본문에 그냥 글자로
    "페이지 링크"가 들어 있는 글이 1건 있는데(`[Ch1] 빅데이터의 이해`) 안 건드린다.
  - ②는 **노션 데이터베이스가 페이지가 아니라 `posts`에 절대 안 들어가서** 생긴다.
    행 793건은 이미 posts에 다 있고, 없는 건 목록 그 자체다.
  - **데이터베이스 id로는 그 자식을 찾을 수 없다.** 남은 유일한 끈이
    `original_path`다. 한 층 더 들어간 글의 경로가 `{주인 경로} > {DB 이름} > {제목}`
    꼴이라 가운데 칸이 곧 DB 이름이고, 링크 글자와 **정확히 같을 때만** 펼친다.
    바로 아래 한 칸인 이름은 뺀다 — 그건 실제 글(child_page)이지 DB가 아니다.
  - **이름이 어긋나면 그냥 둔다.** 남은 것끼리 순서대로 짝지어 보는 것도 해봤는데,
    링크는 6개 더 품는 대신 **남의 글 46건이 섞여 들어갔다.** 지금 못 품는 19개는
    전부 이름이 `Untitled`/`New database`인 데이터베이스다.
  - 펼친 HTML은 **줄바꿈이 없어야 한다.** 마크다운 본문에 끼워 넣는데 CommonMark의
    HTML 블록은 빈 줄에서 끝나므로, 줄이 나뉘면 뒷부분이 마크다운으로 다시 해석돼
    태그가 글자로 드러난다. `inlineDBHTML`이 이걸 확인하고 어기면 에러를 낸다.
  - 목록은 `sortPosts`를 사용한다. 수동 순서·번호·자연 정렬과 최근순 예외는
    이 문서의 "형제 순서" 절을 따른다.
- **하나짜리 링크는 그 절의 내용이 그것뿐일 때만 묶는다** (`isWholeSection`,
  2026-09-02). 원래는 둘 이상만 묶었고 근거는 "하나짜리는 목록이 아니라 문장
  사이의 링크다"였다. 63개 중 36개는 실제로 그렇다. 그런데 나머지 27개는 제목
  바로 아래에 링크 하나만 있고 다음 제목까지 아무것도 없는 자리다 — 그건 **항목이
  하나뿐인 목록**이지 문장 사이의 링크가 아니다. `확률분포 정리` 표지에서
  `다변량, 연속형 분포`는 상자인데 바로 아래 `다변량, 이산형 분포`는 맨 링크
  하나로 나왔다. **같은 구조가 같아 보이지 않으면 읽는 사람이 그 차이를 뜻으로
  읽는다.**
- **줄줄이 이어진 낱개 글 링크도 같은 상자로 묶는다** (`groupLinkRuns`). 사람이
  `link_to_page` 블록을 여러 개 쌓아 만든 목록은 인라인 데이터베이스와 겉모습이
  달라질 이유가 없다.
  - **상자 안에는 작성일과 `draft` 뱃지를 함께 찍는다.** 본문에서 뽑아낸 링크에는
    slug와 글자밖에 없어서, 나머지는 `store.PostSummariesBySlug`로 가져와 채운다.
    이걸 안 넘기면 같은 모양의 상자가 한쪽만 날짜를 달고 나온다 — 실제로 그랬다
    (`/dev/tooling`의 `Git / Github` 상자).
  - **링크 글자는 본문 것을 쓴다.** 사람이 그 자리에 쓴 말이 제목과 다를 수 있고,
    자리표시자는 이 시점에 이미 진짜 제목으로 바뀌어 있다.
  - **짝이 없으면 날짜와 뱃지만 빠지고 링크는 남는다.** 전부 훑어보니 그런 자리는
    이름 없는 인라인 데이터베이스(`Untitled`/`New database`)를 가리키는 3곳뿐이고,
    그건 posts에 행 자체가 없는 것이다(operations.md의 "남은 작업" 참고).
- **경로에서 이름이 앞 칸과 같은 조상 글은 건너뛴다** (`appendPostCrumbs`,
  2026-09-03). 분류의 표지 글은 그 분류와 이름이 같은 경우가 많은데(수리통계1·2,
  탐색적 자료분석, 확률과정론 — **61편**), 카테고리 사슬 뒤에 상위 글 사슬을
  그대로 이으면 `… / 수리통계2 / 수리통계2`처럼 같은 말이 두 번 찍혔다.
  **가는 곳도 사실상 같다** — 그 분류를 열면 표지 본문이 위에 펼쳐진다.
  이름이 다른 조상은 그대로 남긴다. 빼면 그 글이 어디쯤인지 알 수 없다.
- **글 상세에는 본문에서 뽑은 목차가 붙는다** (`markdown.Outline`). h1~h3만, 제목이
  3개 이상일 때만. **누르면 접힌다** — `<details open>`이 하므로 스크립트가 없어도
  된다(사이드바가 서버에서 펼쳐 나가는 것과 같은 이유). 삼각형은 사이드바가 쓰는
  것과 같은 SVG다. 목차는 **죽은 링크를 손본 뒤의 문자열**에서 뽑아야 앵커가 본문과
  맞는다. 같은 파서 설정으로 같은 원문을 두 번 읽으면 자동 id가 같은 답을 낸다.
- **본문 제목은 한 단계 내려서 그린다** (`markdown.headingShift`). 페이지의 `<h1>`은
  글 제목(또는 카테고리 이름)이고 템플릿이 그린다. 본문의 `# 제목`까지 `<h1>`이면
  한 페이지에 `<h1>`이 여러 개가 되어, 문서 구조상 형제가 아닌 것이 형제로 보인다.
  파서 단계(AST 변환기)에서 내리므로 **렌더링과 `Outline`이 같은 값을 본다.**
  - **앵커(id)는 안 바뀐다.** goldmark의 자동 id는 제목 글자로 만들고 단계를 보지
    않는다. 이미 나가 있는 `#앵커` 링크가 안 깨진다.
  - `Outline`은 사람이 읽을 단계(본문 기준 1부터)로 **되돌려서** 돌려준다.
    템플릿이 `toc-h{{.Level}}`로 들여쓰기 때문에, 안 되돌리면 목차 들여쓰기가
    통째로 한 칸 밀린다.
  - CSS도 같이 밀었다. 본문에서 가장 큰 제목은 이제 `h2`라 **`article h2`가 옛
    `article h1` 자리**를 쓴다. `article h1` 규칙은 본문에 h1이 없으므로 지웠다.
  - 글 1502페이지 전부 `<h1>`이 정확히 1개임을 확인했다.
- **제목 앵커 생성기를 갈아끼웠다** (`markdown.headingIDs`). goldmark 기본 구현은
  한 바이트가 아닌 글자를 전부 버려서 한글 제목이 죄다 `heading`, `heading-1`이
  된다. 링크는 되지만 주소에 뜻이 없고, **글을 고쳐 제목 하나만 늘려도 뒤쪽 앵커가
  통째로 밀린다.** 규칙은 카테고리 slug와 같다 — 소문자 + 공백/`:`/`/`/`.`→하이픈,
  나머지 기호는 버리고 한글은 그대로. 생성기는 쓴 id를 기억하는 상태라 파싱마다
  새로 만든다(`newParseContext`).
- **본문이 한 번도 안 가리키는 아래 갈래는 상자로 편다** (`store.SubBranches`,
  2026-09-02). 노션에서 온 표지 글은 **나중에 다른 출처로 들어온 글을 알 리가
  없다.** `Java` 표지의 목차 여덟 절은 기초 문법을 전부 안내하는데, 그 아래
  `Java > 모던 자바 >` 16편은 GitHub에서 2026-09-01에 들어온 것이라 본문에
  한 줄도 없었다. `프로그래밍 언어`는 카드만 보여주므로(카드가 있는 분류는
  카드만) **주소를 직접 치는 것 말고 닿는 길이 아예 없었다.**
  - 재료는 `original_path`다. `PathBranches`가 카테고리 화면에서 잃어버린
    첫 칸을 되살리는데, 그보다 깊은 칸은 그 갈래의 표지 글까지 와야 보인다.
  - **한 편이라도 본문에 링크돼 있으면 그 갈래는 안 그린다.** 판정은
    `dropLinkedChildren`과 같은 `linkedSlugs`다 — 두 곳이 같은 질문("본문이
    이미 안내했나")을 하므로 답도 한 곳에서 낸다. `문자열 다루기`와
    `자바 : 자료구조`가 그렇게 빠진다.
  - **두 편부터다.** 대부분은 갈래가 아니라 직속 자식 한 편인데, 그건 층이
    아니라 글 하나다. 이름표를 씌워 상자로 세우면 알려주는 것보다 늘어나는
    것이 많다.
  - **`hiddenBranch`는 웹의 화면 장치다.** `(제목 없음)`은 이름이 아니고,
    `수업 : 통수 & 선계`는 사람이 `curation.BodyEdits`로 이미 없앤 묶음이라
    여기서 되살리면 **코드가 사람이 지운 것을 되돌리는** 셈이다(남은 다섯
    편은 최적화이론의 평범한 글로 이미 목록에 선다). 갈래 카드·외부 링크와
    같은 이유로 코드에 둔다 — 본문(DB)에 적으면 `import -db`가 덮고,
    curation에 적으면 웹이 그 패키지를 읽게 되어 "DB가 정본"이 깨진다.
  - 상자 모양은 **인라인 데이터베이스를 펼친 것과 같다.** 둘 다 "이 글 아래에
    이런 목록이 있다"를 말하는 자리다.
  - 공개 글 962편을 전부 훑어 상자가 붙는 곳이 **둘뿐**임을 확인했다:
    `Java`의 `모던 자바` 16편, `R`의 `난수 만들기` 3편. 돌연변이 넷(guard를
    전부 없앰 / 한 편짜리도 세움 / 이름 검사 없앰 / 본문 링크 무시)을 넣어
    테스트가 실제로 실패하는 것을 확인했다.
- **글 상세의 "하위 글"에서, 본문이 이미 링크로 가리키는 글은 뺀다**
  (`dropLinkedChildren`). `cmd/postparent`가 `parent_id`를 채운 근거가 child_page
  블록인데 **그 블록은 본문에서 링크가 된다.** 그래서 손대지 않으면 본문에 목록이
  있고 그 아래 "하위 글"에 같은 목록이 또 나온다.
  - **본문 HTML에서 찾는다.** 원문 마크다운이 아니라 렌더링 결과를 보는 이유는,
    펼친 인라인 데이터베이스처럼 렌더링 단계에서 생기는 링크까지 세야 하기 때문이다.
  - **글 하나씩 따진다.** 카테고리 쪽 `dropCoveredChildren`과 달리 "일부만 겹치면
    남긴다"를 안 따진다. `Children`은 직속 하위 글의 평평한 목록이고 뺀 글로 가는
    링크가 본문에 그대로 있어서 길이 사라지지 않는다.
  - 지금은 하위 글이 있는 부모가 13편이다(수리통계1 6, 수리통계2 5,
    탐색적 자료분석 1, 확률과정론 1). 링크된 직속 자식만 빼기 때문에 일부만

  (`dropCoveredChildren`). 노션에서 한 절의 머리에 두던 인라인 데이터베이스가 두
  벌로 나타나기 때문이다: categorize가 경로에서 그 이름을 카테고리로 뽑아 "하위
  분류"에 넣고, 같은 데이터베이스가 표지 글 본문에도 링크로 남아 이제 목록으로
  펼쳐진다.
  - **이름이 아니라 글로 따진다.** `Language > 프로그래밍 언어`는 이름이 같은데
    분류에 191건이 있고 본문에 펼쳐진 건 7건뿐이다. 이름만 보고 빼면 184건으로
    가는 길이 사라진다.
  - 섹션을 통째로 없애지 않는 이유도 같다. `머신러닝 & 딥러닝`은 본문이 안 다루는
    분류가 하나 더 있다.
  - 표지 글이 있는 분류 중 9개가 이 처리에 걸리고, 그중 6개는 섹션이 통째로 사라진다.
- **좁은 화면(375px)에서 페이지가 가로로 밀리지 않는다.** 넘칠 수 있는 것은
  전부 **제 안에서만** 스크롤한다: `pre`(코드), `table`, `.math-display`,

  - 훑을 때 **검사기가 진짜로 잡는지 먼저 확인할 것.** 900px짜리 div를 끼워 넣어
    918이 잡히는지 보는 식이다. "0개"가 검사가 안 돌아서 나온 0일 수 있다.

    조용히 멈춘 채 "진행 중"으로 보인다. iframe의 `load`면 충분하다 —

  손볼 때 깨지기 쉬운 자리 넷:
  - **인라인 `code`에 `white-space: nowrap`을 걸지 마라.**
    `array(['longitude', 'latitude', ...])` 같은 조각이 460px까지 삐져나간다.
  - **인라인 수식은 줄바꿈이 안 된다.** KaTeX가 한 덩어리로 그리므로
    `.math-inline`을 `inline-block` + `overflow-x: auto`로 가둔다.
  - **`overflow-x: auto`만 걸면 스크롤바 두 개가 생긴다.** 한 축이 `visible`이
    아니면 다른 축의 `visible`은 `auto`로 계산되므로 `overflow-y`까지 `auto`가 된다.
    KaTeX가 그린 식이 줄 상자보다 2px 높은 것만으로 세로 스크롤바가 뜨고, 그게
    폭을 15px 먹으면 이번엔 가로까지 넘쳐 가로 스크롤바가 또 뜬다 — 짧은
    `\sqrt x` 옆에 회색 알약 두 개가 붙는다. 수식 1528개 중 **730개(글 113편)**가
    이랬다(2026-08-21에 고쳤다). 세로는 스크롤할 것이 없으니 `overflow-y: hidden`,

    넘치는 인라인 식은 1528개 중 2개뿐이다.** 블록 수식(`.math-display`)은 제 줄을

    나가는 링크와 같은 이유다 — 본문(DB)에 순서를 적으면 다음 `import -db`가
    덮어써서 사라진다.
- **카테고리 글 목록은 `parent_id`대로 중첩해서 그린다** (`nestPosts`). 뿌리는
  `parent_id`가 NULL인 글과 **부모가 그 목록 밖에 있는 글**이다. 후자가 흔하다 —
  카테고리 최상단 글들의 부모는 보통 한 단계 위 카테고리에 붙은 표지 글이다.
  그래서 "`parent_id IS NULL`인 것만 뿌리"로 잡으면 목록이 통째로 빈다.
- **`parent_id`가 없는 분류는 노션 경로에 남은 층으로 다시 묶는다**
  (`internal/web/pathtree.go`). `프로그래밍 언어` 191편처럼 한 층으로 쏟아지던
  목록이 그 대상이다 — categorize가 3단계에서 평평하게 만든 층이
  `original_path`에는 그대로 남아 있어서, 분류 이름을 닻으로 삼아 그 뒤의 칸을
  다시 세운다. `postparent`가 채운 `parent_id`와 달리 **DB는 안 건드리고 읽을
  때만 묶는다** — `sortPosts`가 제목 앞 번호를 읽는 것과 같은 성질이다.
  - **못 묶으면 error가 아니라 nil이다.** 그러면 화면이 예전 `posttree`로
    돌아간다. 반쪽짜리 묶음보다 평소 목록이 낫다.
  - **포기하는 조건이 넷이고 넷 다 테스트가 지킨다**(돌연변이로 확인했다):
    ① 사람이 만든 분류(`source_name`이 NULL)거나 12편 미만,
    ② `parent_id`가 이미 층을 만든 목록 — 계층이 두 벌이면 어느 쪽이 맞는지
    화면만 보고는 알 수 없다, ③ **한 편이라도 닻을 못 찾으면 통째로** —
    `PostMoves`가 다른 분류에서 데려온 글(선형대수 11편)이 그렇고, 그 경로로
    묶으면 남의 층을 빌려온다, ④ 마디 수가 글 수의 절반을 못 넘기면 —
    45편짜리 백준 목록처럼 노션에서도 원래 평평했던 곳이라 이름표만 늘고
    목록은 그대로다.
  - **닻은 경로에 마지막으로 나온 이름이다.** 같은 이름이 두 번 나오는 자리가
    실제로 있다(`네트워크 > HTTP 완벽 가이드 > HTTP 완벽 가이드 > …`) —
    분류가 된 페이지 안에 같은 이름의 인라인 데이터베이스가 또 있는 것이다.
  - **형제가 하나뿐인 층은 벗겨낸다.** 모두가 같은 첫 칸을 가지면 그 칸은
    아무것도 가르지 않고 들여쓰기만 한 칸 늘린다. 그 반복문은
    **`len(items) > 0`을 스스로 확인한다** — ①의 최소 개수 검사가 지금은 빈
    목록을 막고 있지만, 40줄 떨어진 검사에 반복문의 종료를 맡기지 않는다.
    실제로 돌연변이 시험에서 ①을 지웠더니 여기가 영원히 돌았다.
- 재귀 템플릿 `posttree`는 **layout.html에** 정의한다. 페이지마다 템플릿 집합을
  따로 파싱하는데 layout은 모든 집합에 들어가므로, 거기 둬야 category와 post
  양쪽에서 쓸 수 있다.
- **템플릿은 페이지마다 따로 파싱한다.** Go 템플릿은 이름 공간이 하나라 여러 파일을
  한 번에 파싱하면 각 파일의 `{{define "content"}}`가 서로를 덮어써서 마지막 것만
  남는다. 그러면 모든 페이지가 같은 내용을 그린다.

### 레이아웃과 색

**왼쪽 고정 사이드바 + 본문.** 사이드바는 모든 페이지에 나온다(`layout.html`).

- 트리는 **한 번의 조회**로 가져온다(`store.NavTree`). 87개뿐이라 전부 읽어
  Go에서 묶는다. 페이지마다 단계별로 세 번 찌르는 것보다 낫다.
- **최상위 8개는 늘 펼쳐진 목록**이고 그 아래(18 + 61)는 접혀 있다. 한 번에 다
  펼치면 목록이 화면보다 길어져서 지금 어디 있는지가 오히려 안 보인다.
- **지금 보고 있는 곳으로 가는 길만 서버가 펼쳐서 보낸다** (`markNav`, `nav.go`).
  펼침/현재 위치를 노드에 표시해서 넘기는 이유: Go 템플릿은 재귀할 때 dot이
  바뀌어서 바깥의 맵을 같이 넘기기가 번거롭다. 노드가 자기 상태를 들고 있으면
  템플릿은 그리기만 하면 된다.
- 그래서 **`sidebar.js`가 못 떠도 길이 막히지 않는다.** 스크립트가 더해주는 것은
  "다른 가지를 눌러 열기"와 좁은 화면의 서랍 여닫기뿐이다.
- 좁은 화면(60rem 미만)에서는 사이드바가 서랍으로 숨고 상단에 햄버거가 나온다.
  넓어지면 서랍 상태를 강제로 닫는다 — 안 그러면 scrim과 스크롤 잠금만 유령처럼
  남는다.

**본문 폭은 두 겹이다.** 산문은 `--measure`(46rem)에서 멈추고, **코드·표·블록
수식만** `--column`(62rem)까지 쓴다. 그것들은 줄바꿈이 아니라 스크롤로 감당하는
것이라 넓을수록 읽기 쉽고, 산문은 한 줄이 길어지면 눈이 되돌아오는 거리가 멀어진다.

**팔레트는 "편집숍"이다** (2026-09-01에 갈아엎었다). 흰 지면에 잉크빛
괘선(`#121415`), 라이트의 포인트는 **형광 노랑 블록**(`#FFE600`)이다.
그림자·그라데이션·둥근 모서리를 쓰지 않고 **테두리 두께로 위계를 만든다.**

- **노랑은 잉크가 아니라 지면이다.** 글자색으로 쓰면 흰 바탕에서 대비가
  1.2:1이라 읽을 수 없다. 언제나 블록으로 깔고 그 위에 검정 글자를 얹는다 —
  형광펜으로 그은 자리에 가깝다.
- **그래서 링크가 노랗지 않다.** 링크는 잉크에 가깝게(`#1F2937`) 두고
  **밑줄로 알린다.** 색을 하나만 쓰는 데서 편집숍의 절제가 나온다 —
  링크까지 색을 다투면 지면이 시끄러워진다. 대신 hover에서 노랑이 깔린다.

- **강조는 색 글자가 아니라 색 지면이다.** 사이드바의 현재 위치, 홈 표제지의
  둘째 줄, 주 버튼은 강조 블록이고 그 위 글자는 검정이다. 다크는 초록 토큰을 쓴다.
- **머리띠(반전 블록)가 이 언어의 시그니처다.** 코드 라벨·목차·표 머리·인라인
  데이터베이스·최근 글이 전부 같은 띠를 쓴다 — 상자 안에 무엇이 들었는지
  말하는 자리는 언제나 같은 모양이다.
- **허용하는 그림자는 블러 없는 오프셋뿐이다**(`--hard-shadow`). 인쇄물의
  판 어긋남이지 빛이 아니다. 갈래 카드와 외부 링크 카드의 hover가 그것이다.

- **CSS 토큰 이름은 색이 아니라 역할이다** (`--surface`, `--rail`, `--badge-bg`,
  `--mark-bg` …). `--sand`, `--sky`로 짓지 않은 이유가 이것이다. 같은 역할에
  라이트/다크의 다른 색을 매핑하고 컴포넌트 규칙은 공유한다.
- **다크는 색 반전이 아니라 판의 반전이다.** 지면이 잉크가 되고 잉크가 지면이
  되므로, **머리띠는 밝은 띠에 검정 글자**가 된다. "반전 블록"이라는 정체성이
  테마와 무관하게 유지된다.
- **포인트는 라이트에서 노랑(`#FFE600`), 다크에서 초록(`#4ADE80`)이다.**
  역할은 같은 강조 블록이며 컴포넌트는 토큰을 공유한다.
- highlight.js의 밝은 테마는 다크에서 읽히도록 토큰 색을 별도로 덮는다.
- **우측 하단 버튼이 화면 설정을 연다** (`static/preferences.js`).
  `prefs-shell`이 열리고 닫히며 현재 CSS는 각진 외곽선을 쓴다.
  - 한국어/English/Español 공통 UI는 고정 사전으로 바꾼다. 본문·제목은 브라우저의
    온디바이스 `Translator` API가 있을 때 코드·수식을 빼고 번역한다. 지원하지 않는
    브라우저에서는 조용히 성공한 척하지 않고 설정창에 지원 불가를 명시한다.
  - 테마는 시스템/화이트/다크 세 가지다. 시스템은 OS의 색상 변경 이벤트를 실시간으로
    따라가고, 명시적 테마는 고정한다. 선택은 `localStorage`에 저장한다. 저장된 테마는
    `<head>`에서 CSS보다 먼저 적용해 첫 화면이 밝게 번쩍이지 않는다.

### 코드 블록의 언어 라벨

`internal/markdown/codeblock.go`가 펜스 코드 블록을 껍데기로 감싼다:

```html
<div class="codeblock"><span class="lang">python</span><pre><code class="language-python">
```

- **브라우저가 아니라 서버가 붙인다.** 언어는 이미 본문에 적혀 있으니 JS를 기다릴
  이유가 없고, CDN이 막혀도 라벨은 남는다. highlight.js는 여전히 안쪽
  `code.language-*`만 보므로 하이라이팅은 그대로다.
- **`text`(265건)에는 라벨을 붙이지 않는다.** 그건 언어 이름이 아니라 변환기가
  "모른다"고 적어둔 값이다. 전부 `text`라고 찍으면 알려주는 것 없이 시선만 끈다.
  `plaintext`/`plain`/`txt`/`none`도 같이 뺀다. **클래스는 남긴다** —
  highlight-init.js가 그 값을 보고 "칠하지 말 것"으로 알아본다.
- 정보 문자열은 사람이 손으로 적은 것이라 무엇이든 들어온다. 라벨은 화면에 그대로
  나가므로 형태를 좁혀뒀다(소문자+숫자로 시작, 20자 이내). 안 걸리면 라벨만
  생략하고 클래스는 그대로 낸다.
- 현재 언어가 적힌 펜스 2578개 중 **2313개에 라벨이 찍히고 265개(전부 `text`)가
  빠진다.** 상위: python 548, c 440, r 423, bash 249, java 169, javascript 142,
  sql 134, cpp 71, mermaid 30.
- **들여쓰기(4칸) 코드 블록은 이제 0개다** (2026-08-21). 변환기가 코드를 언제나
  백틱 울타리로 내보내므로 결과에 4칸 들여쓰기가 나오면 그건 사고였다 —
  operations.md의 "노션 이관" 참고. 그래도 **상자(배경·테두리·가로
  스크롤)는 `.codeblock pre`가 아니라 `article pre`에 건다.** `.codeblock`은 라벨
  자리만 만들고, 껍데기 없는 `<pre>`가 다시 생기면 그때 상자가 없으면 긴 줄이
  375px 화면을 통째로 민다(실제로 472px까지 밀렸다).

### 코드 블록의 복사 버튼 (2026-08-31)

코드 블록 오른쪽 위 모서리에 아이콘만 있는 복사 버튼이 붙는다
(`internal/web/static/copy.js`). 언어 라벨과 같은 띠에 나란히 선다.

- **여기서는 서버가 안 찍고 스크립트가 만든다.** 언어 라벨과 정반대인데
  이유가 있다: 라벨은 스크립트가 없어도 읽을 수 있는 글자지만, **클립보드는
  JS 없이 쓸 수 없다.** 미리 찍어두면 스크립트가 꺼진 브라우저에 눌러도 아무
  일이 없는 죽은 버튼이 남는다. youtube.js가 누르기 전까지 그냥 링크로 있는
  것과 같은 점진적 향상이다.
- **`navigator.clipboard`는 보안 컨텍스트(HTTPS/localhost)에만 있다.** 없으면
  버튼을 아예 만들지 않는다. 못 하는 일에 버튼을 두지 않는다.
- **기준은 `<pre>`가 아니라 껍데기 `.codeblock`이다.** `article pre`에는
  `overflow-x: auto`가 걸려 있어서, 그 안에 absolute로 두면 **긴 줄을 밀 때
  버튼이 코드와 함께 흘러간다.** 껍데기는 스크롤하지 않는다. 실측으로
  확인했다 — 592px짜리 코드를 336px 창에서 끝까지 밀어도 버튼의 x가 357에서
  안 움직인다.
- **껍데기가 없는 `<pre>`는 copy.js가 씌우고 나서 단다.** `codeblock.go`는
  펜스 코드 블록만 감싸므로, 들여쓰기(4칸) 코드 블록이 다시 생기면 `<pre>`만
  홀로 나온다(현재 0개). 그때 붙일 기준이 없으면 버튼이 스크롤하는 pre 안으로
  들어간다.
- **`Assets.Copy`는 `Assets.Code`와 다른 판정이다.** Code는 "**색칠할** 것이
  있는가"라서 `text` 265건처럼 일부러 색칠을 건너뛰는 블록만 있는 글은 거짓인데
  **복사할 코드는 그대로 있다.** 그래서 언어 클래스가 아니라 `<pre>` 자체를
  센다. 실제로 갈리는 글이 있다 — `0701bd18…`은 highlight.js를 안 받고
  copy.js만 받는다.
- **`copy.js`는 `preferences.js`보다 앞에 둔다.** `defer`끼리는 순서가
  지켜지므로, 여기서 만든 버튼의 `aria-label`을 뒤이어 도는 사전이 세 언어로
  바꿔준다. `TestCopyScriptRunsBeforePreferences`가 지킨다.
- **`aria-label`은 `textContent`가 아니라 속성이다.** 상태가 바뀔 때마다
  문서 전체를 다시 훑으면 본문 번역까지 다시 돌게 되므로, `preferences.js`가
  요소 하나에 사전을 입히는 `window.blogLabel`을 열어뒀다.
- 아이콘 셋(복사/완료/실패)을 한꺼번에 넣어두고 **어느 것을 보일지는 CSS가
  정한다**(`.copy[data-state]`). JS는 `data-state` 한 글자만 바꾼다.
- **실패해도 조용히 넘어가지 않는다.** 눌렀는데 아무 표시가 없으면 복사된 줄
  안다. 실패는 `--warn`(라이트 `#B3261E`, 다크 `#F0938B`) 색의 × 표시다.
- **모바일에는 hover가 없다.** 평소에도 무엇인지 알아볼 만큼(`opacity: .68`)
  보이게 두고 hover/focus에서 또렷해진다. 전환은 위쪽의 `*` 규칙이
  `prefers-reduced-motion`에서 끈다.
- admin 미리보기도 같은 스크립트를 쓴다. `innerHTML`을 갈아치우면 버튼이 통째로
  사라지므로 `window.blogCopyButtons`를 다시 부른다 — `blogRenderMath` /
  `blogHighlight`와 같은 자리다.
- 헤드리스 브라우저로 확인했다: 29페이지 · 버튼 553개, **375px에서 문서폭이
  375를 넘는 곳 0개**, 껍데기 밖으로 나간 버튼 0개, 눌렀을 때 `<code>`
  textContent와 정확히 같은 글자가 클립보드에 들어감, aria-label이 ko/en/es로
  바뀜, 라이트·다크 모두 읽힘. **검사기가 진짜로 잡는지 먼저 봤다** — 900px
  조각을 끼우면 901px이 나온다.

### mermaid는 다이어그램으로 그린다 (2026-09-02)

### 본문 안의 바깥 링크는 카드가 된다

`internal/markdown/extlink.go`. **문단 하나가 통째로 링크일 때만** 카드다.

  중간의 링크까지 카드로 만들면 "자세한 건 [여기]를 봐라"가 상자로 끊긴다.

  되고, 나머지 46개는 글자 링크로 남는다.
- **내부 글 링크(`/p/...`)는 절대 카드가 되지 않는다.** 스킴이 있는 http(s) 절대
  주소만 본다. 이게 깨지면 본문 링크 670개가 통째로 카드가 된다.
- 두 줄을 이렇게 정한다: 캡션이 있으면 `제목=캡션 / 아래=호스트`, 없으면
  `제목=호스트 / 아래=경로`. 캡션이 없는 bookmark는 링크 글자가 URL 그대로라,
  그냥 쓰면 두 줄이 같은 말을 두 번 한다.
- **쿼리는 화면에서 버린다.** 노션이 호스팅하던 첨부파일 URL은 서명이 붙어 쿼리만
  1,500자가 넘는다. `href`에는 그대로 둔다.
- `rel="noreferrer"`를 붙인다. 우리 주소가 상대 쪽 로그에 남지 않게 하려는 것이다.
- 아이콘은 **호스트에 상관없이 같은 기본 그림**이다. 진짜 파비콘은 이관 때 받아
  DB에 넣기로 했다 — operations.md의 "남은 작업" 참고.

- 재생목록(`list`)이 붙어 있으면 같이 넘긴다. 원래 링크가 목록의 한 편을 가리키던

- `youtu.be`, `/embed/`, `/shorts/`도 같이 잡는다. id는 `[\w-]{6,64}`로 좁혀 둔다 —

### 수식은 마크다운 파서로부터 지켜야 한다

`internal/markdown/math.go`가 `$...$`와 `$$...$$`를 goldmark보다 먼저 가로챈다.
**두 파서로 나눠 맡는다.**

| 파서 | 맡는 것 | 우선순위 |
|---|---|---|
| `mathBlockParser` (블록) | 제 줄에서 시작해 다음 줄 이후에 닫히는 `$$` | 99 |
| `mathParser` (인라인) | `$...$`와 한 줄로 닫히는 `$$...$$` | 강조보다 앞 |

**블록 파서가 반드시 필요하다.** 인라인 파싱은 블록이 다 정해진 뒤에 도는데,
수식 안의 한 줄이 블록 문법으로 먼저 읽히면 문단이 쪼개져서 인라인 파서에게는
이미 조각난 것만 온다. 실제로 이렇게 깨졌다:

```
$$
a\lambda^n + \cdots + c
=
(\lambda - \lambda_1) \cdots = 0
$$
```

`=` 한 글자만 있는 줄이 **CommonMark의 setext 제목 밑줄**이라 윗줄이 h1이 된다.
`#`(제목), `-`(목록), 백틱 세 개(코드 펜스)도 같은 식으로 문단을 끊는다. 그래서
우선순위를 setext 제목(100)보다 앞인 **99**로 둔다.

- **닫는 `$$`는 빈 줄 전까지만 찾는다.** 변환기가 블록 수식 안에 빈 줄을 남기지
  않으므로(`normalizeBlockMath`) 빈 줄은 곧 "닫는 짝이 없다"는 뜻이다. 예전에는
  문서 전체에서 다음 `$$`를 찾아서, 짝이 안 맞는 `$$` 하나가 뒤의 제목과 코드
  블록을 통째로 삼켰다. 그렇게 망가진 자리가 **64개** 있었고 KaTeX를 붙이니
  드러났다. 지금은 2898개 전부 정상 렌더링되고 글자로 남는 `$$`도 0개다.
- **한 줄로 닫히는 `$$...$$`는 블록 파서가 가져가지 않는다.** 가져가면 그 줄의
  앞뒤 글자가 사라진다. 인라인 파서에게 넘긴다.
그냥 넘기면 CommonMark 규칙이 LaTeX를 먹는다:

- `\{` → `{` (백슬래시 이스케이프)
- `X_t ... _n`의 밑줄이 짝지어져 `<em>`
- `*`가 강조로

가로챈 수식은 원문 그대로 들고 있다가 `<span class="math math-inline">` /
`<div class="math math-display">`로 내보낸다. **서버에서 수식을 그리지 않는다** —
브라우저에서 KaTeX가 그린다(`internal/web/static/math.js`).

- **KaTeX의 auto-render 확장을 쓰지 않는다.** 그건 문서 전체를 훑으며 `$...$`를
  찾는데, 본문에 진짜 `$`를 쓴 글이 90개다. 서버가 이미 수식을 골라 `.math` 안에
  `$` 없이 원문만 넣어놨으므로 **그 요소만 집어서** `katex.renderToString`을 부른다.
- **성공했을 때만 넣는다.** 실패하면 원문을 그대로 두고 `.katex-failed`만 붙인다.
  `throwOnError:false`로 KaTeX에게 맡기면 못 읽은 원문을 자기가 빨갛게 그리는데,
  여기서 실패하는 건 대개 수식이 아니라 본문이 통째로 딸려 들어온 자리라
  빨간 덩어리가 되면 더 읽기 힘들다.
- CDN에 **무결성 해시(SRI)**를 건다. 버전을 올릴 때 해시도 같이 바꿔야 한다 —
  안 그러면 브라우저가 조용히 실행을 거부한다.
- 스크립트가 못 떠도 원문 LaTeX가 그대로 보인다. 빈 자리가 되지 않는다.

- 코드 블록과 코드 스팬 안에서는 goldmark가 인라인 파서를 부르지 않는다. 그래서
  R의 `data1$col`이나 Makefile 변수는 저절로 걸러진다. 실제로 `$`가 270개인
  페이지를 확인해보니 math 노드가 0개였다.

## Admin 화면

`internal/admin`은 글을 쓰고 고치는 화면이다. 화면·GitHub 인증·DB 저장은 구현되어 있다.
글감함(메모 → OpenRouter → draft, `notes.go`)도 구현되어 있다. 나머지 AI 삽입/MCP는
[운영 문서의 남은 작업](operations.md)에 있다. 배포 설정·DB 사본 절차도 그 문서를 따른다.

<a id="section-23"></a>
### 정해둔 것 (2026-08-26)

본문과 편집기의 다음 설계 결정을 유지한다.

**① 본문 정본은 계속 마크다운이다.** 노션처럼 블록 JSON을 정본으로 두는 길은
안 간다. 그러면 렌더링 파이프라인(goldmark + 수식 파서 + 코드 라벨 + 외부 링크
카드 + 제목 내리기)을 통째로 다시 써야 하고, **1357편을 마크다운 → 블록으로
되돌려야 한다** — 노션에서 마크다운으로 옮겨온 것을 다시 블록으로 옮기는 셈이다.
쓸 만한 블록 에디터는 대부분 npm/번들러를 전제해서 "빌드 스텝 없음"과도 부딪힌다.

**② ✅ 노션식 `/` 팔레트는 마크다운 위에 얹는다** (2026-08-31에 만들었다). `/`를 누르면 팔레트가 뜨고,
고르면 **마크다운 조각이 커서 자리에 꽂힌다**(코드 펜스, `$$수식$$`, 이미지, 표…).
본문 정본은 마크다운이다. `/admin`은 두 칸, 공개 화면은 블록 인라인 편집이다. 노션 느낌의 대부분은
팔레트 하나에서 오고, 그 값에 ①을 버릴 이유는 없다. 저장 기능과 함께 제공한다.

**③ ✅ 편집은 결국 공개 글 화면 안으로 들어간다** (네이버 블로그처럼, 2026-08-31에 했다). 인증되면
글 화면에 편집 버튼이 나타나고 거기서 바로 고치는 형태다. **이건 어려운 쪽이
아니다** — 이 사이트는 이미 SSR이라 `layout.html`에 세션 조건 한 줄이면 된다.
지금 `/admin`을 별도 앱으로 만든 건 인증이 없어서 격리해 둔 것이고, 2단계가
끝나면 옮길 수 있다. **1단계 결과물은 버려지지 않는다** — `/api/admin/*`와
미리보기 렌더러가 그대로 그 편집창의 뒷단이 되고, `/admin` 목록은 "글 관리
화면"으로 남는다.

**④ ✅ 애니메이션을 본문에 JS로 박지 않는다** (2026-08-31에 `:::anim`으로 만들었다). 렌더러가 `html.WithUnsafe()`라
(`internal/markdown/render.go`) 본문에 `<script>`를 쓰면 **이미 실행된다.** 그래서
"되냐"가 아니라 "그래도 되냐"가 문제다. 본문에 임의 JS를 담기 시작하면 그 글
자체가 XSS 벡터가 되고 — **4단계에서 AI가 본문을 만들기 시작하면 특히 그렇다** —
나중에 CSP를 걸 길도 막힌다. "HTML → CSS → 마지막에 JS" 원칙과도 어긋난다.
대신 **이름 붙인 컴포넌트 중에서 고르게 한다**: 본문에는 `:::anim sort-bubble`
같은 표시만 들어가고 실제 JS는 `internal/web/static/`에 사람이 쓴 파일로 있다.
본문은 안전한 텍스트로 남고, 같은 애니메이션을 여러 글에서 다시 쓸 수 있다.

**✅ 글별 메타 패널은 3단계에서 같이 만들었다.** `분류 · 계층 · 날짜`를 접어둔
`<details>` 안에 분류(select)·부모 글(slug)·형제 순서·작성일을 둔다. 아래
"3단계로 만든 것" 참고.

- **✅ 옛 글 편집 화면에 경고를 띄운다.** 노션에서 온 글은 제목·날짜·순서를
  `internal/curation`이 이기고 본문은 `import -db`가 통째로 덮는다. 웹에서 고쳐도
  **다음 재이관에 그냥 사라진다.** `PostDetail.Source`와 `Managed`가 그걸
  알려주고 편집 화면이 폼 위에 띠로 적는다.

<a id="section-24"></a>
### 패키지 경계와 API

- **`-admin` 플래그가 없으면 화면 자체가 없다.** 활성화한 경우 GitHub 인증과 허용 목록을 적용한다.
  배포는 `/etc/blog/admin.env`의 `BLOG_ADMIN_FLAG`로 켠다.
- **`internal/web`과 다른 패키지다.** web은 "읽기 전용 공개 페이지"고 draft를
  어디에도 안 보여주는 것이 그쪽 규칙인데(`notHidden`), admin은 반대로 **draft가
  주인공**이다. 한 패키지에서 플래그로 가르면 언젠가 공개 쪽에 샌다.
- **붙이는 방법은 바깥 mux 하나다** (`cmd/blog`의 `withAdmin`). 공개 mux에는
  `GET /` catch-all이 있어서 같은 mux에 넣으면 두 패키지가 라우팅을 나눠 갖게 된다.
  ServeMux가 더 구체적인 패턴을 먼저 고르므로 `/admin/`이 `/`를 이긴다.

| 라우트 | 하는 일 |
|---|---|
| `GET /admin`, `GET /admin/{rest...}` | 껍데기 하나. 안은 `admin.js`가 그린다 |
| `GET /admin/static/{file}` | admin 전용 JS·CSS |
| `GET /api/admin/posts` | 목록 (**draft 포함**, 본문은 안 싣는다) |
| `GET /api/admin/posts/{slug}` | 글 하나 + 본문 |
| `POST /api/admin/preview` | 마크다운 → HTML (실시간 미리보기) |
| `GET /api/admin/categories` | 메타 패널의 분류 선택지 (경로까지 만들어서) |
| `POST /api/admin/posts` | 새 글. 201 + 저장된 글 |
| `PUT /api/admin/posts/{slug}` | 고치기. `{slug}`는 **지금의** slug다 |
| `POST /api/admin/images` | 이미지 저장. sha256으로 dedup |
| `GET /api/admin/posts/{slug}/refs` | 지우면 무엇을 잃는지 |
| `DELETE /api/admin/posts/{slug}` | 글 지우기. rev와 확인이 필요하다 |
| `GET /api/admin/posts/{slug}/siblings` | 공개 화면의 형제 순서 |
| `POST /api/admin/blocks` | 블록 분할과 렌더링 |
| `GET` / `PUT /api/admin/settings` | 홈 설정 읽기·변경 |
| `GET /api/admin/stats` | 콘텐츠 통계 |

<a id="section-25"></a>
### 미리보기가 실제 화면과 같아야 한다

이게 이 단계의 핵심이다. 미리보기가 발행 뒤 화면과 다르면 미리보기가 아니다.
그래서 **세 가지를 복사하지 않고 공개 쪽에서 가져다 쓴다.**

| 무엇 | 어디서 | 왜 |
|---|---|---|
| 마크다운 렌더러 | `markdown.New()` | 수식·코드 라벨·외부 링크 카드·제목 내리기가 전부 그 안에 있다 |
| 스타일시트 | `web.SiteCSS()` | `layout.html`의 `{{define "sitecss"}}`를 그대로 뽑아온다 |
| CDN 태그 | `web.PreviewAssetTags()` | `{{define "katex-cdn"}}` / `{{define "hljs-cdn"}}` |

- **`layout.html`에서 CSS와 CDN 태그를 이름 붙은 템플릿으로 떼어냈다.**
  이름만 붙였을 뿐이라 **공개 페이지의 출력은 한 바이트도 안 바뀐다**(표본
  43페이지로 확인했다). 정본이 한 곳이라 admin과 공개 화면이 갈라질 수 없다.
- **CDN 태그를 특히 복사하면 안 되는 이유는 SRI 해시다.** 주소와 버전만 베끼고
  해시를 안 맞추면 브라우저가 **아무 말 없이** 실행을 거부한다. 실제로 이 작업 중에
  해시를 잘못 적었다가 layout에서 뽑아 쓰는 쪽으로 고쳤다.
- **`static/math.js`와 `static/highlight-init.js`도 공개 것을 그대로 쓴다.**
  미리보기는 본문을 계속 다시 그리므로 그때마다 다시 불러야 하는데, 두 스크립트가
  자기 함수를 `window.blogRenderMath` / `window.blogHighlight`로 열어둔다.
  자동 실행은 그대로다 — 공개 페이지 동작은 안 바뀐다.
- **아직 다른 점 하나:** 실제 글 화면은 렌더링 직전에 죽은 링크를 손본다
  (`web`의 `resolveBody` — `[페이지 링크]` 자리표시자와 인라인 DB 펼치기).
  그건 노션에서 온 본문에만 해당하고 DB 조회가 필요해서 미리보기에서는 안 한다.
  **새로 쓰는 글에는 그런 링크가 없으므로 지금은 차이가 없다.** 옛 글을 admin에서
  열었을 때만 그만큼 다르다.
- 공개 페이지는 본문을 보고 필요할 때만 CDN을 받지만(`assets.go`) admin은 늘 받는다.
  작업 도구라 무엇을 칠지 미리 알 수 없다. 다만 common 묶음 밖의 언어
  (latex·dockerfile·powershell)는 아직 안 받아서 미리보기에서만 색이 없다.

<a id="section-26"></a>
### 성공한 척하지 않는다

1단계에서 저장과 업로드는 501을 줬다. **그 띠가 사라지는 시점이 곧 3단계가
끝난 시점**이라고 적어뒀고, 2026-08-31에 사라졌다. 남은 띠는 `-admin-no-auth`로
떴을 때의 경고 하나뿐이다.

**원칙은 그대로 뒤집혀 남는다: 실패를 숨기지 않듯 성공도 삼키지 않는다.**
새 글을 저장하면 주소가 바뀌면서 폼을 다시 그리는데, 그때 "저장했다"가 같이
지워지면 사람은 저장이 됐는지 알 수 없다. 다시 그리는 폼에 그 말을 넘긴다
(`renderEditor`의 `note`). **실제로 그렇게 지워지던 것을 브라우저에서 보고
고쳤다.**

<a id="section-27"></a>
### 2단계로 만든 것 — GitHub 로그인 (`internal/admin/auth.go`)

**허용 목록에 적은 GitHub 계정 말고는 아무도 못 들어온다.**

- **OAuth는 "누구인지"만 알려준다. "들어와도 되는지"는 우리가 정한다.**
  GitHub 계정은 누구나 몇 초면 만드니까, 로그인에 성공했다는 것만으로 통과시키면
  인증이 없는 것과 같다. `allows()`가 진짜 관문이고,
  **`AllowedLogins`가 비면 "전부 허용"이 아니라 "전부 차단"이다** — 설정을
  빠뜨렸을 때 열리는 쪽으로 틀리는 것이 여기서 제일 위험한 실수다.
- **비밀번호를 우리가 들고 있지 않는다.** 사용자 테이블도 비밀번호 해시도 없고
  앞으로도 만들 이유가 없다.

**세션은 서명한 쿠키 하나다.** 세션 테이블을 안 만든다 — 마이그레이션이 늘고,
지우는 마이그레이션을 안 만든다는 원칙 때문에 나중에 물리기도 어렵다. 대신
`login|만료`를 HMAC-SHA256으로 서명해 쿠키에 담는다.

- `HttpOnly` — 본문 렌더러가 `html.WithUnsafe()`라 본문에 들어온 스크립트가
  실행될 수 있다. 그때 세션까지 가져가면 안 된다.
- `SameSite=Lax`, 만료 12시간. 훔쳐간 쿠키를 서버에서 끊을 방법이 없어서 짧다.
- **`Secure`는 HTTPS로 온 요청에 붙인다.** 운영은 Caddy가 전달하는
  `X-Forwarded-Proto`를 사용한다. 로컬 평문 접속과 운영 HTTPS를 구분한다.
- **서명이 맞아도 허용 목록을 다시 본다.** 설정에서 계정을 빼면 살아 있는 쿠키도
  그 순간부터 안 통해야 하는데, 세션 테이블이 없어서 취소할 길이 이것뿐이다.
- `BLOG_SESSION_KEY`를 안 주면 시작할 때 무작위로 만든다. 재시작하면 다시
  로그인해야 하지만, 키를 저장소나 유닛 파일에 적어두는 것보다 낫다.

| 라우트 | 하는 일 |
|---|---|
| `GET /admin/login` | 로그인 화면. **관문 밖이다** |
| `GET /admin/auth/start` | state를 심고 GitHub으로 보낸다 |
| `GET /admin/auth/callback` | code → 토큰 → login → 허용 목록 대조 |
| `POST /admin/logout` | 세션 쿠키를 지운다 |

- **관문(`guard`)은 mux보다 바깥이다.** 핸들러마다 챙기게 하면 새 API를 더할
  때마다 구멍이 하나씩 생긴다 — web이 draft 판정을 `store` 한 곳에 모은 것과
  같은 이유다. `openPaths`에 없는 `/admin`·`/api/admin`은 **전부 막힌다**.
- **API에는 로그인 화면을 주지 않는다.** `fetch()`가 받는 자리라 HTML이 오면
  JSON 파싱에서 터지고 "로그인이 풀렸다"는 진짜 이유가 가려진다. 401 JSON이다.
- **`state`는 CSRF 방지다.** 없으면 남이 자기 code로 우리 callback을 부르게
  만들어서 브라우저 주인이 모르는 사이에 **남의 계정으로 로그인시킬** 수 있다.
  쿠키 path가 `/admin`이라 **지울 때도 같은 path를 줘야 한다** — 다르면 안
  지워지고 같은 이름이 두 개가 된다.
- **로그아웃은 POST다.** GET이면 남의 페이지에 박아둔 `<img>` 하나로도 사람을
  로그아웃시킬 수 있다.
- **`redirect_uri`를 우리가 만들어 보내지 않는다.** GitHub이 OAuth 앱에 등록된
  주소를 쓴다. 조립하는 자리를 만드는 것 자체가 위험하고 등록된 것과 어긋나기도 쉽다.
- `scope`는 비운다. 알아야 할 것이 `login` 하나뿐이라 저장소나 이메일 권한을
  달라고 할 이유가 없다.
- 거절당한 계정 이름은 **로그에만** 남기고 화면에 도로 찍지 않는다. 남이 지은
  이름이 우리 화면에 나오는 자리를 만들지 않는다.

**설정은 환경변수로 받는다. 플래그로 받지 않는다** — client secret이 플래그면
`ps`에 그대로 보이고 셸 히스토리에도 남는다.

| 환경변수 | 뜻 |
|---|---|
| `BLOG_GITHUB_CLIENT_ID` | OAuth 앱의 client id |
| `BLOG_GITHUB_CLIENT_SECRET` | 〃 secret |
| `BLOG_ADMIN_LOGINS` | 허용할 GitHub login (쉼표로 여럿) |
| `BLOG_SESSION_KEY` | 세션 서명 키. 없으면 무작위. **32바이트 이상** |

**애매하면 안 뜬다** (`cmd/blog`의 `adminAuth`). 인증이 반쯤 설정된 채로 서버가
뜨는 것이 여기서 제일 나쁜 결과라, 모자라면 `log.Fatal`이다.

- `-admin`인데 설정이 모자라면 → **안 뜬다.** 무엇이 없는지 이름으로 알려준다.
- 인증 없이 여는 길은 **`-admin-no-auth` 하나뿐이고 loopback에서만 된다.**
  `-addr`이 밖에서 닿는 주소면 안 뜬다. **`:8080`은 loopback이 아니다** —
  모든 인터페이스에 붙는다는 뜻이라 여기서 틀리면 그대로 공개된다.
- 설정과 `-admin-no-auth`를 **같이 주면 거절한다.** 사람이 무엇을 원하는지 알 수
  없는 상태고, 조용히 인증을 끄는 쪽으로 고르면 그게 사고다.
- 이름을 길게 지은 것도 일부러다. **위험한 것은 이름이 위험해야 한다.**

**테스트는 가짜 GitHub을 `httptest`로 세워 네트워크 없이 전체 흐름을 돈다.**
진짜 GitHub을 부르면 남의 서비스에 매달리고, 무엇보다 "거절당하는 계정" 같은
경우를 만들 수가 없다. 돌연변이 셋을 넣어 테스트가 **실제로 실패하는 것**을
확인했다: `allows()`가 늘 통과, `guard`를 뺌, `":8080"`을 loopback으로 침.

<a id="section-28"></a>
### 3단계로 만든 것 — 저장 (2026-08-31)

**글이 실제로 DB에 들어간다.** `internal/admin/save.go`·`upload.go`·`csrf.go`.

#### 새 글에는 `notion_page_id`를 넣지 않는다

새 글은 `source = native`, `notion_page_id = NULL`로 저장한다.
GitHub 글도 notion ID가 NULL이므로 native 판정에는 source를 사용한다.
업로드 가드의 현재 조건은 [운영 문서](operations.md)와 `deploy/upload-guard.sql`을 따른다.

#### 덮어쓰기를 막는 표 (`rev`)

**두 탭에서 같은 글을 열어 각각 저장하면 나중 것이 앞의 것을 통째로 지운다.**
그게 조용히 일어나는 것이 문제다. 그래서 불러올 때 준 `updated_at` 글자를
저장할 때 그대로 돌려받아 DB의 지금 값과 견준다. 다르면 409다.

- **`rev`가 비어 있어도 거절한다.** 검사를 건너뛰는 쪽으로 틀리지 않는다.
- **`time.Time`이 아니라 글자 그대로 주고받는다.** JSON 왕복에서 정밀도가
  깎이면 멀쩡한 저장이 거절당한다.
- **저장 응답에 새 `rev`를 실어 보낸다.** 안 주면 두 번째 저장이 늘
  "그새 바뀌었다"로 거절당한다.

#### PUT은 부분 갱신이 아니라 통째로 바꾸기다

안 보낸 칸은 "그대로 두라"가 아니라 "비우라"로 읽는다. 부분 갱신으로 두면
"이 칸을 지우고 싶다"와 "이 칸은 안 건드린다"를 JSON으로 구별할 수 없고,
그 모호함은 결국 사람이 지운 줄 안 값이 남는 쪽으로 끝난다.

**단 `published_at`은 요청에 아예 없다.** 사람이 적는 값이 아니라 status가
**처음** published가 되는 순간 서버가 찍는 값이다. 받아주면 두 곳에서 정해지고,
저장할 때마다 갱신하면 "언제 공개했나"가 "마지막으로 저장한 때"가 된다.

#### slug를 바꾸면 그 글을 가리키는 링크도 같이 바꾼다

운영 문서의 "내부 링크" 절이 요구하던 것이다. relink가 모든 내부 링크를
`](/p/{slug})` 한 형태로 맞춰뒀으므로 닫는 괄호까지 붙여 정확히 짝지어
같은 트랜잭션에서 바꾼다. 안 하면 다른 글 몇 편이 **조용히 404를 가리킨다.**

- slug에는 `%`도 `_`도 들어갈 수 없어서(Slugify가 걸러낸다) LIKE가 안전하다.
- `PUT /api/admin/posts/{slug}`의 `{slug}`는 **지금의** slug이고 본문의
  `slug`는 **바꾸고 싶은** slug다. 둘이 다른 경우가 곧 이름 바꾸기다.

#### slug 규칙은 카테고리와 같은 함수가 정한다

`importer.Slugify(s) == s`면 쓸 수 있는 형태다. 규칙을 admin에 다시 적으면
카테고리 slug와 언젠가 갈라진다.

**그래서 한글이 그대로 남는다.** 스키마 주석은 "영문 소문자 + 하이픈"이라고
적혀 있지만 **카테고리 slug는 이미 한글을 쓰고 그 주소가 배포되어 있다**
(`/data-math/수리-통계-이론/선형대수`). 글만 로마자로 강제하면 같은 사이트
안에서 주소 규칙이 두 벌이 되고, 한국어 제목에서 slug를 만들 길이 없어진다.
`slug를 비우면 제목에서 만든다` — `"웹에서 쓴 글"` → `웹에서-쓴-글`.

#### 부모 사슬이 도는 것은 여기서 막는다

**`posts.parent_id`에는 `categories`와 달리 깊이·순환을 막는 트리거가 없다**
(002는 categories만 지킨다). 도는 사슬을 한 번 만들면 `nestPosts`와
`PostAncestors`가 각자 방어해야 하고 `cmd/postparent`도 같은 검사를 자기
쪽에서 한다. 저장할 때 막는 것이 가장 싸다.

부모는 id가 아니라 **slug로 주고받는다.** 사람이 화면에서 알아볼 수 있는
값이어야 잘못 붙였을 때 눈에 띈다.

#### 이미지: 멱등 키는 파일 이름이 아니라 내용의 sha256

`cmd/import`가 445개를 넣을 때 쓴 규칙과 같다. 같은 그림을 두 번 올려도 행이
늘지 않고, 이름을 바꿔 올려도 새 그림이 되지 않는다. 있는 행은 덮지 않는다 —
`caption`·`original_url`처럼 이관이 채워둔 칸을 지울 이유가 없다.

- **SVG는 안 받는다.** `/img/{sha256}`이 `images.mime`을 그대로 Content-Type에
  실어 보내는데, `image/svg+xml`은 브라우저가 문서로 열고 그 안의 `<script>`가
  **우리 도메인에서** 실행된다. 그림 하나 올리는 일이 사이트 전체에 대한 XSS가
  된다. png·jpeg·gif·webp만이다.
- **형식은 내용을 보고 정한다**(`http.DetectContentType`). 브라우저가 보낸
  Content-Type도 확장자도 올리는 쪽이 마음대로 적는 값이라, 믿고 `images.mime`에
  넣으면 그 값이 그대로 응답 헤더가 된다. HTML에 `.png` 이름표만 붙인 것이
  실제로 걸러지는 것을 테스트가 확인한다.
- **크기는 아는 만큼만 적는다.** webp는 표준 라이브러리가 못 읽어서 NULL이다.
  없는 값을 0으로 적으면 "가로 0픽셀"이 되어 뒤에 읽는 쪽을 속인다.
- **본문에 꽂을 마크다운은 서버가 만들어 보낸다.** 화면과 서버 두 곳에 규칙을
  두면 언젠가 갈라진다. alt는 비운다 — 파일 이름을 넣으면 `IMG_4821.png`가
  화면 낭독기에 읽힌다.
- **커서 자리에 끼운다.** 쓰던 자리에서 올렸는데 글 맨 끝에 생기면 다시 옮겨야 한다.
- **여기서만 읽기 마감을 미룬다**(`http.NewResponseController`). 서버 전체의
  `ReadTimeout`은 15초인데 8MB 업로드에는 초당 546KB가 필요하다. 서버 값을
  늘리면 **공개 GET의 방어까지** 헐거워지므로 이 요청 하나만 2분으로 늘린다.
  헤더 단계(`ReadHeaderTimeout` 5초)는 그대로라 느린 연결 공격은 거기서 막힌다.

#### 쓰기에는 관문이 하나 더 있다 (`csrf.go`)

세션 쿠키가 `SameSite=Lax`라 남의 페이지에서 보낸 POST에는 안 붙는다. 그래서
지금도 실제로는 막힌다 — **다만 그건 브라우저가 막아주는 것이다.** 서버가
자기 눈으로도 봐야 한다.

`Origin` 헤더 하나를 본다. 일반적인 브라우저 요청의 출처를 검증하며,
이 API는 Origin이 없는 쓰기 요청도 거부한다.

| | |
|---|---|
| Origin이 있고 우리 것 | 통과 |
| Origin이 있고 남의 것 | 403 |
| **Origin이 없음** | **403** |

- **없으면 막는다.** 통과시키면 검사 전체가 "헤더를 빼면 그만"이 된다.
  스크립트로 부를 일이 생기면 그때는 세션이 아니라 토큰을 쓸 자리다.
- **GET/HEAD는 안 본다.** 상태를 안 바꾸고, 남의 페이지가 응답을 읽는 것은
  CORS가 막는다. 여기서 GET까지 막으면 로그인 화면조차 못 연다.
- **관문(`guard`)보다 안쪽이다.** 로그인하지 않은 요청의 진짜 이유는 "출처가
  다르다"가 아니라 "로그인이 필요하다"이고, CSRF는 살아 있는 세션을 지키는
  장치라 세션이 있을 때 의미가 있다. 순서를 바꾸면 401이 403이 된다.
- 거절 사유에 **남이 보낸 값을 되찍지 않는다.** 거절당한 GitHub 계정 이름을
  화면에 안 찍는 것과 같은 이유다.

<a id="section-29"></a>
### 글 지우기 (2026-08-31)

**이 프로젝트는 원래 글을 지우지 않는다.** 공개 여부는 삭제가 아니라 status로
가리고(`draft`), 노션에서 온 글을 빼는 것은 `curation.DropPosts`에 적는 일이다.
그 원칙은 그대로다.

여기가 필요한 이유는 **웹에서 잘못 만든 글**이다. 저장이 붙은 뒤로 오타 하나로
생긴 빈 글이 남을 수 있는데, 치우는 길이 DB를 직접 여는 것뿐이면
"DB를 손으로 고치지 마라"는 원칙과 정면으로 부딪힌다.

**그래서 지우는 것보다 "말해주는 것"이 이 기능의 일이다** (`delete.go`).
누르기 전에 `GET /api/admin/posts/{slug}/refs`가 무엇이 걸리는지 먼저 알려준다.

| 무엇 | 어떻게 |
|---|---|
| 자식이 있다 | **아예 막는다.** force로도 안 된다 |
| 분류의 표지다 | 알려주고, 확인하면 표지를 잃는다(`ON DELETE SET NULL`) |
| 노션에서 왔다 | 알려준다 — **다음 `import -db`가 되살린다** |
| 가리키는 링크가 있다 | 같은 트랜잭션에서 **글자로 푼다** |

- **링크를 반드시 풀어야 한다.** 안 풀면 그 링크의 대상이 "posts에 없는 slug"가
  되는데, `resolveBody`는 그걸 **노션 인라인 데이터베이스로 판정한다**
  (위 "공개 서버"의 `②`). 죽은 링크가 남는 데서 그치지 않고 **엉뚱한 목록이
  펼쳐질 수 있다.** 링크를 통째로 지우지 않고 글자만 남기는 것은 공개 쪽
  `unlinkHidden`과 같다 — 줄째 지우면 문장이 끊긴다.
- **SQLite에는 정규식이 없어서** 푸는 일은 Go에서 한다. 한 글을 가리키는 링크는
  많아야 몇 편이라 통째로 읽어도 된다. **정규식이 못 잡은 것이 남으면 멈춘다** —
  중첩 대괄호 같은 모양을 조용히 넘기면 죽은 링크가 남는다.
- 저장과 같은 `rev` 표를 쓴다. 목록에서 본 그 글이 맞는지 확인하지 않으면
  다른 탭이 고친 글을 모르고 지운다.
- **잃을 것이 없으면 확인을 두 번 묻지 않는다.** 잘못 만든 빈 글을 치우는 것이
  본래 쓰임이라, 거기에 확인 창을 겹쳐두면 매번 무심코 누르게 된다.
- 돌연변이 5종(자식 있어도 지움 / 확인 없이 지움 / 링크 안 풂 / 링크를 글자
  대신 통째로 지움 / rev 건너뜀)을 넣어 테스트가 실제로 실패하는 것을 확인했다.

<a id="section-30"></a>
### `/` 조각 팔레트 (2026-08-31)

본문 칸에서 `/`를 치면 조각 목록이 뜬다(`internal/web/static/palette.js`).
고르면 **마크다운 조각이 커서 자리에 꽂힌다** — WYSIWYG가 아니라 지금처럼
마크다운 원문을 편집한다. 정본이 계속 마크다운인 이유는 "정해둔 것 ①"에 있다.

- **서버에 묻지 않는다.** 목록이 그 파일 안에 다 있고 거르는 것은 부분 일치
  하나다. `/`를 친 순간과 목록이 뜨는 순간 사이에 네트워크가 끼면 그 지연은
  절대 감출 수 없다 — 미리보기(120ms 디바운스)와 정반대의 요구다.
  실측 **8.2ms**, 네트워크 요청 0건이다.
- **줄 처음이나 공백 뒤의 `/`만 본다.** 안 그러면 `https://`나 경로를 칠 때마다
  팔레트가 튀어나온다.
- 캐럿 좌표는 **거울 div**로 잰다. 텍스트에어리어에는 캐럿 위치를 알려주는
  API가 없어서 같은 글꼴·같은 폭의 숨은 div에 커서 앞까지를 복사하고 그 끝을
  잰다. 아래로 넘치면 커서 위로 올린다.
- 항목은 20개다: 제목·목록·인용·구분선, 수식(인라인/블록), 코드 6가지,
  표, 애니메이션 2가지, 접기, 링크, **이미지 올리기**.
  - **"이미지 올리기"만 조각을 꽂지 않는다.** 파일 고르는 창을 열고, 올린 뒤에
    서버가 준 마크다운이 커서 자리에 들어간다.
  - 검색어는 한국어와 영어를 함께 단다(`/수식`도 `/math`도 `/katex`도 걸린다).
    **초성 검색 같은 것은 안 한다** — 목록이 스무 줄이라 그럴 값이 없고,
    규칙이 늘면 예측이 어려워진다.
- **`internal/web/static`에 둔다.** admin 편집기와 공개 화면의 바로 고치기가
  같은 팔레트를 쓴다 — 두 벌로 두면 반드시 갈라진다.

<a id="section-31"></a>
### 이름 붙인 애니메이션 (2026-08-31)

본문에 `:::anim sort-bubble` 한 줄을 쓰면 그 자리가 애니메이션이 된다
(`internal/markdown/anim.go` + `internal/web/static/anim.js`).

**"정해둔 것 ④"를 그대로 구현한 것이다.** 렌더러가 `html.WithUnsafe()`라
본문에 `<script>`를 쓰면 **이미 실행된다.** 그래서 "되냐"가 아니라 "그래도
되냐"가 문제다. 본문에 임의 JS를 담기 시작하면 그 글 자체가 XSS 벡터가 되고 —
4단계에서 AI가 본문을 만들기 시작하면 특히 그렇다 — 나중에 CSP를 걸 길도 막힌다.

- **본문에는 이름만 들어간다.** 실제 JS는 `anim.js`에 사람이 쓴 파일로 있고,
  새 애니메이션을 더할 때 손대는 곳은 `COMPONENTS` 한 줄과 그 함수 하나다.
  등록 예시는 `sort-bubble`(버블 정렬), `binary-search`(이진 탐색),
  `joint-probability`(결합확률)다. 전체 이름은 COMPONENTS를 확인한다.
- **이름 형태를 좁혀뒀다**(`^[a-z][a-z0-9-]{0,40}$`). HTML 속성값으로 그대로
  나가는 값이다. **안 맞으면 지시로 안 받아준다** — 그 줄이 평범한 문단으로
  남아 글자 그대로 보인다. 조용히 사라지는 것보다 낫다.
- **한 줄짜리다.** 닫는 `:::`을 요구하지 않는다. 지금 넣을 것이 이름뿐이라
  여는 줄과 닫는 줄 사이가 늘 비고, 빈 껍데기를 요구하면 자꾸 빠뜨린다.
- **`PeekLine`은 개행을 붙여 준다.** Go의 `$`는 (멀티라인이 아니면) 마지막
  개행 **앞**에서 맞지 않는다 — Perl과 다른 점이고 여기서 실제로 한 번 걸렸다.
  줄 끝을 떼고 견준다.
- 스크립트가 없으면 **빈 자리를 남기지 않는다.** 서버가 "애니메이션 {이름} —
  스크립트가 있어야 움직인다"를 적어두고 anim.js가 그 자리를 대신 채운다.
  **모르는 이름도 조용히 넘기지 않는다** — "그런 애니메이션이 없다: nope".
- **계산과 그리기를 나눈다.** 걸음을 미리 다 만들어 두고 하나씩 보여줘서
  "한 걸음씩"과 "자동 재생"이 같은 목록을 쓰고 되감기도 공짜다.
- **`joint-probability`는 죽은 apption.co 임베드를 대신한다** (2026-09-02).
  `1. 확률`의 조건부확률 절은 "노란색 부분을 결합확률, 초록색 부분을 주변확률"
  이라고 설명하는데 정작 볼 그림이 없었다 — 그 자리의 임베드가 이미 죽어 있었다.
  - **눈높이 둘을 버튼으로 오간다.** 기본은 위에서 내려다보기(표처럼 읽힌다)고,
    누르면 오른쪽 위에서 비스듬히 본 3D 막대가 된다(높이가 곧 확률이다).
  - **등각투상을 직접 계산한다.** 막대 하나가 윗면·왼면·오른면 세 다각형이고,
    `i+j`가 작은 것부터 그려 앞 막대가 뒤를 가린다(화가 알고리즘).
  - **노란색은 결합확률, 초록색은 주변확률이다.** 본문이 바로 아래에서 그
    두 색을 **글자로 부르기 때문**에, 이 그림만은 색을 둘 쓴다. 처음에는
    포인트 한 색으로 칠했는데 그러면 무엇이 결합이고 무엇이 주변인지 구별이
    안 되고 그 두 문장이 그림과 어긋난다.
  - **칸마다 흰 바탕을 먼저 깐다.** 진하기로 크기를 나타내는데 그냥 투명하게
    두면 다크에서 옅은 칸이 검게 가라앉아 그 위의 검정 숫자가 안 보인다.
    노랑·초록은 검정 글자를 얹는 지면이라 어느 테마에서든 밝은 바탕 위에
    있어야 한다.
  - **3D 면은 불투명한 세 단계다.** `fill-opacity`로 명암을 만들면 바닥
    격자와 뒤 막대가 비쳐 입체가 아니라 유리 덩어리로 보인다.
  - **결합 막대와 주변 막대를 한 목록에 담아 함께 정렬한다.** 노란 막대를
    다 그린 뒤 초록 막대를 그리면, 뒤에 있어야 할 초록이 앞의 노랑을 덮는다 —
    깊이는 종류가 아니라 자리가 정한다.
  - **같은 대각선(`i-j`가 같은) 칸은 화면에서 x가 똑같다.** 그래서 그 칸들의
    숫자 라벨은 세로로만 갈리는데, 높이 차이가 깊이 차이를 지우면 겹친다 —
    실제로 두 라벨이 14px까지 붙었다. 깊이 간격을 키우고 높이 배율을 줄여
    최소 간격을 32px로 벌렸고, **라벨은 막대를 다 그린 뒤 한 번 더 돌아서**
    앞 막대가 뒤 라벨을 덮지 않게 했다.
  - 칸을 누르면 그 칸의 행과 열만 남고 나머지가 물러난다 — 조건부확률이
    "그 줄만 떼어 다시 1로 만든 것"이라는 게 눈에 보여야 한다.
  - SVG `viewBox`라 폭에 맞춰 저절로 줄어든다. 모바일·태블릿·PC를 따로 손보지
    않았고, 넘치면 페이지가 아니라 그 상자가 가로로 스크롤한다.
- `prefers-reduced-motion: reduce`면 **저절로 움직이지 않는다.** 버튼은
  그대로라 보고 싶은 사람은 한 걸음씩 볼 수 있다.
- `Assets.Anim`이 있는 페이지에만 `anim.js`를 받는다.

### 블록 인라인 편집 (2026-09-08)

**글 화면의 `고치기`가 두 칸에서 한 칸이 됐다.** 평소에는 완성된 화면만 보이고,
문단을 누르면 그 문단만 원문이 되고, 벗어나면 곧바로 다시 그려진다.
**노션이 실제로 하는 것이 이 방식이다** — 노션도 고르는 블록만 원문을 보여준다.

- **`/admin` 편집기는 두 칸 그대로다.** 새 방식이 안 맞으면 그리로 가면 되고,
  되돌리는 것도 커밋 하나다. 큰 것을 바꿀 때 물러설 자리를 함께 둔다.
- **왜 WYSIWYG가 아닌가.** 노션처럼 블록 JSON을 정본으로 두는 길은 "정해둔
  것 ①"과 정면으로 부딪힌다(1,252편을 되돌려야 한다). 마크다운 위에 얹는
  라이브 프리뷰(CodeMirror 등)는 **그 라이브러리의 파서가 그린다** — 우리
  확장(수식·코드 라벨·외부 링크 카드·제목 내리기·유튜브)을 모르므로
  편집기에서 본 것과 발행 뒤 화면이 갈린다. 그건 미리보기가 미리보기가
  아니게 되는 일이고, 두 칸으로 나눠 두었던 이유 자체였다.
- **서버가 자르고 서버가 그린다**(`POST /api/admin/blocks`). 브라우저에서
  흉내 내면 위와 같은 문제가 그대로 생긴다 — 미리보기가 렌더러·CSS·CDN
  태그를 공개 쪽에서 그대로 가져다 쓰는 것과 같은 규칙이다.

**자르는 규칙은 `markdown.SplitBlocks`에 있다.** 계약은 하나다 —
**잘라서 `\n\n`으로 다시 이어 붙이면 같은 화면이 나온다.** 저장이 언제나 이어
붙인 문자열을 보내므로, 이게 깨지면 **글을 열었다 닫기만 해도 본문이 달라진다.**

- 빈 줄로 자르되 **한 덩어리로 다뤄야 하는 것은 안 자른다**: 코드 울타리
  (닫는 줄이 없으면 끝까지), 제 자리에 선 `$$` 블록, 항목 사이가 빈 목록.
- **문단 한가운데의 `$$`에서는 안 끊는다.** 거기서 끊으면 한 문단이 셋으로
  갈리는데 원문에서는 문단 안의 수식이라 화면이 달라진다 — 테스트가 잡았다.
- **제목은 언제나 혼자 선다.** 아래 문단과 붙여두면 제목을 고치려고 눌렀을 때
  본문까지 통째로 원문이 된다.
- **실제 글 1,252편 · 블록 23,032개로 확인했다** — 잘라 이어 붙인 것의 화면이
  전부 원문과 같다. 갈린 자리 23편은 **전부 문서 끝의 빈 줄 하나**였고,
  그래서 `bodyText()`가 끝에 줄바꿈 하나를 둔다. 안 두면 글을 열었다 저장하기만
  해도 마지막 줄이 달라져 **"안 고쳤는데 바뀐 글"**이 생긴다.

**화면에서 정한 것들.**

- **누를 수 있다는 표시는 왼쪽 띠 하나다.** 바탕색을 깔면 그 문단이 본문에서
  어떻게 보일지가 가려진다 — 여기 보이는 것이 곧 발행될 화면이라는 것이 이
  방식의 전부다.
- **빈 줄을 넣으면 문단이 갈린다.** 마크다운의 규칙 그대로라 따로 배울 것이
  없다. 그래서 서버가 돌려준 개수를 그대로 받는다(하나가 여럿이 될 수 있다).
- **내용을 다 지우면 그 문단이 없어진다.**
- **맨 아래 `+ 여기에 이어 쓰기`**가 있다. 빈 문서에도 쓸 자리가 있어야 하고,
  글 끝에 덧붙이는 것이 가장 흔한 일이다.
- **편집 중에는 링크를 안 따라간다.** 지금 하려는 일은 읽기가 아니라 고치기다.
- **Escape로 문단을 닫는다.** 마우스를 안 쓰고도 빠져나올 길이 있어야 한다.
- **수식 상자가 여기서 값이 가장 크다** — 옆에 미리보기가 없으니 수식만은
  다른 길로 보여줘야 한다(아래 절).
- 못 그리면 원문을 그대로 둔다. 반쯤 그린 것을 남기지 않는다.
- 확인한 것: 문단 29개를 전부 열었다 닫고 저장해도 **한 글자도 안 바뀌고**,
  고친 문단만 제자리에서 다시 그려지고, 390px에서 문서폭이 안 넘치고,
  빈 글에서도 쓸 자리가 있고, `/admin`의 두 칸은 그대로다.

### 커서 위의 수식 상자 (2026-09-08)

**커서가 `$…$`나 `$$…$$` 안에 들어가면 그 자리 바로 위에 그린 수식이 뜬다**
(`internal/web/static/math-live.js`). 노션이 수식만 따로 상자를 띄우는 것과
같은 자리다.

- **왜 수식만인가.** 왼쪽 마크다운·오른쪽 미리보기로 대부분은 충분한데
  수식만은 다르다 — `\dfrac{\partial}{\partial x}`는 글자로 봐서는 맞게
  썼는지 알 수 없고, 오른쪽까지 눈을 옮겨 찾는 사이에 어디를 고치고 있었는지
  놓친다.
- **서버에 안 묻는다.** KaTeX가 이미 그 페이지에 있어서 치는 즉시 그린다 —
  미리보기는 왕복이 있어 못 하는 일이다(`/` 팔레트와 같은 판단).
- **안 되는 동안에는 안 된다고 적는다.** 쓰는 도중에는 미완성이 정상이라
  실패가 잦은데, 조용히 옛 그림을 남겨두면 **다 고친 줄 알고 넘어간다.**
  되는 순간 그림으로 바뀌는 것이 곧 "이제 맞다"는 신호다. KaTeX의
  `throwOnError: false`(빨간 그림)는 쓰지 않는다 — 떴다 사라졌다 하면 화면만
  시끄럽고 무엇이 잘못됐는지는 그 글자에 없다.
- **코드 펜스 안은 안 본다.** 셸의 `$PATH`나 R의 `data1$col`이 수식으로
  둔갑하면 고칠 것 없는 자리에 상자가 뜬다.
- **인라인은 한 줄 안에서만 닫는다.** 줄을 넘겨 찾으면 본문의 진짜 `$` 둘이
  짝을 지어 문단 하나를 통째로 수식으로 만든다(본문에 진짜 `$`를 쓴 글이 90개다).
  짝이 없는 `$` 하나는 건너뛰고 다음부터 다시 본다 — 통째로 포기하면 뒤의
  멀쩡한 수식까지 못 찾는다.
- **캐럿 좌표는 `palette.js`의 것을 쓴다**(`window.blogPalette.caretXY`).
  커서 자리에 무언가를 띄우는 일이 둘이 됐는데 거울 div를 두 벌 두면 글꼴이나
  여백을 고칠 때 한쪽만 고쳐진다.
- **고칠 수 있는 화면에서는 수식이 없어도 KaTeX를 받는다**(`pageData.CanEdit`).
  편집기는 작업 도구라 무엇을 칠지 미리 알 수 없다 — admin이 늘 받는 것과 같은
  판단이고, 없으면 수식 하나 없던 글에 수식을 쓸 때 미리보기도 이 상자도
  아무것도 안 그린다. **읽는 사람에게는 안 나간다** — 그러지 않으면 자산을
  페이지별로 가른 것이 통째로 무의미해진다. highlight.js도 같이 받는다.
  **mermaid는 안 받는다**(3.5MB) — 그건 admin 편집기에서만 미리 보인다.
- **`Editor`와 `EditSlug`를 함께 봐야 한다.** 앞은 "누가 들어와 있나", 뒤는
  "무엇을 고칠 수 있나"라 질문이 다르다. 갈래 카드만 있는 분류처럼 고칠 본문이
  없는 화면에 편집기용 CDN을 실을 이유가 없다.
- **미리보기 지연을 250ms → 120ms로 줄이고 스크롤을 따라가게 했다.** 두 칸의
  높이가 달라 줄을 정확히 맞출 수는 없으므로 **비율로 맞춘다** — 없는 정확도를
  지어내지 않는다.
- **노션처럼 WYSIWYG로 가지는 않았다.** 그건 본문 정본을 블록으로 바꾸는
  일이라 "정해둔 것 ①"과 정면으로 부딪히고(1,357편을 되돌려야 한다), 마크다운
  위에 얹는 라이브 프리뷰도 CodeMirror 같은 번들을 들여와야 해서 "빌드 스텝
  없음"과 어긋난다. **그 값의 대부분은 수식 상자 하나에서 온다** — 나머지
  마크다운은 글자로 봐도 결과가 보이기 때문이다.
- 브라우저로 확인했다: 완성된 식은 그려지고, 미완성이면 이유가 뜨고, 수식
  밖이나 코드 펜스 안에서는 사라지고, 390px에서 문서폭이 안 넘친다. 돌연변이
  둘(읽는 사람에게도 실음 / 고칠 수 있어도 안 실음)을 넣어 테스트가 실제로
  실패하는 것을 확인했다.

<a id="section-34"></a>
### 글 화면에서 바로 고치기 (2026-08-31)

로그인이 확인되면 글 제목 옆에 "고치기"가 나오고, 누르면 **본문이 있던 자리가
편집기가 된다.** `/admin`으로 옮겨 가지 않으므로 읽던 맥락을 잃지 않는다
(`internal/web/static/inline-edit.js`).

**표지 글이 있는 카테고리 화면도 같은 자리를 낸다**(2026-09-06,
`templates/category.html`). 표지 본문은 카테고리 최상단에 그대로 펼쳐지는
글이라 post.html과 다를 이유가 없다 — `inline-edit.js`가 페이지의 첫
`<article>`을 그대로 집으므로 코드를 더 안 늘려도 된다. 갈래 카드만 있는
화면(`.Deck`)은 본문 자체가 없어 슬롯도 안 낸다.

**web과 admin의 경계를 지키는 방법이 이 기능의 핵심이다.**

- web은 "읽기 전용 공개 페이지"고 admin은 따로 있다. 세션이 무엇인지 web이
  알게 되면 그 경계가 무너지므로, **"지금 누가 들어와 있나"라는 질문 하나만**
  함수로 받는다(`web.WithEditor` ← `admin.Server.LoginFor`). 쿠키도 서명 키도
  web은 모른다.
- **기본값은 "닫힘"이다.** 옵션을 안 주면 글 화면은 예전 그대로다 — 버튼도
  스크립트도 나가지 않는다. `cmd/blog`가 `-admin`을 켤 때만 건넨다.
  그래서 **admin을 web보다 먼저 만든다.**
- **요청마다 다시 묻는다.** 한 번 로그인한 것을 서버가 기억해두면 세션이 풀린
  뒤에도 화면이 열린 채로 남는다. `render` 한 곳에서 채운다 — 사이드바와 자산
  판정을 거기서 채우는 것과 같은 이유다.
- **화면이 권한을 판단하지 않는다.** 버튼을 지운다고 아무것도 못 하게 되지
  않고, 억지로 눌러봐야 API가 401을 준다. 진짜 관문은 언제나 서버다.
- **draft를 가리는 규칙은 그대로다.** 로그인은 "고칠 수 있다"는 뜻이지
  "공개 화면의 규칙이 달라진다"는 뜻이 아니다. 그 둘이 섞이면 어느 화면이
  무엇을 보여주는지 아무도 모르게 된다.
- 뒷단은 admin과 **같은 API**다(`/api/admin/posts/{slug}`, `/api/admin/preview`).
  편집기를 두 벌 만들면 "여기서 본 것과 발행 뒤 화면이 같다"는 보장이 두 배로
  깨지기 쉬워진다. 팔레트도 같은 파일을 쓴다.
- **메타도 인라인 편집 패널에서 다룬다.** PUT은 통째로 교체하므로
  선택지를 아직 못 받은 필드는 기존 값을 보존한다. 후속 규칙 절을 참고한다.
- **저장 뒤에는 다시 그리지 않고 새로 받아온다.** 실제 글 화면은 렌더링 직전에
  죽은 링크를 손보는데(`resolveBody`) 미리보기는 그걸 안 한다 — 저장 뒤에
  그 차이가 남으면 안 된다.
- 취소하면 **원래 화면을 통째로 되돌린다.** 다시 그리면 수식·코드 색칠·복사
  버튼·애니메이션을 전부 다시 붙여야 하는데, 그 목록은 언젠가 하나 빠진다.
- 공개 글의 현재 편집기는 한 칸 블록 편집이다. Admin의 두 칸 편집기와 구분한다.
- 돌연변이 3종(옵션 없어도 실어보냄 / 로그인 안 해도 버튼을 그림 / 요청마다
  안 묻고 한 번만 물음)을 넣어 테스트가 실제로 실패하는 것을 확인했다.

<a id="section-35"></a>
### admin 화면의 메뉴

**상단 메뉴는 `전체 글` / `글감함` / `홈 화면` / `데이터` / `지도` / `환경설정`이다.**
홈 문구·자유 본문·최근 글 수는 `/admin/home`에서 편집한다.

- **메뉴는 서버가 그린다**(`templates/admin.html`). 진짜 링크라 스크립트가
  못 떠도 화면 사이를 오갈 수 있고, `admin.js`는 지금 어디인지 표시만
  덧입힌다(`ad-on`) — 사이드바를 서버에서 펼쳐 내보내는 것과 같다.
  각 주소가 껍데기를 주는지 테스트가 지킨다.
- **새 글과 편집 화면은 `전체 글`을 켠다.** 어디에도 안 걸린 화면을 만들지
  않는다.
- 지금 있는 곳은 **반전 블록**이다. 사이드바의 현재 위치와 같은 신호다.

**목록 아래에 필터를 깔았다**(찾기 · 상태 · 분류 · 본문 없는 것만).

- **서버에 다시 묻지 않는다.** 목록이 이미 통째로 와 있어서 거르는 일은 그
  자리에서 끝난다 — `/` 팔레트가 서버에 안 묻는 것과 같은 판단이다.
- **한 건도 안 남으면 그렇다고 적는다.** 빈 표만 남으면 거르개가 걸린 것인지
  목록을 못 가져온 것인지 화면만 보고는 알 수 없다.
- `본문 없는 것만`이 이 화면에서 가장 자주 하는 일이다 — 공개 화면에서
  제목만 뜨는 글이 그것들이다.

**환경설정에는 저장되는 자리가 다른 것이 섞여 있어, 절마다 어디에 남는지
적는다.** 테마 셋(시스템/화이트/다크)은 공개 화면과 **같은 `localStorage`
키**(`blog-theme`)에 저장하므로 admin에서 다크로 바꾸면 공개 화면도 다크다.
AI 설정은 반대로 **서버의 `settings` 표**에 남아 다른 기기에서도 같다. 한
화면에 있다고 같은 자리에 저장되는 줄 알면, 왜 하나는 따라오고 하나는 안
따라오는지 알 수 없다. 계정과 허용 목록은 서버가 정하는 것이라 여기서 바꿀
수 없다고 적어둔다 — **없는 것을 있는 척하지 않는다.**

**AI 초안 생성 절**(`internal/admin/ai.go`, `admin.js`의 `aiCard`)은 글감함의
"초안 생성"이 무엇으로 돌아가는지를 한 자리에 모은다 — 쓸 모델, 지시문,
그리고 OpenRouter에 남은 금액. 누르기 전에 보이는 것이 요점이다. 예전에는
버튼을 눌러 실패해야 키가 없다는 것을 알았다.

글감을 저장하거나 AI 초안 생성이 끝나면 가운데 `<dialog>`로 결과를 알린다.
초안 생성 완료 창의 `글 화면으로 가보기`는 공개되지 않은 draft의 admin 편집기로
간다. 공개 가능한 글을 저장한 뒤에는 자동 이동 대신 완료 창의
`화면으로 가보기`가 공개 글로 간다. 비공개 글은 저장 완료만 알린다.

기존 글의 `AI로 기존 글 수정`은 현재 편집기의 제목·본문과 수정 요청을 OpenRouter에
보내 수정안을 받는다(`POST /api/admin/posts/{slug}/ai-revise`). 서버는 현재 rev를
확인한 뒤 호출하며 글을 저장하지 않는다. 화면은 원본과 제안을 나란히 보여주고,
사람이 적용한 뒤 기존 저장 버튼을 눌러야 반영된다. 저장 때의 rev 충돌 검사와
status·visibility는 그대로 적용된다. 노션 이관 글은 기존 재이관 경고가 적용된다.

- **키는 이 화면에서 못 고친다.** 서버의 환경변수(`OPENROUTER_API_KEY`)이고
  배포가 넣는다. 응답에 실리는 것은 `configured` 불리언 하나뿐이다 —
  `blog.db`는 로컬로 내려받아 이관에 쓰는 파일이라, 키가 거기 섞이면 백업과
  작업본 전부가 secret을 들고 다니게 된다.
- **무엇이 실제로 쓰일지 고르는 자리는 `aiConfig` 하나다**(저장값 → 환경변수
  → 코드 기본값). 화면도 생성도 그 결과를 쓰고, 칸이 비어 있을 때 무엇이
  쓰이는지 화면이 글자로 적는다 — 빈 칸이 "아무것도 안 쓴다"로 읽히면 안 된다.
- **잔액과 모델 목록은 설정 조회와 다른 요청이다.** OpenRouter가 느리거나
  죽어도 설정 화면과 초안 생성은 그대로다. 모델 목록(수백 개)은 누를 때만
  받아 `<datalist>`에 넣는다 — 화면을 열 때마다 받으면 쓰지도 않는 사람이
  매번 기다린다.
- 새 컴포넌트를 만들지 않았다. 잔액은 데이터 화면의 `.ad-stats`(auto-fit이라
  폭마다 규칙을 따로 쓰지 않는다), 나머지는 `.ad-card`·`.ad-input`·`.ad-body`를
  그대로 쓴다. 손가락 화면에서는 입력 글자를 16px 위로 올린다 — 그 아래면
  iOS가 칸을 누를 때 확대하고 돌아오지 않는다.

- **비동기로 그리는 화면에는 표를 붙였다**(`drawTicket`). 목록과 데이터
  보기는 서버에 물어본 뒤에 그리는데, 그 사이에 메뉴를 한 번 더 누르면
  **늦게 온 응답이 새 화면을 덮어썼다** — 실제로 데이터를 누르고 곧장
  환경설정을 눌렀더니 주소는 설정인데 화면은 데이터였다. 헤드리스로 몰아보다
  찾았다.
- **표는 제 안에서만 가로로 스크롤한다**(`.ad-tablewrap`). 여섯 칸이라
  375px에서 35px쯤 넘쳐 페이지가 통째로 밀리고 있었다. 이제 세 화면 모두
  문서폭이 375다.

<a id="section-37"></a>
## 편집기·모바일의 후속 규칙

다음은 과거 완료 일지에만 있던 현재 규칙을 기능 설명으로 합친 것이다.

<a id="section-38"></a>
### 터치와 좁은 화면

- 터치 기기(`pointer: coarse`)의 주요 조작 영역은 44px 이상으로 둔다. 고정 높이 대신
  min-height를 써 여러 줄을 허용하고, 화살표 그림은 그대로 두되 누를 영역을 넓힌다.
- 입력 글자는 16px 이상으로 둬 iOS 포커스 확대를 피한다. viewport로 사용자 확대를 막지 않는다.
- 브랜드는 시각적 로고 크기를 키우지 않고 투명한 영역으로 터치 범위를 넓힌다.
- 터치 규칙도 `sitecss` 안에 둬 Admin 미리보기에 공유한다. 선택자 우선순위와 선언 순서를 확인한다.
- 메타 grid는 `minmax(0, 1fr)`와 항목의 `min-width: 0`으로 긴 select가 화면을 밀지 않게 한다.
- 서랍을 열면 껍데기에 포커스를 준다. 사용자는 Tab으로 링크에 들어가고 로고에 불필요한 링이 생기지 않는다.
- 좁은 화면 테스트에서 실제 viewport와 pointer 모드를 확인한다. 과거 macOS 헤드리스 창이
  500px 미만으로 줄지 않아 잘린 스크린샷을 모바일 레이아웃으로 오인한 적이 있다.
  iframe과 최상위 프레임의 pointer 동작도 다를 수 있다. 900px 시험 요소로 넘침 검사를 검증한다.
  elementFromPoint가 비정상적으로 빈 결과를 주면 프로브의 한계부터 확인한다.
- zsh의 스칼라 변수는 자동으로 단어 분리되지 않는다. 브라우저 플래그는 배열이나 개별 인자로 전달한다.

<a id="section-39"></a>
### 편집 상태와 저장

- 공개 글 화면은 블록 인라인 편집, `/admin`은 원문·미리보기 두 칸이다.
- 편집 중에는 저장된 본문에서 만든 목차를 숨긴다. `⌘S`/`Ctrl+S`는 문서 단위로 저장을 실행하고
  브라우저의 페이지 저장 동작을 preventDefault로 막는다.
- 미저장 변경이 있을 때만 beforeunload 경고를 건다. 저장 성공 후에는 이동 전에 해제한다.
- 분류·부모·형제 순서·작성일도 인라인 편집의 메타 패널에서 다룬다.
  선택지는 `/api/admin/categories`에서 받고, 아직 불러오지 못했으면 기존 값을 보존한다.
  PUT은 전체 교체라 누락하면 데이터가 사라진다.
- `markdown.SplitBlocks`의 분할·재결합은 렌더링을 유지해야 한다. 본문 끝 줄바꿈도 보존해
  글을 열고 닫기만 해도 변경으로 잡히는 일을 막는다.

<a id="section-40"></a>
### 공통 도구와 사이드바

- `pagetools`는 layout에 한 번 정의한다. 편집 메뉴는 `<details>`로 열고 패널은 본문을 밀지 않는다.
  JS가 필요한 고치기·지우기 버튼은 JS가 만든다. 삭제는 Admin의 refs·자식 차단·확인·rev 흐름을 따른다.
- `Editor`는 권한, `EditSlug`는 고칠 본문을 나타낸다. 본문 없는 갈래 카드 화면에는 편집 슬롯이 없다.
- `새 글`은 분류 화면에서 `?category=`를 전달한다. 글 상세도 activeCat을 채우므로 그 값만으로
  분류 화면을 판정하지 않는다. 낼 도구가 없으면 껍데기도 내보내지 않는다.
- 사이드바 GitHub·Pages·로그아웃·Admin은 `.side-grid` 한 그리드다. form은 칸을 채우고
  로그인 전에는 로그인 링크가 두 칸을 차지한다. 번역 키는 아이콘 바깥이 아니라 글자 span에 단다.
- 로그인 상태는 브랜드의 색 블록으로 표시한다. AdminOn은 Admin 기능 존재, Editor는 현재 로그인이다.
  로그아웃은 POST이며 인증 없는 로컬 서버에도 라우트가 있다.
- UI 글꼴은 `--chrome`의 한글 고정폭 우선 목록을 쓴다. 본문 산문에 강제하지 않고 웹폰트를 받지 않는다.
- 로그인 화면은 위·아래 띠를 가진 터미널 형태다. 돌아가기 링크도 창 안에 둔다.
- 데이터 보기(`/admin/data`)는 작성 콘텐츠 통계다. 방문자 추적은 하지 않는다. 분류별 직속 글을 세고
  막대는 최댓값에 대한 비율이다. 0인 불필요한 행은 생략한다. 글 목록에서 편집·보기·삭제를 제공한다.

<a id="section-41"></a>
### 요청 속도 제한

`internal/throttle`이 서버 핸들러에 연결되어 있다. 주소당 20/s, burst 60이고
초과 시 429와 Retry-After를 준다. 기억하는 주소는 최대 4096개이며 여유가 회복된 주소부터 비운다.
X-Forwarded-For의 마지막 주소를 신뢰하는 전제는 Caddy가 앞에 있고 blog가 loopback에만 있다는 것이다.
직접 외부에 노출하거나 프록시 구성을 바꾸면 ClientIP도 함께 검토한다. 회선 수준 DDoS 방어는 별도다.

<a id="section-42"></a>
### 저장 검증의 회귀 조건

`TestSaveRollsBackWhatItAlreadyWrote`처럼 첫 UPDATE 성공 후 다음 쓰기를 실패시켜
앞선 변경까지 남지 않는지 확인한다. 첫 UPDATE에서 바로 실패하는 테스트만으로는
여러 쓰기의 원자성을 확인할 수 없다. 새 글 픽스처와 이관 글 픽스처도 source와 notion_page_id를
실제 출처대로 구분해야 가드·통계 계약을 검증할 수 있다.
